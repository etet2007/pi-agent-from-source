Chapter 1: Architecture Overview — The Design Philosophy of a Minimal Agent

Nine packages with strictly one-way dependencies, a pure two-layer loop, and an organizing philosophy that keeps complexity out of the core

What You Are Up Against

A traditional CLI is a function: it takes arguments, performs a task, and exits. grep will never take it upon itself to run sed. The contract is simple and deterministic — one command, one action.

An agentic CLI breaks that contract. It takes a natural-language prompt, decides on its own which tools to call, executes them in whatever order it chooses, evaluates the results, and keeps looping until the task is done or the user stops it. A "program" is no longer a fixed set of instructions but a loop around a language model — the model dynamically generates its own instruction sequence at runtime. Tool calls are the side effects; the model's reasoning is the control flow.

The industry has two typical answers to this inherent complexity.

One is the monolith route: build in every capability that might ever be needed. A permission system, dozens of tools, context compaction, lifecycle hooks, a homegrown renderer — all packed into one enormous monolith. Claude Code is the representative of this route — nearly two thousand files, and behind every if branch stands a real failure that once happened. This complexity is "submarine-like": you cannot remove any single compartment, because seawater once leaked in through that exact spot.

Pi Agent offers another answer. Its CONTRIBUTING.md opens with a declaration:

pi's core is minimal. If your feature does not belong in the core, it should be an extension.

Pi's core exists to be minimal and to be extensible so that it can be influenced and manipulated by extensions.

This is not polite boilerplate in the docs; it is an organizing principle that runs through the entire codebase. The task of this chapter is to show you how that principle shapes every layer of the system — from the package boundaries, to the shape of the loop, to the security model, to the extension mechanism.

The Law of Conservation of Complexity

Before we go into details, let's establish a core observation that runs through the whole book.

The complexity a production-grade agent must handle is conserved: multi-provider adapters, streaming parsers, tool execution, concurrency safety, context bloat, persistence, error recovery, terminal rendering, extensibility — these hard problems do not vanish just because you don't write them. The monolith route absorbs all of them into the core; the minimalist route tries to push them to the edge — into extensions, into containers, into an optional daemon, into the caller's responsibility.

Pi Agent's key "push-outs":

ComplexityWhat the monolith route doesWhere Pi Agent pushes it out
Permissions & securitySeven built-in permission modes + per-tool approval dialogsContainers/sandboxes + a one-time "project trust" decision
Tool ecosystem40+ built-in tools7 built-in tools + extensions register custom tools
Lifecycle hooks27 runtime hook eventsStrongly typed ExtensionAPI (33 events)
External tool protocolsBuilt-in MCP (8 transports)Not provided; extensions integrate it themselves
Remote controlBuilt-in bridge / cloud executionStandalone optional packages pi-server / pi-protocol
Session storage backendBuilt-inAbstract interface + pluggable backends (JSONL / SQLite)

Each push-out makes the core a little smaller while handing the choice of "whether to take on this complexity" to the user. Once you understand this, you can explain almost every seemingly "missing" feature of Pi Agent — they weren't skipped; they were deliberately placed outside the core.

Nine Packages: The Dependency Stack Is the Architecture

Pi Agent is not a file tree; it is a monorepo. Its architecture shows up first in the package boundaries. Understanding the responsibility and dependency direction of each of the nine packages is understanding half the system.

This diagram has several features worth noting.

Dependencies are strictly one-way. pi-ai depends on no sibling package; pi-agent-core depends only on pi-ai; pi-coding-agent depends on pi-agent-core, pi-ai, and pi-tui. There are no circular dependencies. This means every layer can be lifted out and reused on its own — you could write an LLM application with no agent in it using pi-ai, or a terminal tool with no LLM in it using pi-tui.

pi-tui has nothing to do with LLMs. The terminal UI library depends on neither pi-ai nor pi-agent-core. It is a standalone, general-purpose diff-rendering library. Fully decoupling the UI from agent logic is one of the key differences between Pi Agent and agents where "UI and logic are tangled together." As we'll see in Chapter 12, the library isn't even built on React/Ink — it's entirely homegrown.

Remote capability is an independent side branch. pi-protocol and pi-client form a separate remote-session channel, while pi-server is a daemon that supervises headless agent subprocesses. They all depend on the product layer, but the product layer does not depend on them — installing the pi command itself needs no remote components at all. As we'll see in Chapter 15, there are actually two distinct remote-control designs hiding here.

Storage is pluggable. pi-storage-sqlite-node implements the storage interface defined by pi-agent-core, but the core does not depend on it. The default session storage is plain JSONL files (implemented in the product layer); SQLite is an optional backend with full-text search.

This arrangement is itself the first manifestation of "minimalism": the core is small because it has cut a large amount of responsibility out into separate packages.

Six Core Abstractions

If the monolith route is defined by six built-in subsystems, Pi Agent is defined by six interface abstractions. Everything else — the nine packages, dozens of files — exists to implement or consume these six abstractions.

1. StreamFn — the LLM boundary (packages/agent/src/types.ts). This is the only seam between the core loop and the model world:

export type StreamFn = (
	model: Model<Api>,
	context: Context,
	options?: SimpleStreamOptions,
) => AssistantMessageEventStream | Promise<AssistantMessageEventStream>;

The AssistantMessageEventStream it returns is an event stream that must end with either done or error, and both termination events carry the same AssistantMessage (packages/ai/src/types.ts, excerpt):

export type StopReason = "pending" | "stop" | "length" | "toolUse" | "error" | "aborted";

export interface AssistantMessage {
	role: "assistant";
	content: (TextContent | ThinkingContent | ToolCall)[];
	// ... api / provider / model / usage 等元数据字段
	stopReason: StopReason;
	errorMessage?: string;
	// ...
}

export type AssistantMessageEvent =
	// ... 中间的 text_delta / thinking_delta 等增量事件
	| { type: "done"; reason: Extract<StopReason, "stop" | "length" | "toolUse">; message: AssistantMessage }
	| { type: "error"; reason: Extract<StopReason, "aborted" | "error">; error: AssistantMessage };

There is one crucial convention in StreamFn's contract: it never throws. Failed requests, model errors, network outages — none of these may surface as exceptions; they must be encoded into the error event at the end of the stream. The AssistantMessage it carries marks the failure with stopReason: "error" | "aborted" and puts the details in errorMessage. This single convention makes the loop's error handling trivially simple — it never needs to try/catch a model call, only to inspect the stream's result. pi-ai's Models.streamSimple satisfies this shape; Chapter 2 will show how the entire pi-ai package is organized around the principle of "encoding failure into the stream."

2. AgentEvent — the loop's output (packages/agent/src/types.ts). The loop doesn't return one big object; it emits a sequence of lifecycle events:

agent_start | agent_end
turn_start  | turn_end
message_start | message_update | message_end
tool_execution_start | tool_execution_update | tool_execution_end

A "turn" = one assistant response plus its tool calls and their results. Every consumer — the TUI REPL, headless print mode, RPC mode — works by subscribing to this event stream. Chapter 11 will show that the essential difference between the three run modes is merely "how they render the same event stream."

3. AgentTool — the self-describing tool (packages/agent/src/types.ts):

export interface AgentTool<TParameters extends TSchema = TSchema, TDetails = any>
	extends Tool<TParameters> {
	label: string;
	prepareArguments?: (args: unknown) => Static<TParameters>;
	execute: (
		toolCallId: string,
		params: Static<TParameters>,
		signal?: AbortSignal,
		onUpdate?: AgentToolUpdateCallback<TDetails>,
	) => Promise<AgentToolResult<TDetails>>;
	executionMode?: ToolExecutionMode; // "sequential" | "parallel"
}

A tool is not just a function. It carries its own parameter schema (TypeBox), execution logic, concurrency declaration (executionMode), and progress-reporting callback (onUpdate). The loop knows nothing about a tool's internals — it only knows "validate against the schema, call execute, collect the result." Adding the N+1th tool requires no change to a single line of the loop. Detailed in Chapter 4.

4. AgentMessage and convertToLlm — the message bridge (packages/agent/src/types.ts, agent-loop.ts). Internally the loop uses an extensible message union type:

export interface CustomAgentMessages {} // 通过声明合并扩展
export type AgentMessage = Message | CustomAgentMessages[keyof CustomAgentMessages];

Message (from pi-ai) covers user | assistant | toolResult. But the product can stuff custom message types into the transcript — compaction summaries, branch summaries, bash execution records — which are meaningful to the UI yet should never be sent to the model. convertToLlm is the bridge: before every model call, it filters and converts the internal AgentMessage[] into a Message[] the provider can understand. This separation of "internal representation ≠ wire representation" is the key to Pi Agent accommodating custom message types without polluting the protocol.

5. The session tree — the persistent transcript (packages/agent/src/harness/session/session.ts). The transcript is not a flat array but an appendable, forkable tree of immutable entries. Every entry has an id, parentId, and timestamp; a leaf marker points at the "current position." moveTo(entryId) can repoint the leaf, enabling branching and backtracking; compaction doesn't delete history, it inserts a compaction entry. This design makes "fork a session" and "go back three steps and try another approach" first-class citizens. Detailed in Chapter 5.

6. ExtensionAPI — the typed extension surface (packages/coding-agent/src/core/extensions/types.ts). This is the most direct product of the minimalist philosophy. Pi Agent has no runtime hook strings and no MCP; it concentrates extensibility into one strongly typed interface:

export type ExtensionFactory = (pi: ExtensionAPI) => void | Promise<void>;

An extension receives a pi object and can on(event, handler) to subscribe to 33 events, registerTool(...) to register tools, registerCommand(...) to register slash commands, registerShortcut(...) to register keybindings, and registerFlag(...) to register CLI flags. Because everything is TypeScript types, extensions get full compile-time type checking and autocompletion. Detailed in Chapter 14.

Core and Harness: Two Layers in One Package

Inside the pi-agent-core package hides the key cut for understanding Pi Agent's design philosophy. It actually contains two layers:

The core runtime (src/agent.ts, src/agent-loop.ts, src/types.ts) is a stateful Agent class wrapping a pure, event-emitting loop. It only maintains the in-memory transcript; it never touches the filesystem and does no persistence. This is "the minimal core" taken literally — it is small enough to run in any environment, including a browser.

The harness layer (src/harness/**) builds on top of the core, adding persistent session-tree storage, context compaction, branch summaries, skills, prompt templates, and the built-in file/Shell tools. It is the optional layer for "if you want a ready-to-use, persistable agent."

The key insight: the product layer pi-coding-agent does not use the harness layer's AgentHarness class. In packages/coding-agent/src/core/sdk.ts it instantiates the core Agent directly:

import { Agent, type AgentMessage, setDefaultStreamFn } from "@earendil-works/pi-agent-core";
// ...
agent = new Agent({
	initialState: { systemPrompt: "", model, thinkingLevel, tools: [] },
	convertToLlm: convertToLlmWithBlockImages,
	streamFn: async (model, context, options) => modelRuntime.streamSimple(model, context, { ... }),
	// ...
});

The product layer then builds its own orchestrator AgentSession (3,333 lines) and its own JSONL session management SessionManager on top of the core Agent.

Why? Because the orchestration logic the product layer needs (the extension system, project trust, three run modes, slash commands, the model-switching UI) does not overlap with the concerns of the generic harness. pi-agent-core offers you both "a pure minimal loop" and "one generic persistence scheme," but it does not force you to use the latter — the product layer proves you can build a fully custom, product-specific orchestration layer on top of the minimal core alone.

This is the second manifestation of "minimalism": even inside a single package, the core stays pure and leaves the freedom of "how to orchestrate" to the layer above. Chapter 6 goes deep into the harness layer; Chapter 9 goes deep into the product layer's own AgentSession.

The Golden Path: From Keystroke to Output

Now let's trace the complete flow of a single request. You type "add error handling to the login function" and press Enter.

Three points about this path are worth noting, each mapping to a later chapter.

The loop is an event stream, not a callback chain. Inside Agent.prompt() drives runLoop, which emits AgentEvents through an emit callback. The Agent class reduces these events into its own mutable state and then dispatches them to subscribers. Consumers process events at their own pace — the TUI renders, print mode writes to stdout, RPC mode serializes to JSON. Chapter 3 will show that the loop itself is a clean two-layer nested state machine, with none of the thousand-line error-recovery mazes of the monolith route.

Model calls never throw. Because of StreamFn's contract, checking message.stopReason === "error" | "aborted" in the loop suffices to handle every model-layer failure. The complexity of error recovery is pushed out to pi-ai (two-layer retries) and to extensions (which can hook before_provider_request).

Tool execution is orthogonal to the model boundary. The loop doesn't know whether a tool reads files or runs a shell, nor whether it runs in parallel or sequentially — that information is cohesive inside AgentTool's own executionMode field. Chapter 4 will show that the concurrency strategy is just reading this field and choosing Promise.all or a for loop — nothing more.

The Security Model: Project Trust, Not Per-Tool Approval

This is the most glaring divergence between Pi Agent and the monolith route, and the most thorough expression of the minimalist philosophy.

The monolith route ships an elaborate permission system: multiple permission modes, an approval dialog before every tool call, and an LLM classifier that evaluates the transcript. Pi Agent's README.md simply forgoes all of it:

Pi does not include a built-in permission system for restricting filesystem, process, network, or credential access. By default, it runs with the permissions of the user and process that launched it.

If you need stronger boundaries, containerize or sandbox Pi.

It pushes isolation out to the operating system and containers (the README lists three containerization options: the Gondolin micro-VM, plain Docker, and the OpenShell sandbox).

But that doesn't mean Pi Agent does nothing about security. It narrows the security concern down to one question: do you trust the resources in the current project directory? Because the project directory may contain AGENTS.md, custom extensions, and skills — all of which influence the agent's behavior and may come from untrusted third-party repositories.

This decision is persisted by ProjectTrustStore in packages/coding-agent/src/core/trust-manager.ts (recorded per cwd), resolved by resolveProjectTrusted(...) in project-trust.ts, mapped to the --approve/-a and --no-approve/-na flags on the CLI, and to the /trust command plus a trust-selector component in interactive mode. Extensions can even hook the project_trust event to participate in the decision.

Tool-level "security" is expressed through allow/deny lists rather than approval dialogs: --tools, --exclude-tools, --no-tools, --no-builtin-tools, plus a "read-only tool group" (grep/find/ls are off by default).

This is a fundamentally different security posture: instead of a gate before every action, it makes one decision at the boundary and then makes the execution environment itself safe. The complexity of "judging each tool call for safety" is pushed out to containers and the user's trust decision. Chapter 14 will return to this model when discussing extensions.

Many Providers: Few Protocols, Many Endpoints

Pi Agent supports about 38 LLM providers (OpenAI, Anthropic, Google, Bedrock, Vertex, OpenRouter, Groq, xAI, DeepSeek…). Writing a bespoke adapter for each provider would be an enormous maintenance burden. pi-ai's solution introduces two layers:

  • Api (wire protocol): how to talk to a family of servers. About 10 of them: openai-completions, openai-responses, anthropic-messages, google-generative-ai, bedrock-converse-stream, mistral-conversations, and more.
  • Provider (a configured endpoint): one concrete runtime endpoint (id, baseUrl, auth, model catalog, which Apis it binds to). About 38 of them.

The key point: many providers reuse the same Api. OpenRouter, Groq, Together, and xAI all speak openai-completions/openai-responses. So about 10 protocol adapters unify about 38 vendors — few protocols, many endpoints. Adding a provider that "speaks OpenAI's dialect" takes little more than a factory function and a model-catalog file. Detailed in Chapter 2.

How the Pieces Connect

Put the six abstractions and nine packages together, and the system's dependencies and data flow look like this:

AgentSession is the product-layer hub: it holds the core Agent, turns user input into prompt() calls, translates the AgentEvents emitted by the Agent into higher-level AgentSessionEvents dispatched to the run modes, and also owns persistence, compaction, model switching, and extension binding. Practical Takeaways

If you're building an agent system, Pi Agent's architecture offers five transferable patterns.

Use the dependency stack as a firewall. Split the system into layers with strictly one-way dependencies (model layer → runtime layer → product layer), with each layer depending only on the abstract interfaces of the layer below. The problem it solves: complexity spreading freely inside a monolith. When pi-tui doesn't even depend on pi-ai, you know the UI's complexity can never leak into agent logic. Layer boundaries are the firewalls of complexity.

Make "whether to take on complexity" a choice. Permissions, remote, storage backends, extensions — none of these are forced into the core; they are optional packages or pushed-out responsibilities. The problem it solves: the core being held hostage by every edge-case requirement. When the core stays minimal, an SDK user who only wants to run an in-memory agent doesn't have to drag along an entire persistence and remote infrastructure.

Separate core from orchestration without forcing a binding. The same runtime package offers both a pure minimal loop and an optional persistable harness, but the product can use neither and build its own orchestration. The problem it solves: frameworks imposing their own orchestration assumptions on every user. Separate the "mechanism" (the loop) from the "policy" (how to orchestrate, how to persist), and policy can vary by product.

Encode failure into the stream instead of throwing. StreamFn's convention is to never throw; failure is a terminal event at the end of the stream. The problem it solves: try/catch scattered throughout an async streaming pipeline, with consumers unsure when to disconnect. When failure is data rather than control flow, error handling reduces to a single field check.

Put the security decision at the boundary, not before every action. Don't pop a dialog before each tool call; make one trust decision when entering the project, then make the execution environment itself (the container) safe. The problem it solves: approval fatigue and the maintenance burden of permission systems. Of course, this pattern presupposes you actually control the execution environment — if your agent runs directly on the user's host and can't be containerized, per-action approval may still be necessary. The minimalist security model has its limits; understanding those limits matters more than imitating it.

Summary

Pi Agent's architecture is an argument for restraint. It splits the system into nine packages with one-way dependencies, narrows the core to a pure two-layer loop, hands permissions to containers, extensions to a typed API, and storage to pluggable backends. It hasn't "done less" than the monolith route — it has simply placed every piece of extra complexity outside the core, letting users take it on as needed.

This design is not without cost. Delegating isolation to containers means a bare pi running on the host genuinely has all of the user's permissions; not providing MCP means people who want to plug into the external tool ecosystem must write their own extensions. The rest of this book will not shy away from these trade-offs. But once you grasp the "conservation of complexity" thread, you can see the deliberate trade-off behind every seemingly missing feature of Pi Agent.
