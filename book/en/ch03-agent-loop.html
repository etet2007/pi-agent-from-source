Part II · Agent Core

Chapter 3: Agent Loop — Two Nested Loops

Two nested loops, ten lifecycle events, and the "contract discipline" that pushes compaction, stopping, and resumption entirely outside the loop

The Beating Heart

Chapter 2 showed how pi-ai hides roughly 38 providers behind one unified streaming API — StreamFn goes in, AssistantMessageEventStream comes out, and failures are encoded into the stream. But a single model call is not an agent. An agent is a loop: call the model, execute tools, feed the results back, call the model again — until the work is done.

Every system has a center of gravity. In a database it's the storage engine; in a compiler it's the intermediate representation. In Pi Agent, it's packages/agent/src/agent-loop.ts — the core loop that drives every interaction, from the first keystroke in the REPL to the last tool call of a headless -p invocation.

If you've read query.ts from Claude Code in the companion book — that 1,730-line "submarine" with four layers of compaction, five kinds of error recovery, and ten terminal states — Pi Agent's loop will come as a relief. The runLoop function at the heart of agent-loop.ts is a two-level nested while loop: no compaction maze, no recovery ladder. Its complexity lives not inside the loop but in what it pushes outward: compaction goes to the transformContext callback, error recovery to pi-ai's two-layer retry, and stopping decisions to the shouldStopAfterTurn hook.

This chapter traces the loop from start to finish. By the end, you'll understand why it's so clean — and what that cleanliness costs.

The Shape of the Loop: Event Stream + emit Callback

The first architectural question: how does the loop tell the outside world about its progress?

Pi Agent's answer is to split the "pure loop logic" from the "observable wrapper" into two layers. At the bottom is an emit callback:

export type AgentEventSink = (event: AgentEvent) => Promise<void> | void;

export async function runAgentLoop(
	prompts: AgentMessage[],
	context: AgentContext,
	config: AgentLoopConfig,
	emit: AgentEventSink,
	signal: AbortSignal | undefined,
	streamFn: StreamFn,
): Promise<AgentMessage[]>

runAgentLoop takes an emit function, invokes it every time the loop makes progress, and finally returns all the new messages from this run. It is a pure "run a round" function — it doesn't care who is listening.

On top of that, agentLoop provides an observable wrapper that returns the EventStream you saw in Chapter 2:

export function agentLoop(
	prompts: AgentMessage[],
	context: AgentContext,
	config: AgentLoopConfig,
	signal: AbortSignal | undefined,
	streamFn: StreamFn,
): EventStream<AgentEvent, AgentMessage[]> {
	const stream = createAgentStream();
	void runAgentLoop(prompts, context, config, async (event) => {
		stream.push(event);
	}, signal, streamFn).then((messages) => {
		stream.end(messages);
	});
	return stream;
}

Notice how thin the wrapper is: it just bridges emit to stream.push and the return value to stream.end. The EventStream created by createAgentStream() completes on the agent_end event, extracting messages from it as the final result.

This contrasts with the choice Claude Code made in the companion book. Claude Code uses an async generator (yielding messages, returning a Terminal union type) as the shape of its loop. Pi Agent uses EventStream + emit callbacks. Both provide backpressure and composability, but Pi's separation has an extra benefit: the core runLoop depends on no streaming abstraction at all — it only knows one emit function. That lets any orchestrator (the core Agent, the Harness, or the product-layer AgentSession) drive the loop however it likes. Chapter 6 will show the Harness driving runAgentLoop directly, and Chapter 9 will show the product layer driving it indirectly through the core Agent.

There's also a pair of "continuation" variants, runAgentLoopContinue / agentLoopContinue, for retry scenarios — when the context already holds user messages or tool results, so no new messages need to be appended. They carry one precondition check: the last message must not be assistant (otherwise the provider rejects the request).

The Contract That Keeps the Loop Simple: Never Throw

Before tracing the loop body, you have to understand why it can be so lean. The secret lives in each callback of AgentLoopConfig. Open packages/agent/src/types.ts and you'll find the same sentence repeated in the docs of every callback:

export interface AgentLoopConfig extends SimpleStreamOptions {
	model: Model<any>;

	// Contract: must not throw or reject. Return a safe fallback value instead.
	convertToLlm: (messages: AgentMessage[]) => Message[] | Promise<Message[]>;

	// Contract: must not throw or reject. Return the original messages or another
	// safe fallback value instead.
	transformContext?: (messages: AgentMessage[], signal?: AbortSignal) => Promise<AgentMessage[]>;

	// Contract: must not throw or reject. Return undefined when no key is available.
	getApiKey?: (provider: string) => Promise<string | undefined> | string | undefined;

	// Contract: must not throw or reject.
	shouldStopAfterTurn?: (context: ShouldStopAfterTurnContext) => boolean | Promise<boolean>;

	prepareNextTurn?: (context: PrepareNextTurnContext) => AgentLoopTurnUpdate | undefined | Promise<...>;

	// Contract: must not throw or reject. Return [] when no steering messages are available.
	getSteeringMessages?: () => Promise<AgentMessage[]>;

	// Contract: must not throw or reject. Return [] when no follow-up messages are available.
	getFollowUpMessages?: () => Promise<AgentMessage[]>;

	toolExecution?: ToolExecutionMode; // 默认 "parallel"
	// ... beforeToolCall / afterToolCall / toolExecution 等
}

convertToLlm, transformContext, getApiKey, shouldStopAfterTurn, getSteeringMessages, getFollowUpMessages — each one says "must not throw or reject". Combined with StreamFn's never-throw contract from Chapter 2, every collaborator of the loop promises: failure is a return value, not an exception.

That's why there is almost no try/catch inside the loop. It doesn't need to defensively wrap every callback, because the contract has ruled out the exception path. The complexity didn't vanish — it moved to the contract's implementors (pi-ai encodes failures into the stream; convertToLlm returns a safe fallback value). It's a trade of "contract discipline" for "loop simplicity," and Pi Agent considers it a good deal.

The AgentLoopConfig callbacks are also the loop's entire seam with the outside world. Compaction? That's transformContext's job. Stop policy? That's shouldStopAfterTurn's job. Switching models between turns? That's prepareNextTurn's job. The loop itself knows nothing about any of this — it just invokes these callbacks at fixed points. The compaction of Chapter 7 and the product orchestration of Chapter 9 are both implemented by plugging callbacks into these slots.

The Loop Body: Two Levels of Nesting

Now for the core. runLoop is the heartbeat of the whole system; here's its skeleton (some details omitted for clarity):

async function runLoop(
	initialContext: AgentContext,
	newMessages: AgentMessage[],
	initialConfig: AgentLoopConfig,
	signal: AbortSignal | undefined,
	emit: AgentEventSink,
	streamFunction: StreamFn,
): Promise<void> {
	let currentContext = initialContext;
	let config = initialConfig;
	let firstTurn = true;
	let pendingMessages: AgentMessage[] = (await config.getSteeringMessages?.()) || [];

	// 外层循环：当 agent 本应停止后又有 follow-up 消息到达时继续
	while (true) {
		let hasMoreToolCalls = true;

		// 内层循环：处理工具调用与 steering 消息
		while (hasMoreToolCalls || pendingMessages.length > 0) {
			if (!firstTurn) await emit({ type: "turn_start" });
			else firstTurn = false;

			// 1. 注入待处理消息（steering）
			if (pendingMessages.length > 0) {
				for (const message of pendingMessages) {
					await emit({ type: "message_start", message });
					await emit({ type: "message_end", message });
					currentContext.messages.push(message);
					newMessages.push(message);
				}
				pendingMessages = [];
			}

			// 2. 流式获取助手响应
			const message = await streamAssistantResponse(currentContext, config, signal, emit, streamFunction);
			newMessages.push(message);

			// 3. 错误/中止 → 立即终止
			if (message.stopReason === "error" || message.stopReason === "aborted") {
				await emit({ type: "turn_end", message, toolResults: [] });
				await emit({ type: "agent_end", messages: newMessages });
				return;
			}

			// 4. 执行工具调用
			const toolCalls = message.content.filter((c) => c.type === "toolCall");
			const toolResults: ToolResultMessage[] = [];
			hasMoreToolCalls = false;
			if (toolCalls.length > 0) {
				const executedToolBatch =
					message.stopReason === "length"
						? await failToolCallsFromTruncatedMessage(toolCalls, emit)
						: await executeToolCalls(currentContext, message, config, signal, emit);
				toolResults.push(...executedToolBatch.messages);
				hasMoreToolCalls = !executedToolBatch.terminate;
				for (const result of toolResults) {
					currentContext.messages.push(result);
					newMessages.push(result);
				}
			}

			await emit({ type: "turn_end", message, toolResults });

			// 5. 轮间准备：可替换 context / model / thinking
			const nextTurnSnapshot = await config.prepareNextTurn?.({ message, toolResults, context: currentContext, newMessages });
			if (nextTurnSnapshot) {
				currentContext = nextTurnSnapshot.context ?? currentContext;
				config = { ...config, model: nextTurnSnapshot.model ?? config.model, /* thinking... */ };
			}

			// 6. 停止检查
			if (await config.shouldStopAfterTurn?.({ message, toolResults, context: currentContext, newMessages })) {
				await emit({ type: "agent_end", messages: newMessages });
				return;
			}

			// 7. 轮询 steering 消息
			pendingMessages = (await config.getSteeringMessages?.()) || [];
		}

		// 内层结束：agent 本应停止。检查 follow-up 消息。
		const followUpMessages = (await config.getFollowUpMessages?.()) || [];
		if (followUpMessages.length > 0) {
			pendingMessages = followUpMessages;
			continue; // 外层循环继续
		}
		break; // 真的结束了
	}

	await emit({ type: "agent_end", messages: newMessages });
}

That's the whole loop. Let's dissect its structure.

Inner loop: tool calls and steering

The inner while (hasMoreToolCalls || pendingMessages.length > 0) is the classic agent-loop shape: keep going as long as there are tool calls to handle. Each iteration:

  1. Emit turn_start (except on the first turn)
  2. Inject any pending steering messages
  3. Stream the assistant response
  4. If the response errors or aborts, terminate the whole agent
  5. Extract and execute tool calls, appending the results to the context
  6. Emit turn_end
  7. Call prepareNextTurn (may swap model/context)
  8. Call shouldStopAfterTurn (may stop gracefully)
  9. Poll for new steering messages

The update of hasMoreToolCalls is the key: it equals !executedToolBatch.terminate. In other words, as long as no tool call in the batch carries a "terminate" signal, the loop continues. The model doesn't need to explicitly say "I want to keep going" — as long as it issues tool calls, the loop continues by default; the moment it stops issuing tool calls, hasMoreToolCalls becomes false and the inner loop ends.

Outer loop: follow-up

The outer while (true) handles one special case: the agent has no more tool calls and no steering messages, so it should have stopped — yet follow-up messages may be waiting in the queue.

The difference between steering and follow-up is timing: steering means "interjecting while the agent is still working" (polled at the end of every inner-loop turn), while follow-up means "saying the next thing once the agent has finished" (polled by the outer loop after the inner loop ends). This two-level structure lets the product layer implement both "the user typed a clarification while the agent was working" (steering) and "the user queued the next task" (follow-up). Chapter 9 will show how AgentSession drives these two callbacks with two queues.

Continuation and stopping: all the decision points

Lay out the loop's exit paths in a table and you'll find there are surprisingly few:

Decision pointConditionOutcome
Model failurestopReason === "error" | "aborted"Emit agent_end, return
Tool terminationThe tool batch returns terminate: truehasMoreToolCalls = false, inner loop ends
No tool callsAssistant message has no toolCall blockhasMoreToolCalls = false, inner loop ends
Graceful stopshouldStopAfterTurn() returns trueEmit agent_end, return
Follow-up arrivesgetFollowUpMessages() is non-emptyOuter loop continues
Natural completionNo tools, no steering, no follow-upbreak, emit agent_end

No "four layers of compaction," no "escalation ladder," no discriminated union of ten terminal states. The loop's termination reasons have been pushed outward: compaction failures and token limits are handled in transformContext or pi-ai, and ultimately arrive at decision point 3 as stopReason: "error". This is the minimization philosophy made concrete inside the loop.

streamAssistantResponse: the LLM boundary

The only place in the loop that talks to the model is streamAssistantResponse. Its comment hits the nail on the head:

This is where AgentMessage[] gets transformed to Message[] for the LLM.

async function streamAssistantResponse(
	context: AgentContext,
	config: AgentLoopConfig,
	signal: AbortSignal | undefined,
	emit: AgentEventSink,
	streamFunction: StreamFn,
): Promise<AssistantMessage> {
	// 1. 可选的上下文变换（AgentMessage[] → AgentMessage[]）
	let messages = context.messages;
	if (config.transformContext) {
		messages = await config.transformContext(messages, signal);
	}

	// 2. 转换成 LLM 消息（AgentMessage[] → Message[]）
	const llmMessages = await config.convertToLlm(messages);

	// 3. 构建 LLM 上下文
	const llmContext: Context = {
		systemPrompt: context.systemPrompt,
		messages: llmMessages,
		tools: context.tools,
	};

	// 4. 解析 API key（对会过期的 token 很重要）
	const resolvedApiKey =
		(config.getApiKey ? await config.getApiKey(config.model.provider) : undefined) || config.apiKey;

	// 5. 调用 StreamFn，迭代事件流
	const response = await streamFunction(config.model, llmContext, { ...config, apiKey: resolvedApiKey, signal });

	let partialMessage: AssistantMessage | null = null;
	let addedPartial = false;
	for await (const event of response) {
		switch (event.type) {
			case "start":
				partialMessage = event.partial;
				context.messages.push(partialMessage);
				addedPartial = true;
				await emit({ type: "message_start", message: { ...partialMessage } });
				break;
			case "text_delta": /* ...各类 delta... */
				if (partialMessage) {
					partialMessage = event.partial;
					context.messages[context.messages.length - 1] = partialMessage;
					await emit({ type: "message_update", assistantMessageEvent: event, message: { ...partialMessage } });
				}
				break;
			case "done":
			case "error": {
				const finalMessage = await response.result();
				context.messages[context.messages.length - 1] = finalMessage;
				await emit({ type: "message_end", message: finalMessage });
				return finalMessage;
			}
		}
	}
	// ...
}

A few designs here are worth noting.

Two message conversions, each with a clear responsibility. transformContext works at the AgentMessage level (trimming old messages, injecting external context), while convertToLlm translates AgentMessage[] into the provider's Message[] (filtering out UI-only custom messages). Chapter 7's compaction hangs off transformContext; Chapter 5's custom-message filtering hangs off convertToLlm. Two slots, two concerns.

In-place updates of the partial message. When streaming starts, the start event brings a partial message that gets pushed into context.messages; each subsequent delta event replaces the last element of the array with the new partial (context.messages[context.messages.length - 1] = partialMessage). So the context always holds exactly one "in-progress" assistant message rather than one per delta. On done/error, it is replaced by the final message from response.result().

getApiKey is resolved on every call. The comment explains why: short-lived OAuth tokens, like GitHub Copilot's, can expire during a long tool-execution phase. Re-resolving the key before every model call avoids requesting with stale credentials.

done and error take the same path. Because EventStream's result() also resolves on error (resolving to the stopReason: "error" message), there's no need to distinguish success from failure here — just take the final message, emit message_end, and return. Failure handling is deferred to step 3 of the loop body (checking stopReason).

Truncation Protection: When Output Is Cut Off by the Token Limit

One piece of defensive code in the loop sits behind a real trap. When an assistant response has stopReason === "length" (output cut off by the token limit), the tool calls it emitted may carry truncated arguments.

The problem: streaming tool-call arguments are parsed incrementally by a "best-effort JSON salvager." A truncated tool call's arguments might happen to parse and validate, yet be silently incomplete — say, a file path cut off halfway. Executing such a tool call is dangerous.

The loop's response is to fail every tool call in the batch outright:

const executedToolBatch =
	message.stopReason === "length"
		? await failToolCallsFromTruncatedMessage(toolCalls, emit)
		: await executeToolCalls(currentContext, message, config, signal, emit);

failToolCallsFromTruncatedMessage produces an error result for each tool call, telling the model:

Tool call "X" was not executed: the response hit the output token limit, so its arguments may be truncated. Re-issue the tool call with complete arguments.

The model will then re-issue complete tool calls. It's a safety choice of "rather fail than execute a suspect call" — and since the failure results are fed back into the context, the loop naturally continues, giving the model a chance to retry.

prepareNextTurn: the between-turns makeover

prepareNextTurn is an easily overlooked but powerful hook. Called after each turn_end, it can return a new context, model, or thinkingLevel:

const nextTurnSnapshot = await config.prepareNextTurn?.({ message, toolResults, context: currentContext, newMessages });
if (nextTurnSnapshot) {
	currentContext = nextTurnSnapshot.context ?? currentContext;
	config = {
		...config,
		model: nextTurnSnapshot.model ?? config.model,
		reasoning: nextTurnSnapshot.thinkingLevel === undefined ? config.reasoning : /* ... */,
	};
}

Note that what it replaces are the loop's local variables, currentContext and config — the next turn uses the new values. This lets the product layer switch models mid-conversation (e.g., "use a stronger model for this task"), re-read the session tree to pick up changes made while it runs, or adjust the thinking level. Chapter 9 will show how AgentSession uses this hook to rebuild the context from the session tree between turns.

AgentEvent: the language of the loop

The loop says nothing but AgentEvent. This discriminated union (packages/agent/src/types.ts) is the loop's only language for talking to the outside world:

export type AgentEvent =
	// Agent 生命周期
	| { type: "agent_start" }
	| { type: "agent_end"; messages: AgentMessage[] }
	// 轮次生命周期 - 一个轮次 = 一次助手响应 + 其工具调用/结果
	| { type: "turn_start" }
	| { type: "turn_end"; message: AgentMessage; toolResults: ToolResultMessage[] }
	// 消息生命周期 - user、assistant、toolResult 都会发
	| { type: "message_start"; message: AgentMessage }
	| { type: "message_update"; message: AgentMessage; assistantMessageEvent: AssistantMessageEvent }
	| { type: "message_end"; message: AgentMessage }
	// 工具执行生命周期
	| { type: "tool_execution_start"; toolCallId: string; toolName: string; args: any }
	| { type: "tool_execution_update"; toolCallId: string; toolName: string; args: any; partialResult: any }
	| { type: "tool_execution_end"; toolCallId: string; toolName: string; result: any; isError: boolean };

Ten events cover the lifecycles of four layers: agent, turn, message, and tool. message_update fires only while an assistant message is streaming, carrying the raw AssistantMessageEvent (from pi-ai) so consumers can render incrementally.

The core Agent class (packages/agent/src/agent.ts) plays the role of a reducer over this event stream. Its processEvents(event) method updates its mutable state according to event type — message_end appends a message to messages, tool_execution_start/end add or remove entries in the pendingToolCalls set — and then dispatches the events to all subscribers. Chapter 5 will detail Agent's state management.

This "the loop emits events, upper layers reduce" architecture lets a single loop serve completely different consumers: the TUI renders events into pixels, print mode writes them out as text or JSON, and RPC mode serializes them across a pipe. They all subscribe to the same AgentEvent stream, differing only in how they reduce it. Chapter 11 will show how the three operating modes consume this stream.

A Worked Example: "Fix the Bug in auth.ts"

Let's make the loop concrete. We'll trace three turns of a real interaction.

User input: Fix the null pointer bug in src/auth/validate.ts

Turn 1: the model reads the file. runAgentLoop emits agent_start and turn_start, then emits message_start/message_end for the user message. First pass through the inner loop: streamAssistantResponse calls the model, which streams back "let me take a look at this file" plus one toolCall: read({ path: "src/auth/validate.ts" }). stopReason is toolUse, not error, so we continue. One tool call is extracted, and executeToolCalls runs it (read is concurrency-safe; Chapter 4 goes into detail), with the file content appended to the context as a toolResult. hasMoreToolCalls = true (no terminate). turn_end. shouldStopAfterTurn returns false. Poll steering — none. The inner loop continues.

Turn 2: the model edits the file. turn_start. The model streams back "there's a bug at line 42 — userId could be null" plus one toolCall: edit({ path: ..., old_string: ..., new_string: ... }). edit isn't concurrency-safe, but this batch has only one tool, so it runs serially. The edit applies cleanly; the toolResult is appended. turn_end. Continue.

Turn 3: the model declares done. turn_start. The model streams back "I added a guard clause that fixes the null pointer bug." No toolCall block. toolCalls.length === 0, so hasMoreToolCalls stays false. turn_end. shouldStopAfterTurn returns false. Poll steering — none. The inner-loop condition hasMoreToolCalls || pendingMessages.length > 0 is false, so we exit the inner loop. The outer loop polls for follow-up — none. break. Emit agent_end.

In total: three model calls, two tool executions, zero permission prompts (Pi Agent has no per-tool approval; see Chapter 1). The entire flow completes within the same two-level while structure, with not a single special-case branch.

Practical Takeaways

Pi Agent's loop offers four transferable patterns for "how to design an agent's main loop."

Trade contract discipline for loop simplicity. Make every collaborator of the loop — model calls, message conversion, stop decisions, message queues — promise "never throw; failure is a return value." The problem it solves: try/catch scattered throughout the loop, error handling entangled with the normal flow. Once the exception path is excluded by contract, the loop degenerates into a plain sequence of steps. The cost is that you must implement these contracts seriously — but the complexity is pushed to the boundaries instead of pervading the core.

Separate loop logic from the observable wrapper. The core loop knows only one emit callback; the EventStream wrapper is a paper-thin bridge. The problem it solves: a loop locked into a single consumption style. When runLoop depends on no streaming abstraction, any orchestrator can drive it however it likes — an in-memory Agent, a persistent Harness, a product session — all reusing the same loop.

Use nested loops to express events with different timing. The inner loop handles "interjections during work" (steering); the outer loop handles "continuations after work" (follow-up). The problem it solves: conflating the two timings, so either interjections get ignored or continuations fire too early. With two loops, two queues, and two callback slots, the timing semantics become clear.

Be skeptical of results that look successful but are actually suspect. A truncated tool call's arguments may parse yet be incomplete — better to fail them and let the model re-issue than to execute a suspect call. The problem it solves: the "best-effort" nature of incremental streaming parsing quietly produces half-baked data. In agent systems, "it parses" does not equal "it's safe," and paranoia about edge cases is worth it.

If you were starting from scratch, the minimal loop skeleton would be:

async function runLoop(context, config, emit, streamFn) {
  while (true) {
    let hasMore = true;
    while (hasMore || pending.length) {
      inject(pending); pending = [];
      const msg = await streamAssistantResponse(context, config, streamFn);
      if (msg.stopReason === "error" || msg.stopReason === "aborted") return end();
      const calls = toolCalls(msg);
      hasMore = calls.length ? !execute(calls).terminate : false;
      if (await config.shouldStopAfterTurn?.()) return end();
      pending = await config.getSteeringMessages?.() || [];
    }
    const followUp = await config.getFollowUpMessages?.() || [];
    if (followUp.length) { pending = followUp; continue; }
    break;
  }
  return end();
}

Every detail in Pi Agent's loop is a refinement of this skeleton: streamAssistantResponse refines the model call, failToolCallsFromTruncatedMessage refines tool execution, and prepareNextTurn refines the between-turn transition. Start from the skeleton, and add a refinement only when you actually encounter the problem it solves.

Summary

Pi Agent's core loop is a two-level nested while: the inner level handles tool calls and steering, the outer level handles follow-up. It emits ten kinds of AgentEvent through the emit callback, meets the model world through StreamFn, and pushes compaction, stopping, resumption, and between-turn transitions entirely outward through a set of never-throw callback slots (transformContext, convertToLlm, shouldStopAfterTurn, prepareNextTurn, getSteeringMessages, getFollowUpMessages).

It is clean not because agents are simple, but because the complexity has been deliberately pushed outside the loop. Understand that, and you grasp Pi Agent's most fundamental disagreement with the all-in-one route: it's not about who does more, but about where each one places its complexity.
