Chapter 8: The Bootstrap Pipeline: From cli.ts to Mode Dispatch

The full startup journey, from process-level setup to three run shapes: subcommands exit early, TTY detection auto-downgrades - all in service of loading nothing you don't need

The Birth of a Command

Across the previous three parts, we worked bottom-up through pi-ai (the model layer) and pi-agent-core (the runtime layer). Now we enter the product layer, pi-coding-agent - the pi command itself. This chapter traces the most everyday of actions: what happens between the moment you type pi and press Enter, and the moment the prompt waiting for input appears on screen.

The startup pipeline may look trivial, but it exposes a product's core architectural decisions. Pi Agent's startup must answer a chain of questions in a very short time: which mode? which model? trust this project? load which extensions? activate which tools? And these decisions must be made without loading anything you don't need - recall the lazy loading of Chapter 2; startup speed is Pi Agent's obsession.

We will see how this pipeline fans out "one CLI command" into three very different run shapes: the interactive TUI, headless print, and RPC for IDEs.

The Entry Shim: cli.ts

Everything starts with a minimal entry file (packages/coding-agent/src/cli.ts):

#!/usr/bin/env node
import { APP_NAME } from "./config.ts";
import { configureHttpDispatcher } from "./core/http-dispatcher.ts";
import { main } from "./main.ts";

process.title = APP_NAME;
process.env.PI_CODING_AGENT = "true";
process.emitWarning = (() => {}) as typeof process.emitWarning;

// 在任何提供商 SDK 发请求之前配置 undici 的全局 dispatcher
configureHttpDispatcher();

main(process.argv.slice(2));

This file does just four things, each deliberate:

  • process.title = APP_NAME: sets the process name to pi, so ps shows pi instead of node.
  • process.env.PI_CODING_AGENT = "true": stamps an environment marker. Child processes (like the shells tools launch) can use it to know they are running inside pi.
  • process.emitWarning = () => {}: silences Node's warning output. A user-facing CLI should not be spammed with DeprecationWarnings.
  • configureHttpDispatcher(): configures the global dispatcher of undici (Node's HTTP client) before any provider SDK sends a request - this is where the HTTP proxy is set. The comment stresses the timing: it must happen before the first request.

Then it calls the real bootstrap function, main(process.argv.slice(2)). Separating the entry shim from the bootstrap logic lets main be called programmatically - SDK users, tests, and the daemon can call main or the lower-level createAgentSession directly without going through this shim.

main(): The Bootstrap Sequence

main() (packages/coding-agent/src/main.ts, about 918 lines) is the real bootstrap. Its signature reveals an extension point:

	extensionFactories?: InlineExtension[];

export async function main(args: string[], options?: MainOptions)

A few key nodes deserve a closer look.

Subcommands exit early. Subcommands like pi install/remove/update/list (package management) and pi auth print-api-key (credential printing) are handled and exit early in bootstrap - they don't need a full Agent session. This avoids the waste of "wanting just a version number but waiting for an entire session to assemble."

The createRuntime factory closure. main does not create the session directly; instead it builds a factory closure, createRuntime, and hands it to createAgentSessionRuntime:

const createRuntime: CreateAgentSessionRuntimeFactory = async ({ ... }) => {
	// 在这里解析项目信任、构建 services、创建 AgentSession
	const trusted = await resolveProjectTrusted({ cwd, trustStore, trustOverride, defaultProjectTrust, extensionsResult, ... });
	// ...
};
const runtime = await createAgentSessionRuntime(createRuntime, { ... });

Why a factory instead of creating directly? Because the session may need to be recreated - the /reload command, switching sessions, and forking all trigger a rebuild. The host, AgentSessionRuntime, holds the factory and calls it to reassemble a fresh session when needed. Chapter 9 will show this runtime host.

Project trust is decided during bootstrap. resolveProjectTrusted (the trust model from Chapter 1) is called during bootstrap to decide whether to load this project's extensions/skills/AGENTS.md. The decision affects later assembly - untrusted means project resources are skipped.

Mode Resolution: resolveAppMode

The core decision of bootstrap is "which mode to enter." That decision is surprisingly simple (packages/coding-agent/src/main.ts):

function resolveAppMode(parsed: Args, stdinIsTTY: boolean, stdoutIsTTY: boolean): AppMode {
	if (parsed.mode === "rpc") {
		return "rpc";
	}
	if (parsed.mode === "json") {
		return "json";
	}
	if (parsed.print || !stdinIsTTY || !stdoutIsTTY) {
		return "print";
	}
	return "interactive";
}

Four modes, in priority order:

ModeTriggerUse
rpc--mode rpcJSON-RPC over stdin/stdout, for IDEs/daemon
json--mode jsonheadless, streams all events out as JSON lines
print--print/-p, or stdin/stdout is not a TTYheadless, prints only the final text
interactivedefault (both TTYs present)full TUI REPL

Notice the elegance of the third branch: !stdinIsTTY || !stdoutIsTTY. It means echo "fix the bug" | pi automatically downgrades to print mode - because stdin is occupied by a pipe, not an interactive terminal. Likewise, pi > out.txt also downgrades. This embodies the Unix philosophy: a program should adjust its behavior based on whether it is attached to a terminal, so piped compositions just work. --print is explicit force; TTY detection is implicit inference.

toPrintOutputMode folds both json and print into the print path, differing only in the output format (json vs text):

function toPrintOutputMode(appMode: AppMode): Exclude<Mode, "rpc"> {
	return appMode === "json" ? "json" : "text";
}

So json and print share the runPrintMode implementation, differing only in the output-mode parameter. RPC takes the entirely separate runRpcMode.

Argument Parsing: parseArgs

parseArgs (packages/coding-agent/src/cli/args.ts) parses command-line arguments into an Args object. Its fields cover the product's entire configurable surface:

export interface Args {
	provider?; model?; apiKey?;           // 模型选择
	systemPrompt?; appendSystemPrompt?;    // 提示词定制
	thinking?;                             // off|minimal|low|medium|high|xhigh|max
	continue?; resume?;                    // 会话续接
	help?; version?; mode?; name?;
	noSession?; session?; sessionId?; fork?; sessionDir?; // 会话管理
	models?;                               // Ctrl+P 循环的模型集
	tools?; excludeTools?; noTools?; noBuiltinTools?; // 工具控制
	extensions?; noExtensions?;            // 扩展控制
	print?; export?; noSkills?; skills?;
	promptTemplates?; themes?; noContextFiles?;
	listModels?; offline?; alt?; verbose?;
	projectTrustOverride?;                 // --approve / --no-approve
	messages: string[];                    // 位置参数（提示词）
	fileArgs: string[];                    // @file 参数
	unknownFlags: Map<string, boolean | string>; // 未知 flag，留给扩展
	diagnostics: ...;
}

A few design choices stand out.

Fine-grained control over tools and extensions. --tools/--exclude-tools/--no-tools/--no-builtin-tools give precise control over the tool set - this is the CLI surface of Pi Agent's "allow/deny list replaces per-tool approval" security model (Chapter 1). --extensions/--no-extensions likewise control extension loading.

The @file argument. fileArgs collects arguments of the form @path/to/file, handled by file-processor.ts - appending the file's contents to the prompt. It's the convenient syntax for "feeding a file to the agent."

unknownFlags is reserved for extensions. Any --flag that pi itself doesn't recognize is not an error; it's collected into unknownFlags and handed to the extension system. Extensions can register their own CLI flags (Chapter 14) and receive arguments through this mechanism. This is how the core CLI opens itself to extensions - the core doesn't reject unknown flags; it passes them to whoever might understand them.

The help text generated by printHelp lists the built-in tool names (read, bash, edit, write, grep, find, ls) and all flags, and dynamically adds flags registered by extensions.

Dispatch: Three Paths

The last step of bootstrap is dispatch by mode (packages/coding-agent/src/main.ts):

if (appMode === "rpc") {
	printTimings();
	await runRpcMode(runtime);
} else if (appMode === "interactive") {
	const interactiveMode = new InteractiveMode(runtime, {
		migratedProviders,
		modelFallbackMessage,
		autoTrustOnReloadCwd,
		initialMessage,
		initialImages,
		initialMessages: parsed.messages,
		verbose: parsed.verbose,
		alt: parsed.alt,
	});
	// ... startupBenchmark 特判 ...
	printTimings();
	await interactiveMode.run();
} else {
	printTimings();
	const exitCode = await runPrintMode(runtime, {
		mode: toPrintOutputMode(appMode),
		messages: parsed.messages,
		initialMessage,
		initialImages,
	});
	stopThemeWatcher();
	restoreStdout();
	if (exitCode !== 0) process.exitCode = exitCode;
	return;
}

All three paths share the same runtime (AgentSessionRuntime), but consume it very differently:

  • runRpcMode(runtime): enters a JSON-RPC loop, reading commands from stdin and writing responses/events to stdout until the peer closes. It renders no UI - it's for machines (IDEs, daemon).
  • new InteractiveMode(runtime).run(): builds a pi-tui TUI and enters the interactive REPL. This one is for humans.
  • runPrintMode(runtime, ...): runs one (or a few) turns of conversation, writes the final text or a JSON event stream to stdout, then exits with an exit code. This one is for scripts and pipelines.

Note that printTimings() is called before every path - if PI_STARTUP_BENCHMARK is set, it prints how long each startup stage took. Pi Agent's obsession with startup speed shows up in this performance instrumentation that can be switched on at any time.

There's also a startupBenchmark special case: in interactive mode, if the startup benchmark is set, it init()s the TUI, waits 150ms for the stdin handler to consume the terminal query replies (Kitty keyboard protocol, device attributes, cell size - detailed in Chapter 13), then immediately stop()s and exits. This measures, precisely, the time "from startup to TUI ready."

The Assembly Hub: createAgentSession

Whatever the mode, everything ultimately needs an AgentSession. Its creation lives in createAgentSession in packages/coding-agent/src/core/sdk.ts:

export interface CreateAgentSessionOptions {
	model?; thinkingLevel?; tools?; excludeTools?; noTools?; customTools?;
	cwd?; agentDir?; resourceLoader?; settingsManager?; sessionManager?; modelRuntime?;
	// ...
}
export interface CreateAgentSessionResult {
	session: AgentSession;
	extensionsResult: LoadExtensionsResult;
	modelFallbackMessage?: string;
}
export async function createAgentSession(options: CreateAgentSessionOptions = {}): Promise<CreateAgentSessionResult>

This function is the hub where the three packages meet. It resolves cwd/agentDir, creates ModelRuntime (from pi-ai), SettingsManager, SessionManager, and DefaultResourceLoader, resolves the initial model and thinking level, computes the active tool set, then instantiates the core Agent:

agent = new Agent({
	initialState: { systemPrompt: "", model, thinkingLevel, tools: [] },
	convertToLlm: convertToLlmWithBlockImages,
	streamFn: async (model, context, options) => {
		const providerRetrySettings = settingsManager.getProviderRetrySettings();
		// ... 解析超时、重试设置 ...
		return modelRuntime.streamSimple(model, context, {
			...options,
			timeoutMs,
			maxRetries: options?.maxRetries ?? providerRetrySettings.maxRetries,
			maxRetryDelayMs: options?.maxRetryDelayMs ?? providerRetrySettings.maxRetryDelayMs,
			transformHeaders: async (requestHeaders) => {
				const headers = mergeProviderAttributionHeaders(model, settingsManager, options?.sessionId, requestHeaders);
				return headerRunner?.hasHandlers("before_provider_headers")
					? headerRunner.emitBeforeProviderHeaders(headers ?? {})
					: (headers ?? {});
			},
		});
	},
	// onPayload / onResponse / transformContext / 扩展 hook ...
});

Look at this streamFn: it's a closure that plugs the core Agent's StreamFn slot into pi-ai's modelRuntime.streamSimple. But it's not a simple pass-through - in the middle it injects settings (timeouts and retry policy read from SettingsManager) and extension hooks (transformHeaders fires the extension's before_provider_headers event). This is the concrete embodiment of the product layer "building its own orchestration on top of the core Agent" (Chapter 6): the core only knows a streamFn; the product layer stuffs settings management and the extension system into that slot.

convertToLlmWithBlockImages is the product-grade version of the message bridge - on top of convertToLlm, it dynamically decides, based on settingsManager.getBlockImages(), whether to replace images with the placeholder text "Image reading is disabled." Note the comment: "Check setting dynamically so mid-session changes take effect" - settings are read dynamically on every call, so changing a setting mid-session takes effect immediately.

Once Agent is created, it's wrapped into an AgentSession (the protagonist of Chapter 9). createAgentSession returns { session, extensionsResult, modelFallbackMessage } - extensionsResult is the result of extension loading, and modelFallbackMessage is the notice "the model you asked for isn't available, so we fell back to another."

Practical Takeaways

Pi Agent's startup pipeline offers four transferable patterns for "how to design the startup of a CLI product."

Separate the entry shim from the bootstrap logic. cli.ts only does process-level setup (title, env, HTTP dispatcher) and then calls main; the bootstrap logic lives in main and can be called programmatically. The problem it solves: coupling the CLI entry to reusable logic forces SDK users and tests to go through the shim. After separation, the same main/createAgentSession serves the CLI, the SDK, and the daemon.

Use TTY detection to downgrade modes automatically. !stdinIsTTY || !stdoutIsTTY automatically switches to headless mode, letting piped compositions just work. The problem it solves: users would have to remember to add --print to use it in scripts. When a program adjusts itself based on whether it's attached to a terminal, echo ... | pi and pi | grep ... "just work" - that's the essence of Unix composability.

Use a factory closure to defer creation and support rebuilding. main doesn't create the session directly; it hands a createRuntime factory to the runtime host, which rebuilds when needed. The problem it solves: sessions need to be recreated (reload, switch, fork), but the creation logic was scattered around. Wrapping creation in a factory turns rebuilding into "just call the factory again."

Stay open to unknown input; hand it to whoever can handle it. The core CLI doesn't reject unknown --flags; it collects them into unknownFlags and passes them to extensions. The problem it solves: either the core CLI is forced to know every extension's arguments, or extensions can't own their own arguments. When the core hands unknown input onward, extensions get their own CLI surface while the core stays stable.

Summary

The startup of the pi command is a carefully designed pipeline: cli.ts does process-level setup, then calls main; main merges extensions, parses arguments, uses resolveAppMode (combining explicit flags and TTY detection) to decide which mode to enter, makes the project-trust decision during bootstrap, builds the createRuntime factory, creates the AgentSessionRuntime host, and finally dispatches to the three paths: runRpcMode/InteractiveMode/runPrintMode. All three paths share the same runtime but consume it differently - for machines, for humans, for scripts. And createAgentSession is the hub where the three packages meet: it plugs the core Agent's streamFn slot into pi-ai, injecting settings management and extension hooks in between.

Every design in the startup pipeline - subcommands exiting early, lazy loading, automatic TTY downgrade, the startup benchmark - points to the same obsession: be fast, and don't load anything you don't need.
