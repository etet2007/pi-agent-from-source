Part II · Agent Core

Chapter 5: State, Messages, and the Session Tree

Defensive copying in memory, the bridge at the message layer, the immutable session tree, and pluggable storage backends — Pi Agent splits "memory" into four layers

What an Agent Needs to Remember

The previous chapters were about "actions": how the model gets called, how tools get executed. But an agent is more than its actions — it also has memory. It has to remember how far the conversation has gotten, which tools it has used, and which model it is currently using. An agent without state will keep repeating the same mistakes forever.

Pi Agent's state is organized in two levels, matching two very different needs:

  • In-memory state: the current transcript and runtime flags held by the core Agent class. It has a short lifetime (one run), is read and written frequently, and needs no persistence.
  • Persistent state: the session tree. It has a long lifetime (across runs and restarts), needs to be forkable and compactable, and must be able to land on disk.

The relationship between these two levels — and Pi Agent's distinctive choice to model the persistent transcript as a tree rather than an array — is the subject of this chapter. The latter is the design that sets Pi Agent apart from most agents: it makes "fork a session", "go back three steps and try a different angle", and "compact without losing history" all first-class citizens.

Layer One: In-Memory State

The core Agent class (packages/agent/src/agent.ts) is a "stateful wrapper around the loop". Its doc comment is blunt:

Stateful wrapper around the low-level agent loop. Agent owns the current transcript, emits lifecycle events, executes tools, and exposes queueing APIs for steering and follow-up messages.

Copying Arrays with Accessor Properties

Agent's state is created by createMutableAgentState. This function has a detail worth noting — tools and messages are not plain fields but getter/setter accessor properties, and the setters copy the array passed in:

function createMutableAgentState(initialState?) {
	let tools = initialState?.tools?.slice() ?? [];
	let messages = initialState?.messages?.slice() ?? [];
	return {
		systemPrompt: initialState?.systemPrompt ?? "",
		model: initialState?.model ?? DEFAULT_MODEL,
		thinkingLevel: initialState?.thinkingLevel ?? "off",
		get tools() {
			return tools;
		},
		set tools(nextTools: AgentTool<any>[]) {
			tools = nextTools.slice(); // 复制顶层数组
		},
		get messages() {
			return messages;
		},
		set messages(nextMessages: AgentMessage[]) {
			messages = nextMessages.slice(); // 复制顶层数组
		},
		isStreaming: false,
		streamingMessage: undefined,
		pendingToolCalls: new Set<string>(),
		errorMessage: undefined,
	};
}

The state fields fall into two groups. One group is configuration (systemPrompt, model, thinkingLevel, tools, messages), set by the caller; the other is runtime (isStreaming, streamingMessage, pendingToolCalls, errorMessage), maintained by Agent itself during a run and read-only from the outside.

Why do the setters copy with slice()? It is a lightweight form of defensive immutability: after the caller writes agent.state.messages = someArray, later mutations of someArray do not affect the copy Agent holds internally. It only copies the top-level array (no deep copy of the message objects), striking a balance between "keeping the external array from being accidentally mutated" and "copy cost". Note that the appends to messages inside the loop (context.messages.push(...)) operate on the snapshot copied by createContextSnapshot(), not on this state array itself — as seen in Chapter 3, the loop receives messages.slice().

processEvents: The Event Reducer

Chapter 3 said the loop emits AgentEvents via emit. The Agent class reduces those events into its own state. processEvents is that reducer:

private async processEvents(event: AgentEvent): Promise<void> {
	switch (event.type) {
		case "message_start":
			this._state.streamingMessage = event.message;
			break;
		case "message_update":
			this._state.streamingMessage = event.message;
			break;
		case "message_end":
			this._state.streamingMessage = undefined;
			this._state.messages.push(event.message);
			break;
		case "tool_execution_start": {
			const pendingToolCalls = new Set(this._state.pendingToolCalls);
			pendingToolCalls.add(event.toolCallId);
			this._state.pendingToolCalls = pendingToolCalls;
			break;
		}
		case "tool_execution_end": {
			const pendingToolCalls = new Set(this._state.pendingToolCalls);
			pendingToolCalls.delete(event.toolCallId);
			this._state.pendingToolCalls = pendingToolCalls;
			break;
		}
		case "turn_end":
			if (event.message.role === "assistant" && event.message.errorMessage) {
				this._state.errorMessage = event.message.errorMessage;
			}
			break;
		case "agent_end":
			this._state.streamingMessage = undefined;
			break;
	}

	const signal = this.activeRun?.abortController.signal;
	for (const listener of this.listeners) {
		await listener(event, signal);
	}
}

Two things are worth noting. First, a message is formally pushed into the messages array only at message_end — during message_start/message_update it exists solely in streamingMessage, the temporary "being generated" field. This way state.messages always holds "finished messages" while streamingMessage holds "the one in progress", and the UI can render them separately. Second, pendingToolCalls is updated by copying the entire Set and reassigning (new Set(...) then add/delete) rather than mutating in place — so any logic watching pendingToolCalls can detect updates through reference comparison.

After reducing the state, processEvents awaits each listener in subscription order. The listeners are where the product layer (AgentSession) hooks in — it translates AgentEvents into the higher-level AgentSessionEvents. Chapter 9 covers this in detail.

Failure Is Also a Normal Event Sequence

Agent.prompt() wraps each run with runWithLifecycle. If the executor throws unexpectedly (note: normally the loop does not throw, because every collaborator promises "never to throw" — this is the safety net), handleRunFailure converts the error into a normal event sequence:

private async handleRunFailure(error: unknown, aborted: boolean): Promise<void> {
	const failureMessage = {
		role: "assistant",
		content: [{ type: "text", text: "" }],
		api: this._state.model.api,
		provider: this._state.model.provider,
		model: this._state.model.id,
		usage: EMPTY_USAGE,
		stopReason: aborted ? "aborted" : "error",
		errorMessage: error instanceof Error ? error.message : String(error),
		timestamp: Date.now(),
	} satisfies AgentMessage;
	await this.processEvents({ type: "message_start", message: failureMessage });
	await this.processEvents({ type: "message_end", message: failureMessage });
	await this.processEvents({ type: "turn_end", message: failureMessage, toolResults: [] });
	await this.processEvents({ type: "agent_end", messages: [failureMessage] });
}

Even when an unexpected exception occurs, listeners still see a complete, well-formed event sequence (message_start → message_end → turn_end → agent_end), not a half-aborted mess with inconsistent state. This is the last line of defense for the "event stream contract": consumers can always receive agent_end and always reduce their state to a consistent point.

Reentrancy Guard and Two Queues

Agent.prompt() begins with a reentrancy guard:

async prompt(input, images?) {
	if (this.activeRun) {
		throw new Error(
			"Agent is already processing a prompt. Use steer() or followUp() to queue messages, or wait for completion.",
		);
	}
	// ...
}

There can only be one active run at a time. Want to inject messages during a run? Use steer() or followUp() — they place messages into two PendingMessageQueues:

class PendingMessageQueue {
	private messages: AgentMessage[] = [];
	public mode: QueueMode; // "all" | "one-at-a-time"

	drain(): AgentMessage[] {
		if (this.mode === "all") {
			const drained = this.messages.slice();
			this.messages = [];
			return drained;
		}
		const first = this.messages[0];
		if (!first) return [];
		this.messages = this.messages.slice(1);
		return [first];
	}
}

QueueMode controls what drain() does: "all" drains every queued message in one go, "one-at-a-time" takes exactly one per call (the default). Recall from Chapter 3: createLoopConfig wires steeringQueue.drain to getSteeringMessages and followUpQueue.drain to getFollowUpMessages. So the two experiences — "the user interjecting while the agent works" and "queuing the next task" — are implemented through these two queues plus two callback slots. one-at-a-time mode gives each interjection its own independent turn instead of piling them together.

Layer Two: Messages and the Bridge

The Extensible Message Union

The message type flowing through the loop is AgentMessage (packages/agent/src/types.ts), a union type that can be extended via declaration merging:

export interface CustomAgentMessages {} // 通过声明合并扩展
export type AgentMessage = Message | CustomAgentMessages[keyof CustomAgentMessages];

Message (from pi-ai) covers the standard user | assistant | toolResult. But a product can stuff its own message types into the CustomAgentMessages interface — the Harness layer extends it with types such as bashExecution, custom, branchSummary, and compactionSummary. These custom messages matter for the UI and for persistence (say, showing a compaction summary in the terminal), but the model neither needs nor understands them.

convertToLlm: Internal Representation ≠ Wire Representation

This brings us to the bridge mentioned in Chapter 3. The default converter does exactly one thing — filtering:

function defaultConvertToLlm(messages: AgentMessage[]): Message[] {
	return messages.filter(
		(message) => message.role === "user" || message.role === "assistant" || message.role === "toolResult",
	);
}

It filters out every custom message (whose role is not one of those three), keeping only what the provider understands. The product layer uses a convertToLlmWithBlockImages variant (in packages/coding-agent/src/core/messages.ts) that additionally handles image blocking.

The elegance of this design: the transcript may hold any kind of message, but what is sent to the model is always a clean subset. UI messages, compaction summaries, branch summaries, bash execution records — they all live in the transcript, get persisted, get rendered, but are filtered or converted away by the convertToLlm bridge before every model call. Separating the internal representation from the wire representation lets Pi Agent extend message types freely without polluting the provider protocol. The AgentLoopConfig docs even give an example: converting custom messages into user messages and filtering out notification messages.

convertToLlm also carries a "must not throw" contract — it must return a safe fallback, because throwing would "interrupt the underlying loop without producing a normal event sequence". Once again, contract discipline guards the loop's simplicity.

Layer Three: The Session Tree

Now for the centerpiece of this chapter. In-memory state handles "this one run", but the agent also needs memory that spans runs — session persistence. Most agents store the transcript as a flat array of messages. Pi Agent does not. It models the transcript as an appendable, forkable tree of immutable entries.

Why Not an Array

Consider a few real needs:

  • The user wants to "go back three steps and ask again from a different angle" — an array cannot do this short of copying the whole array.
  • The user wants to "fork this session so two branches explore independently" — an array requires a full copy.
  • The context is too long and needs compaction, but "compaction" should not actually delete history (the user may want to look back) — in an array, deletion is deletion.

The tree structure makes all of these natural: history is a set of immutable nodes, and the "current position" is just a pointer to some node (the leaf). Going back = moving the pointer; forking = growing a new branch from some node; compacting = inserting a summary node rather than deleting old ones.

Entries: The Nodes of the Tree

The nodes of the session tree are SessionTreeEntry (packages/agent/src/harness/types.ts), a union of 11 types:

export type SessionTreeEntry =
	| MessageEntry            // 一条消息（user/assistant/toolResult/自定义）
	| ThinkingLevelChangeEntry // thinking 级别变更
	| ModelChangeEntry         // 模型变更
	| ActiveToolsChangeEntry   // 激活工具集变更
	| CompactionEntry          // 压缩摘要
	| BranchSummaryEntry       // 分支摘要
	| CustomEntry              // 自定义条目
	| CustomMessageEntry       // 自定义消息条目
	| LabelEntry               // 标签
	| SessionInfoEntry         // 会话信息（如名称）
	| LeafEntry;               // 叶指针：记录当前活跃叶

Every entry has an id, a parentId (the edge of the tree), a timestamp, and a type. Note that this stores more than messages — model switches, thinking-level changes, and tool-set changes are all entries. That means the "complete history of a session" includes configuration changes, not just conversation content. Looking back at a session, you can see things like "the user switched to a stronger model at turn 5".

LeafEntry is special: it carries no content — it is just a navigation marker recording "which entry is the currently active leaf". The session's "current position" is wherever the leaf points.

Branching: Moving the Leaf

The Session class (packages/agent/src/harness/session/session.ts) wraps operations on the storage. appendMessage appends a message entry (returning the new entry's id); moveTo(entryId, summary?) repoints the leaf:

async moveTo(entryId, summary?): Promise<...> {
	// 把 leaf 重新指向 entryId，实现分支/回溯
}

moveTo deletes nothing — it simply moves the leaf pointer to another entry. If that entry is a node on some old branch, subsequent appendMessage calls grow a new branch from there. That is how "go back three steps and try a different angle" works: moveTo the node from three steps ago, then keep appending. The old branch still lives in the tree, ready to be moveTo'd back to at any time.

getBranch(fromId?) returns the path from the leaf (or a given node) to the root — that is, every entry on "the current branch":

From Tree to Context: buildSessionContext

The model does not need a tree — it needs a linear sequence of messages. buildSessionContext folds "the path of the current branch" into a SessionContext:

export interface SessionContext {
	messages: AgentMessage[];
	thinkingLevel: string;
	model: { provider: string; modelId: string } | null;
	activeToolNames: string[] | null;
}

The folding does two things: first, it derives the current model, thinking level, and active tools from the ModelChangeEntry/ThinkingLevelChangeEntry/ActiveToolsChangeEntry entries in the path (configuration "accumulates along the path"); second, it projects MessageEntrys and friends into an AgentMessage[].

Compaction Takes Effect at Context-Build Time

The most crucial part is how compaction is handled. Recall from Chapter 1: Pi Agent's compaction does not delete history. So how does compaction reduce the tokens sent to the model? The answer is in defaultContextEntryTransform (packages/agent/src/harness/session/session.ts):

export function defaultContextEntryTransform(pathEntries: readonly SessionTreeEntry[]): SessionTreeEntry[] {
	// 找到路径里最后一个 compaction 条目
	let compaction: CompactionEntry | null = null;
	for (const entry of pathEntries) {
		if (entry.type === "compaction") compaction = entry;
	}
	if (!compaction) return [...pathEntries]; // 没有压缩，原样返回

	// 有压缩：上下文 = [压缩摘要] + 保留的尾部
	const entries: SessionTreeEntry[] = [compaction];
	const compactionIdx = pathEntries.findIndex((e) => e.type === "compaction" && e.id === compaction.id);
	if (compaction.retainedTail) {
		for (let i = compactionIdx + 1; i < pathEntries.length; i++) entries.push(pathEntries[i]!);
		return entries;
	}
	if (compaction.firstKeptEntryId) {
		// 从 firstKeptEntryId 开始保留压缩点之前的部分
		// ...
	}
	for (let i = compactionIdx + 1; i < pathEntries.length; i++) entries.push(pathEntries[i]!);
	return entries;
}

The logic: if a compaction entry exists in the path, the context sent to the model becomes "compaction summary + the retained tail after the compaction point". The raw history before the compaction point is not deleted — it is still in the tree — it is simply replaced by the summary when the context is built.

This is an elegant separation: the storage layer keeps the full history, and the context-building layer decides what goes to the model. Compaction is a property of the "context view", not of "storage". So a user can moveTo back before the compaction point and re-expand that history — compaction is a reversible view transformation, not irreversible data deletion. Chapter 7 details how compaction summaries are generated.

The Storage Interface: SessionStorage

Persistence of the session tree is abstracted behind the SessionStorage interface (packages/agent/src/harness/types.ts):

export interface SessionStorage<TMetadata extends SessionMetadata = SessionMetadata> {
	getMetadata(): Promise<TMetadata>;
	getLeafId(): Promise<string | null>;
	setLeafId(leafId: string | null): Promise<LeafEntry>;
	createEntryId(): Promise<string>;
	appendEntry(entry: SessionTreeEntry): Promise<void>;
	getEntry(id: string): Promise<SessionTreeEntry | undefined>;
	findEntries<TType extends SessionTreeEntry["type"]>(type: TType): Promise<Array<Extract<SessionTreeEntry, { type: TType }>>>;
	getLabel(id: string): Promise<string | undefined>;
	getSessionName(): Promise<string | undefined>;
	getSessionStats(): Promise<SessionStats>;
	getPathToRootOrCompaction(leafId: string | null): Promise<SessionTreeEntry[]>;
	getEntries(options?: SessionEntryCursorOptions): Promise<SessionTreeEntry[]>;
}

The core operations are appendEntry (append an immutable entry), setLeafId (move the leaf, i.e., branch), and getPathToRootOrCompaction (get the current branch path, stopping at the compaction point or the root). This interface is the key to pluggable storage backends — the core defines "what operations the session tree needs", and how they are actually stored is the backend's business.

Layer Four: Storage Backends

SessionStorage has three implementations, showing a progression "from simple to powerful".

JSONL: The Default Lightweight Backend

The default backend is JSONL (one JSON object per line). The Harness layer of pi-agent-core provides JsonlSessionStorage (packages/agent/src/harness/session/jsonl-storage.ts), and the product layer pi-coding-agent has its own SessionManager (packages/coding-agent/src/core/session-manager.ts) built on JSONL:

export class SessionManager {
	static create(cwd, sessionDir?, options?);
	static forkFrom(sourcePath, cwd, sessionDir?, options?);
	appendMessage(message): string;
	appendModelChange(provider, modelId);
	appendThinkingLevelChange(level);
	getBranch(fromId?): SessionEntry[];
	buildSessionContext(): SessionContext;
	// ...
}

A session is a JSONL file: one SessionHeader plus a series of typed entries. Appending is appending a line — simple, append-only, human-readable, easy to back up and version-control. Forking a session (forkFrom) means copying the file and setting parentSessionPath. For a single-user local CLI, JSONL is exactly the right choice — no database dependency, no migration burden.

SQLite: The Optional Power Backend

When sessions multiply and full-text search and fast opening are needed, JSONL's "replay the whole file on every open" becomes a bottleneck. pi-storage-sqlite-node (packages/storage/sqlite-node) offers a SQLite backend, SqliteSessionStorage, implementing the same SessionStorage interface.

Its database schema (packages/storage/sqlite-node/src/sqlite/migrations/001_initial.sql) stores the session tree as relational tables:

  • sessions: session metadata + active_leaf_id
  • session_entries: primary key (session_id, id), with entry_seq (monotonically increasing), parent_id (the tree edge), type, payload (JSON)
  • branch_entries: materialized branch membership
  • session_materialized / entry_materialized: precomputed aggregate state

Two optimizations are worth noting. First, materialized aggregates: SessionMaterializedState caches messageCount, token counts, total cost, the current model, and so on. Each appendEntry updates these aggregates incrementally (applyEntryToMaterializedState), so opening a session does not require replaying every entry — just read the materialized state. Second, FTS5 full-text search: createSqliteSessionSearch builds a search index with SQLite's FTS5 (trigram tokenizer), and search() runs a MATCH query ranked by bm25(). This makes "search for that auth bug across all my sessions" possible.

The key point: the SQLite backend and the JSONL backend implement the same interface. The core code (the Session class, buildSessionContext) has no idea whether the backing store is a file or a database. That is the value of interface abstraction — storage backends are genuinely pluggable.

InMemory: Testing and Throwaway Use

There is also InMemorySessionStorage (packages/agent/src/harness/session/memory-storage.ts), which keeps entries in memory. It serves testing (evals use SettingsManager.inMemory() and throwaway sessions) and temporary scenarios that need no persistence.

Walkthrough: The Lifecycle of a Session

Let's tie the layers together. You run pi, type a few prompts, switch models midway, and then fork the session.

  1. Startup: SessionManager.create(cwd) creates a JSONL file and writes a SessionHeader. The leaf is empty.
  2. First message: appendMessage(userMessage) appends a MessageEntry (its parentId points at the root), and the leaf moves to it.
  3. Assistant reply + tools: the assistant and toolResult messages produced by the loop are appendMessage'd one after another, each entry's parentId pointing at the previous one, forming a chain.
  4. Model switch: you switch to a stronger model with /model. appendModelChange(provider, modelId) appends a ModelChangeEntry. From then on, buildSessionContext derives "the current model has changed" from it.
  5. Compaction: the context is nearly full. The compaction logic generates a summary, and appendCompaction(...) appends a CompactionEntry. History is not deleted — but from now on, defaultContextEntryTransform replaces everything before the compaction point with "summary + tail".
  6. Fork: you want a different angle. moveTo(the entryId from three steps ago) moves the leaf back (appending a LeafEntry to record the new position), then appendMessage(new user message) grows a new branch from there. The old branch is intact, and the /tree command shows the whole tree.

Throughout, the in-memory Agent.state.messages holds "the linear transcript of the current run", while the persistent session tree holds "the complete, forkable history". The two are projected into each other via buildSessionContext (tree → linear context) and appendMessage (linear messages → tree entries).

Practical Takeaways

Pi Agent's state design offers four transferable patterns for "how to manage an agent's state and history".

Separate in-memory state from persistent state. In-memory state (the current transcript, runtime flags) uses mutable objects with accessor properties, favoring lightweight reads/writes and defensive copying; persistent state (session history) uses an immutable entry tree, favoring forkability and compaction. The problem it solves: one mechanism serving two access patterns ends up uncomfortable for both. Two layers of state correspond to two lifecycles and two needs.

Reduce events rather than mutating state directly. The loop emits events, Agent reduces them into state, and listeners consume the events. The problem it solves: state mutations scattered everywhere and UI coupled to logic. When every state change flows through the same event stream, you get "any consumer can rebuild the state" for free — TUI, print, and RPC are all different projections of the same reduction.

Internal representation ≠ wire representation; connect them with a bridge. The transcript may hold arbitrary custom message types, but what goes to the model is always the clean filtered/converted subset. The problem it solves: stuffing things into messages for the UI or persistence ends up polluting the provider protocol. When convertToLlm is the only exit, the internals can extend freely without affecting the outside.

Model history as an immutable tree and the "current position" as a pointer. Going back = moving the pointer, forking = growing a new branch, compacting = inserting a summary node instead of deleting. The problem it solves: under a flat array, "going back", "branch exploration", and "reversible compaction" all require full copies or irreversible deletion. When history is immutable and the position is a pointer, these operations all degrade into pointer operations. The cost is somewhat more complex storage and context building — but for an interactive agent where users constantly experiment, backtrack, and fork, that cost is well worth it.

Summary

Pi Agent's state is organized in four layers. In memory, Agent holds the current transcript in accessor properties with defensive copying, reduces AgentEvents into state via processEvents, and even converts failures into normal event sequences. At the message layer, the extensible AgentMessage union lets the transcript hold arbitrary custom types, and convertToLlm filters out a clean subset at the model boundary. At the persistence layer, a session is modeled as an appendable, forkable tree of 11 kinds of immutable entries, the leaf pointer marks the current position, and compaction takes effect at context-build time instead of deleting history. At the storage layer, the SessionStorage interface makes three backends — JSONL, SQLite, and InMemory — pluggable.

The deepest insight is the tree structure. It is not "another way to store messages" but a redefinition of "what a session is": a session is not a line but a tree of exploration, where the user can fork, go back, and compact at any node. Understand that, and you understand why Pi Agent supports fork, /tree, and reversible compaction so gracefully — features that are extremely awkward in the flat-array model.
