Chapter 11: Three Operating Modes

Three projections of the same Agent implementation — interactive TUI, headless print, and RPC — each consuming the same AgentSessionEvent stream

One Stream, Three Presentations

In Chapter 8 we saw resolveAppMode split the pi command into three modes: interactive TUI, headless print, and RPC. In Chapter 9 we saw that all three modes share the same AgentSession, subscribing to the same AgentSessionEvent stream.

This chapter is about where that fork leads: how each mode consumes the event stream. Their core logic is nearly identical — "subscribe to events, drive prompt(), handle results" — but the presentation differs completely: one renders a colored terminal UI for humans, one emits plain text or JSON for scripts, and one serializes to JSON-RPC for IDEs and daemons.

This is the payoff of the "event stream as contract" design. Because AgentSession expresses all progress as events, adding a new "way of consuming" requires touching no Agent logic at all — just writing a new event subscriber. Pi Agent's three modes are three instantiations of this principle.

The Shared Foundation

All three modes start from the same point: AgentSessionRuntime (the runtime host from Chapter 8). It holds an AgentSession and supports rebuilding (reload, switching sessions). A mode obtains the runtime, takes the AgentSession out of it, and then:

  1. Subscribes via session.subscribe(listener) — the listener receives AgentSessionEvents
  2. Drives session.prompt(text) (or steer/followUp)
  3. Handles events in the listener — this is the only point where the three modes diverge

Let's look at each one.

Interactive Mode: InteractiveMode

Interactive mode is the full TUI REPL for humans, implemented in packages/coding-agent/src/modes/interactive/interactive-mode.ts (roughly 6,100 lines — the largest file in the product layer):

export function createInteractiveTui(options: InteractiveTuiOptions): TUI { ... } // :339

export class InteractiveMode {
	constructor(runtimeHost: AgentSessionRuntime, options: InteractiveModeOptions = {})
	async init(): Promise<void>;
	async run(): Promise<void>;          // :886 REPL 主循环
	renderInitialMessages(): void;
	async getUserInput(): Promise<string>; // :3575
	stop(): void;
	private async handleEvent(event: AgentSessionEvent): Promise<void>; // :2910
	// 大量斜杠命令处理器：handleModelCommand, handleCompactCommand, ...
}

run() is the REPL main loop, roughly shaped like this:

订阅 session 事件 → handleEvent
渲染初始消息（续接的会话）
while (true) {
	const input = await getUserInput()   // 等用户输入
	if (是斜杠命令) 处理命令
	else session.prompt(input)           // 驱动对话
	await session.waitForIdle()          // 等这一轮结束
}

The key is handleEvent (:2910) — it translates each AgentSessionEvent into TUI components. This is the core work of interactive mode:

  • message_start/message_update (assistant message) → incrementally render assistant text (Markdown highlighting)
  • tool_execution_start/update/end → render tool calls (using the Chapter 4 tools' renderCall/renderResult, e.g. edit's colored diff)
  • compaction_start/end → show compaction progress
  • auto_retry_start → show "retrying"
  • queue_update → show queued messages
  • thinking_level_changed/model change → update the footer

createInteractiveTui builds the underlying pi-tui TUI (Chapter 12), and InteractiveMode adds roughly 45 components to it (src/modes/interactive/components/): assistant-message, tool-execution, bash-execution, diff, footer, model-selector, session-selector, trust-selector, compaction-summary-message, and more.

Slash commands are handled here. Once getUserInput has the input, if it is a command like /model, /compact, or /export, the corresponding handleXxxCommand is invoked; otherwise the input goes to session.prompt() (the funnel from Chapter 9 further handles extension commands, skills, and templates).

Interactive mode also manages a host of interaction details: Ctrl+P to cycle models (session.cycleModel), Ctrl+C to abort (session.abort()), image pasting, external editor (external-editor.ts), model search (model-search.ts), themes (theme/). All of these exist only because the mode is "for humans" — they make up most of the product's code, yet not a single line touches the core Agent logic.

Print Mode: runPrintMode

Print mode is headless, for scripts and pipes. Implemented in packages/coding-agent/src/modes/print-mode.ts:

export interface PrintModeOptions {
	/** Output mode: "text" for final response only, "json" for all events */
	mode: "text" | "json";
	messages: string[];
	initialMessage?;
	initialImages?;
}
export async function runPrintMode(runtimeHost: AgentSessionRuntime, options: PrintModeOptions): Promise<number>

It returns an exit code (Promise<number>) — this is for the shell; pi -p "..." && echo success depends on it.

Two output modes:

  • text: runs the conversation and outputs only the final assistant text (via session.getLastAssistantText()). This is the default behavior of pi -p "fix the bug" — a clean result, well suited to command substitution like $(pi -p "...").
  • json: streams all AgentSessionEvents out as JSON lines (JSON Lines). This is the behavior of --mode json — one JSON line per event, letting machines parse the entire conversation in real time.

json mode is especially useful: it serializes the event stream that interactive mode "renders to the screen" into structured data, verbatim. External programs can track tool calls, token usage, and compaction events in real time, without parsing terminal ANSI sequences.

Print mode's event consumption is far simpler than interactive's — it subscribes to events, cares only about the final assistant message in text mode, and writes each event to stdout after JSON.stringify in json mode. No TUI, no components, no keybindings. It demonstrates another benefit of the event stream: a consumer can care only about the events it needs and ignore the rest.

RPC Mode: runRpcMode

RPC mode is for machines — IDE integration, daemons (Chapter 15's pi-server spawns a pi --mode rpc child process). Implemented in packages/coding-agent/src/modes/rpc/rpc-mode.ts:

export async function runRpcMode(runtimeHost: AgentSessionRuntime): Promise<never>

Note the return type Promise<never> — it never returns. RPC mode enters an infinite loop, reading commands from stdin and writing responses and events to stdout, until the peer closes the connection.

The protocol is JSON Lines over stdin/stdout:

const handleCommand = async (command: RpcCommand): Promise<RpcResponse | undefined> => { ... }; // :385
// 读循环：
parsed = JSON.parse(line);   // :750 每行一个 JSON 命令
const command = parsed as RpcCommand;

RpcCommand (packages/coding-agent/src/modes/rpc/rpc-types.ts) is the command vocabulary:

prompt, steer, follow_up, abort,
new_session, get_state, set_model, cycle_model, set_thinking_level,
compact, bash, switch_session, fork, clone, get_tree, get_messages, set_session_name, ...

Each command maps to a method on AgentSession. handleCommand is a large dispatcher: a prompt command calls session.prompt(), set_model calls session.setModel(), compact calls session.compact(). Responses (RpcResponse) and events (AgentSessionEvent) are both written back to stdout as JSON lines.

RPC mode also has an extension_ui_request/extension_ui_response mechanism — an extension may need to pop up a picker or an input box inside the IDE (Chapter 14). These UI requests go over RPC to the peer (the IDE), which renders them and sends the user's selection back. This way, extension UI can cross process boundaries too.

RPC mode is the ultimate expression of "event stream as contract": it exposes the entire AgentSession's capabilities as a set of JSON commands, letting any program that can spawn a process and read/write stdin/stdout drive a full pi Agent. That is exactly what Chapter 15's daemon does.

The three modes differ enormously in code size — interactive is 6,100 lines, print a few hundred, RPC a bit over a thousand. Yet their core logic (subscribing to events, driving prompt) is nearly identical. All of the size difference comes from "how to present": interactive renders a rich UI and handles keyboard interaction; print just writes text; RPC just serializes JSON.

This distribution is itself a sign of architectural health: complexity is concentrated in "interacting with humans", not "interacting with the Agent". Because Agent interaction is fully encapsulated by AgentSession and the event stream, each mode only has to handle its own presentation layer.

Why This Matters

Let's step back and look at the value of this design.

Suppose Pi Agent had tangled UI logic with Agent logic from the start — like many agents do, calling the model directly and printing output directly inside the REPL loop. Then:

  • Want a headless mode? You'd have to strip the UI code out of the REPL.
  • Want IDE integration? You'd have to rewrite a driver loop without the UI.
  • Want a daemon? You'd have to rewrite it all over again.

Each time you'd reimplement the logic of "calling the model, executing tools, managing state", and each copy could drift into subtly different behavior from the main loop.

Pi Agent's approach avoids all of this. AgentSession is the single home of Agent logic; it expresses progress as AgentSessionEvents; modes are merely consumers of events. So:

  • Adding a headless mode = writing a subscriber that only outputs text (runPrintMode)
  • Adding IDE integration = writing a subscriber that serializes events to JSON-RPC (runRpcMode)
  • Adding a daemon = spawning an RPC child process (Chapter 15)

The three modes are not "three Agent implementations" but "three projections of a single Agent implementation". This is the final fulfillment, at the product layer, of Chapter 3's "the loop emits events, upper layers reduce" architecture.

Practical Takeaways

Pi Agent's three modes offer four transferable patterns for "how to let one system serve multiple ways of use".

Event stream as contract, modes as projections. Express all progress of the system as one event stream; every way of use is just a consumer/projection of that stream. The problem it solves: each new way of use would otherwise force rewriting the core logic, letting multiple implementations drift apart. When the core only emits events, adding a mode is just adding a subscriber, and the core logic always exists in a single copy.

Let consumers care only about the events they need. Print's text mode takes only the final assistant text and ignores intermediate events; interactive renders every event. The problem it solves: consumers being forced to handle events they don't care about. When the event stream is fine-grained, each consumer takes what it needs.

Express lifecycle semantics in the return type. Print returns Promise<number> (an exit code), RPC returns Promise<never> (never exits). The problem it solves: callers not knowing a mode's lifecycle. When the return type itself says "I will exit and give you an exit code" or "I never return", misuse becomes much harder.

Concentrate complexity where it is genuinely complex. All of the size difference among the three modes comes from "interacting with humans" (UI), not "interacting with the Agent". The problem it solves: core logic getting drowned in UI complexity, becoming hard to test and reuse. When Agent interaction is fully encapsulated, complexity stays only where it belongs — the presentation layer.

Summary

Pi Agent's three operating modes — interactive TUI, headless print, RPC — share the same AgentSession and the same AgentSessionEvent stream, differing only in how they consume it. Interactive mode (6,100 lines) renders events into roughly 45 TUI components for humans; print mode outputs events as plain text or JSON lines for scripts and returns an exit code; RPC mode exposes AgentSession's capabilities as a JSON command vocabulary, serializes events for IDEs and daemons, and never returns.

Their core logic is nearly identical; all the size difference comes from the presentation layer. This is the final fulfillment of the "event stream as contract" design: the three modes are not three Agent implementations but three projections of one. Adding a new way of use only requires adding a new event subscriber.
