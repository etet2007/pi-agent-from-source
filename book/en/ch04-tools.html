Chapter 4: The Tool System: From Definition to Execution

Self-describing tool objects, a prepare / execute / finalize pipeline, and a concurrency philosophy of serial pre-checks, parallel execution, and per-path mutexes

Tools Are the Agent's Hands

A model by itself can do exactly one thing: generate text. It cannot read files, run commands, or modify code. What lets a model actually "do things" is tools — the agent's hands. Chapter 3's loop glossed over executeToolCalls in passing; this chapter takes it apart completely.

Pi Agent's tool system rests on two design decisions worth pondering. First, tools are self-describing objects: concurrency mode, parameter schema, and UI rendering all live inside the tool definition, and the loop knows nothing about a tool's internals. Second, tools have two faces: the AgentTool the core runtime knows is minimal, while the ToolDefinition used by the product layer is rich (adding prompt metadata and TUI renderers), with only a thin wrapper function between them.

Both decisions serve one goal: adding a tool should require no changes to the loop, to system prompt assembly, or to UI rendering. The tool states everything it needs; the system simply takes it at face value.

Two Faces: AgentTool and ToolDefinition

The Core Knows AgentTool

The core runtime (pi-agent-core) knows only a minimal interface (packages/agent/src/types.ts):

export interface AgentTool<TParameters extends TSchema = TSchema, TDetails = any>
	extends Tool<TParameters> {
	label: string;
	prepareArguments?: (args: unknown) => Static<TParameters>;
	execute: (
		toolCallId: string,
		params: Static<TParameters>,
		signal?: AbortSignal,
		onUpdate?: AgentToolUpdateCallback<TDetails>,
	) => Promise<AgentToolResult<TDetails>>;
	executionMode?: ToolExecutionMode; // "sequential" | "parallel"
}

It extends Tool<TParameters> from pi-ai (which brings name, description, the parameters schema, and constrainedSampling), adding four more things:

  • label: the label shown in the UI
  • prepareArguments: optional argument preprocessing before execution
  • execute: the actual execution logic, receiving the tool call id, parameters, abort signal, and progress callback
  • executionMode: declares whether the tool must run sequentially or may run in parallel

Note that execute returns an AgentToolResult<T> (packages/agent/src/types.ts) carrying content (the content fed back to the model), details (structured details for the UI), optional usage and addedToolNames, plus a terminate flag — the last one tells the loop "you may stop once this tool finishes".

The core deliberately does not know how a tool should be rendered or what it should add to the system prompt. Those are product concerns.

The Product Layer Uses ToolDefinition

The product layer (pi-coding-agent) needs a richer interface, because the product also cares about "how this tool appears in the prompt" and "how it renders on the terminal". ToolDefinition (packages/coding-agent/src/core/extensions/types.ts) adds these on top of AgentTool:

export interface ToolDefinition<TParams extends TSchema = TSchema, TDetails = unknown, TState = any> {
	name: string;          // LLM 工具调用用的名字
	label: string;         // UI 标签
	description: string;   // 给 LLM 的描述
	promptSnippet?: string;    // "Available tools" 提示词段落里的一行简介
	promptGuidelines?: string[]; // 工具激活时追加的指南要点
	parameters: TParams;       // TypeBox schema
	constrainedSampling?: false | ConstrainedSamplingConfig;
	renderShell?: "default" | "self";
	prepareArguments?: (args: unknown) => Static<TParams>;
	executionMode?: ToolExecutionMode;
	execute(toolCallId, params, signal, onUpdate, ctx: ExtensionContext): Promise<AgentToolResult<TDetails>>;
	renderCall?(args, theme, context): Component;    // TUI：如何渲染这次调用
	renderResult?(result, options, theme, context): Component; // TUI：如何渲染结果
}

The extra fields fall into two categories:

  • Prompt metadata (promptSnippet, promptGuidelines): as Chapter 10 will show, the "Available tools" section of the system prompt is assembled from the promptSnippet of each active tool, and the "Guidelines" section collects their promptGuidelines. When a tool is enabled, its prompt snippet appears automatically; when it is disabled, the snippet disappears.
  • TUI renderers (renderCall, renderResult): they return a pi-tui Component. As Chapter 12 will show, what a tool call looks like in the terminal (for example, the edit tool's colored diff) is entirely up to the tool itself.

The Bridge: wrapToolDefinition

Only a thin function sits between the two faces (packages/coding-agent/src/core/tools/tool-definition-wrapper.ts):

export function wrapToolDefinition<TDetails = unknown>(
	definition: ToolDefinition<any, TDetails>,
	ctxFactory?: () => ExtensionContext,
): AgentTool<any, TDetails> {
	return {
		name: definition.name,
		label: definition.label,
		description: definition.description,
		parameters: definition.parameters,
		constrainedSampling: definition.constrainedSampling,
		prepareArguments: definition.prepareArguments,
		executionMode: definition.executionMode,
		execute: (toolCallId, params, signal, onUpdate, ctx?: ExtensionContext) =>
			definition.execute(toolCallId, params, signal, onUpdate, ctx ?? (ctxFactory?.() as ExtensionContext)),
	};
}

It projects the rich ToolDefinition onto a minimal AgentTool — dropping promptSnippet, promptGuidelines, renderCall, and renderResult, keeping only the fields the core needs. There is also a reverse createToolDefinitionFromAgentTool: when a caller supplies a bare AgentTool (without prompt metadata or renderers), it synthesizes a minimal ToolDefinition, keeping the product-layer registry "definition-first".

This "rich interface + minimal interface + thin wrapper" pattern is a microcosm of Pi Agent's layering philosophy: the core takes only what it needs, the product keeps what it has extra, and neither contaminates the other. The extension system (Chapter 14) also registers custom tools as ToolDefinitions — so custom tools naturally gain prompt integration and UI rendering for free.

The Execution Pipeline: prepare / execute / finalize

Now we step inside the loop. Chapter 3's executeToolCalls starts with a dispatch decision:

async function executeToolCalls(currentContext, assistantMessage, config, signal, emit) {
	const toolCalls = assistantMessage.content.filter((c) => c.type === "toolCall");
	const hasSequentialToolCall = toolCalls.some(
		(tc) => currentContext.tools?.find((t) => t.name === tc.name)?.executionMode === "sequential",
	);
	if (config.toolExecution === "sequential" || hasSequentialToolCall) {
		return executeToolCallsSequential(currentContext, assistantMessage, toolCalls, config, signal, emit);
	}
	return executeToolCallsParallel(currentContext, assistantMessage, toolCalls, config, signal, emit);
}

The rule is simple: if any tool in the batch declares executionMode: "sequential", or the global config is sequential, the whole batch runs serially; otherwise it runs in parallel. Note this is a "one bad apple spoils the barrel" strategy — a single sequential tool makes every tool in the batch sequential. This is conservative and correct: sequential tools often have ordering requirements on side effects, and a tool running in parallel with them could trip over them.

Whether serial or parallel, every tool call goes through the same three stages.

Stage One: prepare

prepareToolCall does all the pre-execution preparation, returning either a PreparedToolCall or an immediate failure result:

async function prepareToolCall(currentContext, assistantMessage, toolCall, config, signal) {
	// 1. 找到工具，找不到立即报错
	const tool = currentContext.tools?.find((t) => t.name === toolCall.name);
	if (!tool) {
		return { kind: "immediate", result: createErrorToolResult(`Tool ${toolCall.name} not found`), isError: true };
	}
	try {
		// 2. 参数预处理（可选）
		const preparedToolCall = prepareToolCallArguments(tool, toolCall);
		// 3. 按 schema 校验参数（来自 pi-ai）
		const validatedArgs = validateToolArguments(tool, preparedToolCall);
		// 4. beforeToolCall 钩子，可以 block
		if (config.beforeToolCall) {
			const beforeResult = await config.beforeToolCall({ assistantMessage, toolCall, args: validatedArgs, context: currentContext }, signal);
			if (signal?.aborted) return { kind: "immediate", result: createErrorToolResult("Operation aborted"), isError: true };
			if (beforeResult?.block) {
				return { kind: "immediate", result: createErrorToolResult(beforeResult.reason || "Tool execution was blocked"), isError: true };
			}
		}
		if (signal?.aborted) return { kind: "immediate", result: createErrorToolResult("Operation aborted"), isError: true };
		return { kind: "prepared", toolCall, tool, args: validatedArgs };
	} catch (error) {
		return { kind: "immediate", result: createErrorToolResult(error instanceof Error ? error.message : String(error)), isError: true };
	}
}

Four steps: look up the tool, preprocess with prepareArguments, validate against the TypeBox schema with validateToolArguments, and run the beforeToolCall hook. beforeToolCall is the interception point for the product layer and extensions — it can return { block: true, reason } to stop execution. Recall Chapter 1: Pi Agent has no per-tool approval dialog, but extensions can implement their own interception logic through beforeToolCall (or the product layer through the tool_call event). The safety mechanism is extrapolated outward, but the seam is left right here.

Note that every failure returns a result object with kind: "immediate" instead of throwing — once again honoring the "failures are data" contract.

Stage Two: execute

executePreparedToolCall actually invokes the tool, handling progress reporting and exceptions:

async function executePreparedToolCall(prepared, signal, emit) {
	const updateEvents: Promise<void>[] = [];
	let acceptingUpdates = true;
	try {
		const result = await prepared.tool.execute(
			prepared.toolCall.id,
			prepared.args,
			signal,
			(partialResult) => {
				if (!acceptingUpdates) return;
				updateEvents.push(Promise.resolve(emit({
					type: "tool_execution_update",
					toolCallId: prepared.toolCall.id,
					toolName: prepared.toolCall.name,
					args: prepared.toolCall.arguments,
					partialResult,
				})));
			},
		);
		acceptingUpdates = false;
		await Promise.all(updateEvents);
		return { result, isError: false };
	} catch (error) {
		acceptingUpdates = false;
		await Promise.all(updateEvents);
		return { result: createErrorToolResult(error instanceof Error ? error.message : String(error)), isError: true };
	} finally {
		acceptingUpdates = false;
	}
}

The tool reports progress through the fourth parameter, the onUpdate callback, and the loop turns it into tool_execution_update events. The acceptingUpdates flag ensures no late progress updates are accepted after the tool returns. Exceptions thrown by the tool are caught and converted into an error tool result — a failing tool execution does not blow up the loop; it becomes an isError: true result fed back to the model, which decides how to respond (retry? another approach? give up?).

Stage Three: finalize

finalizeExecutedToolCall gives the afterToolCall hook one last chance to modify the result:

async function finalizeExecutedToolCall(currentContext, assistantMessage, prepared, executed, config, signal) {
	let result = executed.result;
	let isError = executed.isError;
	if (config.afterToolCall) {
		try {
			const afterResult = await config.afterToolCall({ assistantMessage, toolCall: prepared.toolCall, args: prepared.args, result, isError, context: currentContext }, signal);
			if (afterResult) {
				result = {
					...result,
					content: afterResult.content ?? result.content,
					details: afterResult.details ?? result.details,
					usage: afterResult.usage ?? result.usage,
					terminate: afterResult.terminate ?? result.terminate,
				};
				isError = afterResult.isError ?? isError;
			}
		} catch (error) {
			result = createErrorToolResult(error instanceof Error ? error.message : String(error));
			isError = true;
		}
	}
	return { toolCall: prepared.toolCall, result, isError };
}

afterToolCall can override content, details, usage, terminate, and isError. This gives the product layer and extensions a "post-hoc review" slot — for example, writing audit logs, modifying the content fed back to the model, or setting terminate to force the loop to stop.

Finally, createToolResultMessage packages the final result into a toolResult message:

function createToolResultMessage(finalized): ToolResultMessage {
	return {
		role: "toolResult",
		toolCallId: finalized.toolCall.id,
		toolName: finalized.toolCall.name,
		content: finalized.result.content ?? [],
		details: finalized.result.details,
		usage: finalized.result.usage,
		...(finalized.result.addedToolNames?.length ? { addedToolNames: finalized.result.addedToolNames } : {}),
		isError: finalized.isError,
		timestamp: Date.now(),
	};
}

The message is appended to the context and becomes input for the next model call. addedToolNames is an intriguing field: a tool can declare "after I run, please add these tools to the available set" — a backdoor for tools to dynamically extend the toolset.

Concurrency: How Parallel Execution Happens Safely

The default is toolExecution: "parallel". Parallel execution has a subtle design point — serial pre-checks, parallel execution:

async function executeToolCallsParallel(currentContext, assistantMessage, toolCalls, config, signal, emit) {
	const finalizedCalls: FinalizedToolCallEntry[] = [];

	for (const toolCall of toolCalls) {
		await emit({ type: "tool_execution_start", toolCallId: toolCall.id, toolName: toolCall.name, args: toolCall.arguments });

		// 预检（prepare）是串行的
		const preparation = await prepareToolCall(currentContext, assistantMessage, toolCall, config, signal);
		if (preparation.kind === "immediate") {
			// 立即结果直接收尾
			const finalized = { toolCall, result: preparation.result, isError: preparation.isError };
			await emitToolExecutionEnd(finalized, emit);
			finalizedCalls.push(finalized);
			continue;
		}

		// 真正的执行被包成一个 thunk，稍后并行跑
		finalizedCalls.push(async () => {
			const executed = await executePreparedToolCall(preparation, signal, emit);
			const finalized = await finalizeExecutedToolCall(currentContext, assistantMessage, preparation, executed, config, signal);
			await emitToolExecutionEnd(finalized, emit);
			return finalized;
		});
	}

	// 所有 thunk 并行执行
	const orderedFinalizedCalls = await Promise.all(
		finalizedCalls.map((entry) => (typeof entry === "function" ? entry() : Promise.resolve(entry))),
	);

	// 结果按助手消息里的原始顺序发出
	const messages: ToolResultMessage[] = [];
	for (const finalized of orderedFinalizedCalls) {
		const toolResultMessage = createToolResultMessage(finalized);
		await emitToolResultMessage(toolResultMessage, emit);
		messages.push(toolResultMessage);
	}
	return { messages, terminate: shouldTerminateToolBatch(orderedFinalizedCalls) };
}

Why "serial pre-checks, parallel execution"? Because the beforeToolCall hook inside prepareToolCall may have side effects (logging, approval prompts, state changes), and letting them happen deterministically in the order the model emitted them is far more predictable than letting them race. The actual execution (reading files, running commands) is what takes time, and parallelism pays off there. Hence:

  • tool_execution_start is emitted in the original order (pre-checks are serial)
  • tool_execution_end is emitted in completion order (whichever finishes first is emitted first, so the UI can update immediately)
  • toolResult messages are appended to the context in original order (keeping the transcript deterministic)

This distinction between "events in completion order, messages in original order" is crucial: the UI wants immediate feedback (show whichever is ready first), but the transcript the model sees must be deterministic (the same input must produce the same message sequence, or caching and replay break down). Pi Agent uses Promise.all to keep execution order and array order in sync, making the message sequence deterministic.

The Terminate Signal

After a batch of tools finishes, shouldTerminateToolBatch decides whether to stop the loop:

function shouldTerminateToolBatch(finalizedCalls: FinalizedToolCallOutcome[]): boolean {
	return finalizedCalls.length > 0 && finalizedCalls.every((finalized) => finalized.result.terminate === true);
}

Only when every final result sets terminate: true does the batch stop the loop. This is an "all votes required" rule: as long as one tool has not said "stop", the loop continues. It prevents a single tool from prematurely cutting off work still in progress.

File Mutex: What If Two Parallel Tools Write the Same File

Parallel execution carries a real danger: what if the model issues two edit calls in the same batch, both modifying the same file? With the two writes interleaving, the file could end up corrupted.

Pi Agent's answer is a per-path mutex queue, withFileMutationQueue (packages/agent/src/harness/tools/file-mutation-queue.ts). At its core is a WeakMap keeping, per ExecutionEnv, a "path → promise chain" table:

const states = new WeakMap<ExecutionEnv, MutationQueueState>();

export async function withFileMutationQueue<T>(env: ExecutionEnv, path: string, fn: () => Promise<T>): Promise<T> {
	const state = getState(env);
	const registration = state.registration.then(async () => {
		const key = await getMutationQueueKey(env, path); // 规范化路径作为 key
		const currentQueue = state.queues.get(key) ?? Promise.resolve();

		let releaseNext = () => {};
		const nextQueue = new Promise<void>((resolve) => { releaseNext = resolve; });
		const chainedQueue = currentQueue.then(() => nextQueue);
		state.queues.set(key, chainedQueue);
		return { key, currentQueue, chainedQueue, releaseNext };
	});
	state.registration = registration.then(() => undefined, () => undefined);

	const { key, currentQueue, chainedQueue, releaseNext } = await registration;
	await currentQueue; // 等前面的写操作完成
	try {
		return await fn();
	} finally {
		releaseNext(); // 放行下一个
		if (state.queues.get(key) === chainedQueue) state.queues.delete(key);
	}
}

The mechanism is the classic "promise-chain mutex": every write targeting the same canonical path appends itself to the end of that path's current promise chain, first awaiting currentQueue for its predecessors to finish, then calling releaseNext() to let the next one through. So parallel edit/write calls automatically serialize at the file layer, never interleaving.

Two details are worth noting. First, the key is the canonical path (canonicalPath) — so ./foo/bar.ts and /abs/foo/bar.ts map to the same queue, and mutex protection is not lost just because the path was written differently. Second, using a WeakMap keyed by ExecutionEnv means different execution environments (say, different sandboxes) have their own independent queues, and the queues are cleaned up automatically when the environment is garbage-collected. createEditTool and createWriteTool wrap their execution bodies in this queue; read does not need to (reads do not conflict).

This is a fine example of "solving concurrency at the right layer": the loop layer lets tools run in parallel (the payoff), and the tool layer eliminates write conflicts with per-path mutexes (the safety). Each layer does its own job.

Let's look at one concrete tool definition (read.ts, excerpt):

const readSchema = Type.Object({
	path: Type.String({ description: "Path to the file to read (relative or absolute)" }),
	offset: Type.Optional(Type.Number({ description: "Line number to start reading from (1-indexed)" })),
	limit: Type.Optional(Type.Number({ description: "Maximum number of lines to read" })),
});

export function createReadToolDefinition(cwd, options?): ToolDefinition<typeof readSchema, ReadToolDetails | undefined> {
	return {
		name: "read",
		label: "read",
		description: `Read the contents of a file. Supports text files and images ...`,
		promptSnippet: "Read file contents",
		promptGuidelines: ["Use read to examine files instead of cat or sed."],
		parameters: readSchema,
		async execute(_toolCallId, { path, offset, limit }, signal?, _onUpdate?, ctx?) {
			// 读文件/图片，截断过长内容
		},
		renderCall(args, theme, context) { /* 返回一个 pi-tui Text 组件 */ },
		renderResult(result, options, theme, context) { /* 语法高亮预览 */ },
	};
}

export function createReadTool(cwd, options?): AgentTool<typeof readSchema> {
	return wrapToolDefinition(createReadToolDefinition(cwd, options));
}

This definition states everything about the tool: the parameter schema (readSchema), the description for the model (description), the one-line summary in the prompt (promptSnippet), the guidelines when enabled (promptGuidelines), the execution logic (execute), and the two TUI renderers. createReadTool is just wrapToolDefinition(createReadToolDefinition(...)) — projecting the rich definition onto a minimal AgentTool.

Tools can also have pluggable operations (such as ReadOperations) that let file IO be delegated to a remote system (like SSH). This is a seam left for remote-execution scenarios; Chapter 15 returns to it.

Practical Takeaways

Pi Agent's tool system offers four transferable patterns for "designing an extensible tool/plugin mechanism".

Tools are self-describing; the orchestrator is ignorant. Let each tool declare its own parameter schema, concurrency mode, prompt snippet, and UI rendering; the orchestrator (the loop) only reads these declarations and "knows" no specific tool. The problem it solves: the central orchestrator becomes a god object that must be modified for every added tool. When tools are self-describing, adding tool N+1 requires zero changes to existing code.

Rich interface + minimal interface + thin wrapper. The core only needs a tool's execution capability; the product also needs prompt and rendering metadata — expressed as two interfaces, projected through one thin function. The problem it solves: the core being forced to carry product-layer concerns. When AgentTool does not know renderCall exists, the core can be reused in any UI-less environment (SDK, browser, daemon).

Serial pre-checks, parallel execution. Run the side-effectful pre-checks that need a deterministic order (validation, approval hooks) serially, and parallelize the time-consuming real execution. The problem it solves: either everything serial (slow) or everything parallel (racing pre-checks, nondeterministic transcripts). This split buys both parallel speed and deterministic ordering.

Solve concurrency at the right layer. The loop layer allows tools to run in parallel for speed; the tool layer eliminates write conflicts with per-path promise-chain mutexes. The problem it solves: either crudely serializing everything at the loop layer (sacrificing concurrency) or ignoring conflicts entirely (corrupting files). Only by sinking the mutex down to the layer of the actually shared resource can you have both concurrency and safety.

Summary

Pi Agent's tools are self-describing objects: the core knows the minimal AgentTool, the product uses the rich ToolDefinition, and wrapToolDefinition bridges the two. Every tool call goes through three stages — prepare (look up the tool, preprocess, validate, beforeToolCall), execute (run + progress reporting + exception capture), and finalize (afterToolCall post-hoc modification). For concurrency: serial pre-checks, parallel execution, events emitted in completion order while messages are appended in original order; write conflicts are eliminated by the per-canonical-path promise-chain mutex.

The seven built-in tools (read/bash/edit/write/grep/find/ls) each spell out their parameters, description, prompt snippet, and renderers, with the first four enabled by default. Nowhere in the system is there central code that "knows all the tools" — which is exactly why it scales linearly.
