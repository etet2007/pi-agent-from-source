Chapter 15: Remote Control — Daemon, RPC, and Protocols

Two remote designs in parallel: one daemon already implemented, one protocol awaiting its server

Beyond localhost

So far, everything we have looked at is "one pi process running in one terminal on one machine." But production scenarios often go beyond that: you want multiple agents running in the background for long periods, to drive them from an IDE, and to reach them from another machine.

Pi Agent's remote-control story hinges on one key fact: this codebase contains two fundamentally different remote designs. That is not redundancy but the product of two different stages and two different goals — understanding the difference helps you see how a system handles the "remote" requirement as it evolves.

The first is pi-server: a fully implemented daemon that supervises multiple headless pi --mode rpc child processes and registers them with a remote relay called Radius. It communicates with newline-delimited JSON.

The second is pi-protocol + pi-client: a transport-neutral, binary (length-prefixed CBOR) protocol paired with a runtime-agnostic client SDK. It is well designed — but in this snapshot of the code, nothing serves this protocol. It is a client prepared for a future remote UI, waiting for its server.

This chapter dissects each design in turn, then answers: why are there two?

The first design: the pi-server daemon

pi-server (packages/server)'s package.json honestly labels it "experimental". At its core it is a supervisor: a long-running daemon that manages multiple headless coding-agent child processes.

Command line

The server binary (packages/server/src/cli.ts) offers these subcommands:

server serve              # 启动守护进程，一直运行
server list               # 列出实例
server spawn [--cwd <path>] [--label <label>]  # 启动一个 Agent 实例
server status <id>        # 查询实例状态
server stop <id>          # 停止实例
server rpc <id> <json>    # 向实例发一个 RPC 命令
server rpc-stream <id>    # 打开持久 RPC 流

Except for serve, every command is a thin IPC client — it sends a request to the daemon over a Unix socket and gets one response. All the real logic lives in the daemon.

Supervisor: ServerSupervisor

The core is ServerSupervisor (packages/server/src/supervisor.ts), an exported singleton supervisor:

export class ServerSupervisor {
	private readonly liveInstances = new Map<string, LiveInstance>();

	async spawnInstance(options: { cwd: string; label?: string }): Promise<InstanceRecord> { ... } // :270
	async stopInstance(instanceId: string): Promise<InstanceRecord | undefined> { ... }            // :300
	async recoverAfterRestart(): Promise<void> { ... }                                             // :244
	async shutdown(): Promise<void> { ... }
	listInstances(): InstanceRecord[];
	listLiveInstances(): InstanceRecord[] { ... }                                                  // :240
}

It maintains a liveInstances table; each LiveInstance bundles an InstanceRecord (the persisted record) with live resources (the RPC process, Radius id, session id, event subscribers).

The spawnInstance flow: create a record (status starting) → persist it → create an RpcProcessInstance (spawn the child process) → bind event/exit/UI handlers → sync session metadata → register with Radius → set status to online. On failure it cleans up and sets stopped.

recoverAfterRestart handles daemon restarts: it marks any online/starting instance as stopped (because their child processes died with the previous process) and disconnects them from Radius. This is the familiar "state reconciliation after restart" of distributed systems.

Child processes: RpcProcessInstance

Each instance is a child process wrapped by RpcProcessInstance (packages/server/src/rpc-process.ts). The spawn command is pi --mode rpc (or the equivalent node .../rpc-entry).

Recall Chapter 11: pi --mode rpc enters a JSON-RPC loop that reads commands from stdin and writes responses to stdout. RpcProcessInstance talks to it over the child process's stdin/stdout using JSON Lines:

send(command: RpcCommand): Promise<RpcResponse> {
	// 分配 id，写 JSON.stringify(command) + "\n"，按 id 关联响应
}

Each stdout line is dispatched: type: "response" resolves a pending request, type: "extension_ui_request" invokes the UI handlers, and everything else is broadcast to event listeners as an AgentSessionEvent.

So the chain is: the daemon drives a headless pi over stdio JSONL, reusing the entire RPC pattern from Chapter 11. The RpcCommand/RpcResponse/AgentSessionEvent types all come from @earendil-works/pi-coding-agent — pi-server depends on coding-agent and treats it as a spawnable RPC service.

Local control plane: IPC

Between the daemon and its CLI clients sits another protocol layer — local IPC (packages/server/src/ipc/). It uses newline-delimited JSON over a Unix socket:

// 请求：spawn / list / stop / status / rpc / rpc_stream
// 响应：spawn_result / list_result / stop_result / status_result / rpc_result / rpc_ready / error
encodeMessage(message): string = JSON.stringify(message) + "\n"

startIpcServer listens on the Unix socket. One-shot requests call socket.end() once they get their response; an rpc_stream request upgrades the socket into a persistent bidirectional JSONL stream. removeStaleSocketIfNeeded + isSocketLive detect and refuse to clobber a running daemon ("server is already running").

Note: this IPC layer and the child-process RPC are both JSON Lines, but with different vocabularies — IPC "manages the daemon" (spawn/stop/list), while RPC "drives an agent" (prompt/steer/set_model). Each layer minds its own segment.

Persistence and Radius

The daemon's state lives in ~/.pi/server/ (packages/server/src/storage.ts): machine.json (machine record) and instances.json (instance records). InstanceRecord has id, status, cwd, label?, sessionId?, sessionFile?, radiusPiId?, and InstanceStatus = starting | online | stopping | stopped | error.

Finally there is Radius (packages/server/src/radius.ts) — the remote relay. RadiusPresence registers the machine's agents with a central service at https://radius.pi.dev/ so they can be reached remotely:

// 注册机器（machines/register）和每个 pi 实例（pis/register）
// capabilities: { rpc: true, relay: false, iroh: false }
// 心跳循环：heartbeatMachine / heartbeatPi，指数退避 + 抖动

It registers the machine and each instance, then runs a heartbeat loop (with exponential backoff + jitter), re-registering after three consecutive 404s. The capabilities field has rpc: true but relay: false, iroh: false — a hint that the relay and iroh transports are planned but not yet implemented.

The full architecture

Putting the first design together:

This is one complete chain: CLI/IPC client → (Unix socket JSONL) → daemon supervisor → (stdio JSONL) → headless pi --mode rpc child processes → (HTTPS heartbeat) → Radius remote relay. It reuses the Chapter 11 RPC pattern as the innermost layer and extends outward layer by layer.

The second design: pi-protocol + pi-client

Now for the second design — one with a very different temperament.

pi-protocol: a transport-neutral CBOR protocol

pi-protocol (packages/protocol) describes itself as a "Transport-neutral CBOR protocol for remote pi sessions". It has only one runtime dependency (typebox) and zero Node-specific imports — it defines a pure protocol: schemas, CBOR encoding, and byte-stream framing.

Framing (packages/protocol/src/framing.ts): protocol version 2; each frame is

[4 字节大端无符号长度][一个定长 CBOR 项]
export const DEFAULT_MAX_FRAME_LENGTH = 16 * 1024 * 1024; // 16 MiB
export function encodeFrame(payload: Uint8Array): Uint8Array; // 加长度头
export class FrameDecoder {
	push(chunk: Uint8Array): Uint8Array[]; // 增量切分任意字节块
	end(): void;
}

FrameDecoder.push incrementally splits any byte stream (handling fragmentation and coalescing) into complete payloads. The CBOR is a strict RFC 8949 subset (cbor/): null/booleans, finite safe integers and float64, UTF-8 strings, byte strings, fixed-length arrays, fixed-length maps. Default limits: 16 MiB payload, 1,000,000 elements, 64 nesting levels.

Message vocabulary (packages/protocol/src/schemas.ts). The first frame is always the handshake:

export const ClientHelloSchema = StrictObject({
	type: Type.Literal("hello"),
	version: Type.Integer({ minimum: 0 }),
	token: Type.String({ minLength: 1 }), // bearer token
});

The server answers with hello (carrying connectionId and snapshot) or hello_error. Afterwards the client sends a request envelope wrapping one command. Nine commands:

export const CommandSchema = Type.Union([
	ListCommandSchema,      // list
	CreateCommandSchema,    // create
	AttachCommandSchema,    // attach
	DetachCommandSchema,    // detach
	PromptCommandSchema,    // prompt
	SteerCommandSchema,     // steer
	AbortCommandSchema,     // abort
	SetModelCommandSchema,  // set_model
	SetThinkingCommandSchema, // set_thinking
]);

Server messages come in a response envelope (correlated by id, ok: true + result, or ok: false + error) and an event envelope. Events are one of four kinds:

export const ServerEventSchema = Type.Union([
	// server_snapshot, session_snapshot, session_progress, session_removed
]);

It also defines a full transcript domain model: content parts (text/thinking/image/toolCall), TranscriptItem (user/assistant/tool, each with a status), TranscriptProgress (item_started/assistant_delta/item_updated/item_finished), SessionSummary, SessionSnapshot, ServerSnapshot, ModelMetadata, and a structured ProtocolError.

One detail shows its alignment with the core: SessionPhase = idle | turn | compaction | branch_summary | retry, with a comment stating it "Matches AgentHarnessPhase so adapters do not need a second phase vocabulary" — the protocol's phase vocabulary directly reuses the harness phases from Chapter 6, so adapters don't have to maintain two vocabularies.

Every schema uses StrictObject (additionalProperties: false) — unknown properties are rejected. This is a strict protocol designed for long-term evolution.

pi-client: a runtime-agnostic client

pi-client (packages/client) consumes pi-protocol, and its root package has no Node-specific imports — the Node/Bun Unix-socket transport is quarantined behind the ./unix subpath export. The whole package rests on a minimal transport seam (packages/client/src/transport.ts):

export interface ByteTransport {
	send(chunk: Uint8Array): Promise<void>; // 顺序交付，尊重背压
	close(): void;                          // 幂等
}
export interface ByteTransportHandlers {
	onData(chunk: Uint8Array): void;
	onClose(): void;
	onError(error: Error): void;
}
export type ByteTransportFactory = (handlers: ByteTransportHandlers) => ByteTransport | Promise<ByteTransport>;

ByteTransport has exactly two methods: send and close. Any ordered byte stream will do — WebSocket, Unix socket, or anything else. The factory must produce a fresh transport for every connection attempt. This seam makes the whole client runtime-agnostic: swap the ByteTransportFactory and it runs on any transport.

PiClient (packages/client/src/client.ts) is the public entry point:

connect(): Promise<ServerSnapshot>;
listSessions(): Promise<readonly SessionSummary[]>;
createSession(options?): Promise<PiSessionHandle>;
attachSession(sessionId): Promise<PiSessionHandle>;
subscribe(listener); onEvent(listener); onConnectionStateChange(listener);

It has no auto-reconnect — the caller drives connect/reconnect/disconnect. PiSessionHandle is a stable client-side reference to a session: prompt(text), steer(text), abort(), setModel(model), setThinking(level), detach(), each returning Promise<SessionSnapshot>.

The internal Connection (connection.ts) is a lifecycle state machine (disconnected | connecting | connected): it first sends a client hello, expects the server hello as the first inbound message, resolves the handshake with the ServerSnapshot, then routes subsequent messages to onMessage. It defends against "data before the handshake" and "unexpected handshake messages".

ClientState (state.ts) holds the snapshot cache (ServerSnapshot plus a per-session SessionSnapshot) and the listener registry; applyServerSnapshot carries a revision guard (stale snapshots don't overwrite newer ones). Subscriber exceptions are quarantined and reported via onListenerError so they "cannot affect client state".

Snapshot authority + ephemeral progress

This protocol embodies an important design philosophy the README hammers home: snapshots are authoritative; progress events are ephemeral UI hints.

The session_progress events (with TranscriptProgress: item_started/assistant_delta/item_finished) are streaming incremental hints that let the UI render in real time. But if a client misses a few progress events, or has just connected, it doesn't need to replay anything — session_snapshot provides the complete current state. The client can rebuild everything from a snapshot at any time; progress events are just an optimization to "make it feel fluid".

This contrasts with the event stream of Chapter 3: there, events are the single source of truth; here, snapshots are the truth and events are hints. Each model suits different scenarios — for a remote system that may disconnect and reconnect, with multiple clients attaching, "snapshot authority" is more robust.

An unwired client

Key fact: in this snapshot of the code, nothing serves pi-protocol. pi-server does not import pi-protocol — it uses its own JSON IPC. pi-client is a well-designed client SDK waiting for a server that is not implemented here.

It reads like it was built for a future remote UI (a GUI, a web interface): transport-neutral (it could run on a browser WebSocket), runtime-agnostic, snapshot-authoritative (suited to multiple clients), and a strictly versioned protocol. It is the design draft of a "next-generation" remote solution.

Why two designs

Putting the two side by side:

pi-server (first design)pi-protocol/pi-client (second design)
StatusImplemented, self-containedClient implemented, server unwired
TransportUnix socket + stdioTransport-neutral (any byte stream)
Encodingnewline-delimited JSONLength-prefixed CBOR (binary)
RuntimeNode/BunRuntime-agnostic (browser-capable)
TopologyDaemon supervising child processesClient-server, multi-client attach
Remote accessRadius relay (HTTPS heartbeat)The protocol itself is transport-neutral
Truth modelEvent streamSnapshot authority + ephemeral progress

These two are not duplicated effort but two phases of evolution. pi-server is "what works today" — it solves the concrete need of "run multiple agents in the background + remote access" with simple JSON-over-socket, reusing the existing RPC pattern. pi-protocol/pi-client are "designed for the future" — a more general, stricter, transport-neutral protocol prepared for a remote UI that has not arrived yet.

This reveals a pragmatic engineering attitude: solve today's problems with the simple approach first, while designing a more general interface for the future — without forcing the two to converge. pi-server does not force itself onto the immature CBOR protocol for the sake of "elegance"; pi-protocol does not bend to pi-server's JSON design for the sake of "reuse". The two evolve independently and converge when the time is right — or never.

This is another facet of the minimalism philosophy: remote capability is an optional side branch (in the Chapter 1 dependency graph, server/protocol/client are all downstream of the product layer; the product layer does not depend on them). Installing the pi command needs no remote components at all. Remote is "there if you need it", not "forcibly built into the core".

Practical Takeaways

Pi Agent's two remote designs offer four transferable patterns for "how to add remote capability to a system".

Achieve transport neutrality with a minimal transport seam. ByteTransport has only send/close; any ordered byte stream can be adapted. It solves the problem of a client being locked to one specific transport (WebSocket/Unix socket). When the transport is a two-method interface, the same client runs on any transport — including the browser.

Snapshots authoritative, events ephemeral. Full state is expressed with snapshots (rebuildable at any time); streaming events are just UI hints (losing them does not hurt correctness). It solves the problem that, when remote clients disconnect and reconnect and multiple clients attach, a pure event stream needs replay and drifts easily. When snapshots are the truth, reconnecting is just "grab a snapshot", and robustness improves dramatically.

Reuse an existing pattern as the inner layer, then extend outward. pi-server's innermost layer directly reuses pi --mode rpc from Chapter 11, wrapped in a supervisor, IPC, and Radius. It solves the problem of writing agent-driving logic from scratch for remote. When remote is "wrapping the existing RPC pattern layer by layer", every layer stays simple and the inner behavior is identical to local.

Let two designs coexist while evolving. The current simple approach (JSON IPC) and the future general design (CBOR protocol) evolve independently, without forced unification. It solves the problem of either saddling today's solution with elegance or compromising the future design for reuse. When the two are decoupled, each matures on its own schedule — pragmatism often beats consistency.

Summary

Pi Agent's remote control has two designs. The first, pi-server, is an implemented daemon: ServerSupervisor supervises multiple pi --mode rpc child processes (over stdio JSONL, reusing the Chapter 11 RPC pattern), the CLI manages it over Unix-socket JSON IPC, state is persisted in ~/.pi/server/, and it registers with radius.pi.dev through the Radius relay for remote access. The second, pi-protocol + pi-client, is a transport-neutral, runtime-agnostic CBOR protocol and client: length-prefixed frames, a hello handshake, nine commands, snapshot authority + ephemeral progress, and the two-method ByteTransport seam — but in this snapshot no server serves it; it is a design draft for a future remote UI.

The coexistence of the two is not redundancy but two phases of evolution: a simple present and a general future. And remote capability as a whole is an optional side branch the product core does not depend on at all — once again reflecting the philosophy of "minimal core, optional capabilities pushed to the edge".
