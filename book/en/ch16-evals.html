Chapter 16: Behavioral Evaluation: pi-evals

Turning "is my agent getting better" from a feeling into a number: isolated environments, comparison matrices, model judges, and lift metrics

How Do You Know It Got Better

Across the previous 15 chapters, we looked at how an agent is built. But there is an equally fundamental question: how do you know you improved it?

Testing traditional software is deterministic: give an input, assert on the output. But an agent is not. You change one sentence in the system prompt, switch models, or add a tool: how will its behavior change? Will it get better on some tasks and worse on others? Will it trade more tokens for higher accuracy? Unit tests cannot answer these questions, because agent behavior is emergent and non-deterministic — run the same prompt twice and the paths may differ.

pi-evals (packages/evals) is Pi Agent's answer to this question. Its README states it plainly:

Pi evals are behavioral, model-backed checks for Pi workflows.

Behavioral, model-backed: those are the key words. It doesn't mock the model or pretend determinism; instead it actually runs an agent, judges the output with a model, and then does rigorous comparisons between baseline and candidate. This chapter dissects the evaluation framework and shows how it turns "is my agent getting better" from a feeling into a number.

For an agent whose philosophy is minimalism, this framework matters even more: as you constantly weigh whether a feature belongs in the core, you need an objective referee to tell you whether a given change helps or hurts.

The Core Abstraction: harness

pi-evals builds on the third-party framework vitest-evals and adapts it to pi. The core adapter is createPiCodingAgentHarness (packages/evals/src/pi-harness.ts):

export function createPiCodingAgentHarness<TOutput extends JsonValue>(
	options: PiCodingAgentHarnessWithOutput<TOutput>,
): Harness<PiCodingAgentInput, TOutput>;
export function createPiCodingAgentHarness(options?: PiCodingAgentHarnessOptions): Harness<PiCodingAgentInput, string>;

It returns a Harness, a vitest-evals concept: essentially an evaluable unit that takes input and produces output. The options include:

{
	name: string;
	model: { provider: string; id: string };
	noTools?: ...;
	transformSystemPrompt?: (defaultPrompt: string) => string; // 变换系统提示词
	output?: ({ response, session }) => TOutput;               // 自定义输出提取
}

The input type (PiCodingAgentInput) can be a single prompt, or a sequence of steps:

export type PiCodingAgentInput = string | Array<{ type: "prompt"; content: string } | { type: "reload" }>;

The { type: "reload" } step is useful: it lets an eval "first have the agent create a resource, then reload the resource, then have the agent use it". We'll see this pattern in the extensions eval shortly.

transformSystemPrompt is the key to controlled experiments: it takes the default system prompt and returns a transformed version. You can then build two harnesses, one with the full prompt and one with a section removed, and compare their performance. That is exactly the rigorous way to test "does my prompt change help".

Running a Real Agent

runPiCodingAgent (packages/evals/src/pi-harness.ts:109) is the real workflow. It doesn't reuse any existing session; instead it runs a brand-new AgentSession in a fully isolated environment:

A few design decisions are worth noting.

Full isolation. Each eval runs in a temporary directory created with mkdtemp, with its own workspace/ (the project the agent operates on) and agent/ (config/session). SettingsManager.inMemory() avoids reading or writing real settings. The temporary directory is removed when done. This guarantees evals don't interfere with each other and don't pollute the developer's real environment.

thinkingLevel: "off". Evals turn thinking off by default, to reduce non-determinism, lower cost, and speed up evaluation. It is a choice that evaluation focuses on behavior rather than the reasoning process.

Assert stopReason === "stop". After each prompt step, it asserts the response completed normally (not error/aborted/length). If the agent fails to complete normally, the eval fails; this is a basic sanity check.

Customizable output extraction. The default output is getLastAssistantText() (the last assistant message text). The output option lets you customize this, for example to extract structured data from the session state.

Session snapshot as artifact. When done, the entire session's JSONL is snapshotted as a test artifact (PI_SESSION_SNAPSHOT_ARTIFACT = "piSessionJsonl"). This means every eval run leaves a complete, replayable session record: you can open it to see exactly what the agent did, which tools it called, and how many tokens it spent.

Controlled Experiments: evalHarnessTable

A single harness run only tells you what it did. To answer "is it better than before", you need comparison. evalHarnessTable (packages/evals/src/vitest-evals/harness-table.ts) builds a baseline × candidate comparison matrix:

evalHarnessTable(evalSet, {
	baseline,        // 基准 harness
	candidate | candidates, // 候选 harness（可以有多个）
	repetitions?,    // 每组重复次数
}): EvalHarnessTableRow[]

It expands every harness × input × repetition into a row and runs them with Vitest's describe.for(...). Each run is tagged with an EVAL_HARNESS_ITERATION_ARTIFACT (evalSet, groupKey, harness, baseline, candidates, repetition) so runs can be paired later.

deriveEvalGroupKey(input, repetition) pairs observations by "input id (or SHA-256 of the input JSON) + repetition number", so baseline and candidate are compared on exactly the same input and repetition. canonicalizeJson enforces JSON canonicalization (finite numbers, no cycles, sorted keys), ensuring the same input yields the same key.

repetitions matters: because agent behavior is non-deterministic, a single run could be luck. Repeating multiple times is the only way to distinguish "genuinely better" from "just lucky this time".

Judging: score and judge

Every eval run produces a score. vitest-evals's convention is: score >= 1 counts as passing. A score can come from:

  • Deterministic judging: check whether the output satisfies hard conditions.
  • Model judging: use another LLM to judge output quality (model-backed).

extensions.eval.ts is a good example of deterministic judging. It evaluates whether the agent can correctly author a pi extension, scoring it with a deterministic ExtensionAuthoringJudge (createJudge) that checks:

  • The generated extension imports @earendil-works/pi-coding-agent (not the outdated @mariozechner/ or @sinclair/typebox)
  • The extension loads without errors
  • A hello tool is registered
  • hello({ name: "Bob" }) returns "Hello, Bob!"

This eval's input is a step sequence: create the extension → reload → use the extension. It uses judgeThreshold: null, so a low score counts as an "observation" rather than a "failure". This is a subtle but important design: an exploratory eval (where you're still learning about baseline performance) shouldn't turn the test red just because scores are low; it should serve as data collection.

smoke.eval.ts, on the other hand, is the simplest end-to-end check: it runs a factual question with noTools: "all", asserts the output is "Paris", and checks usage metadata. It verifies that the evaluation framework itself works.

Metrics: lift and Paired Differences

After the controlled experiment runs, summarizeHarnessComparisons (packages/evals/src/vitest-evals/summary.ts) computes two kinds of metrics.

Correctness lift (CorrectnessLiftSummary):

export type CorrectnessLiftSummary = {
	eligiblePairs: number;
	baselinePassRate: number | null;
	candidatePassRate: number | null;
	lift: number | null; // candidatePassRate - baselinePassRate
};

lift = candidatePassRate - baselinePassRate, measured in percentage points (pp). If the candidate harness's pass rate is 12 points higher than baseline, lift is +12pp. This is the direct answer to "how much did my change improve correctness".

Paired metric differences (PairedMetricSummary): for totalTokens, totalMs (latency), and estimatedCostUsd (cost), it computes the paired differences between baseline and candidate. This answers "how much extra token/time/money did the accuracy gain cost".

The report (formatHarnessComparisonReport) renders these as colored terminal output:

correctness: +12.0 pp (candidate 85%, baseline 73%)
totalTokens: +1,234 (candidate ..., baseline ...)
estimatedCostUsd: +$0.05 (...)

It also diagnoses incomplete observations: missing-observation, duplicate-observation, harness-error, missing-score, unscorable-outcome. These diagnostics tell you which comparison pairs failed to produce valid data, so you aren't misled by incomplete statistics.

So "is switching this model / changing this prompt sentence / adding this tool worth it" becomes a multi-dimensional objective judgment: the correctness lift is positive, but how much did tokens and cost go up? If accuracy is +5pp but cost doubles, it may not be worth it; if accuracy is +5pp and cost stays flat, that's a net improvement.

Why This Matters Especially for a Minimal Agent

Back to the book's main thread. Pi Agent's core philosophy is minimalism: constantly pushing features out of the core. But every such tradeoff demands an answer: did this decision make the agent better or worse?

For example:

  • If you remove a guideline from the default prompt (to make it leaner), does agent performance degrade? extensions.eval.ts tests exactly this: it compares the "full prompt" against a prompt with the Guidelines/documentation sections removed.
  • Is it better to activate 4 tools by default or 7?
  • Switch to a cheaper model: how much accuracy is lost? How much cost is saved?
  • Add a skill: is it actually used effectively?

None of these questions has an a priori answer. pi-evals provides an objective referee: build a baseline and a candidate, run the controlled experiment, and look at lift and cost differences. Minimalism then stops being a matter of faith and becomes a testable hypothesis: if removing something shows lift ≈ 0 and lower cost, delete it with confidence; if lift is negative, keep it.

This is a model of data-driven architecture decisions. Many agent projects tune prompts and tool sets by intuition; Pi Agent turns that tuning into repeatable, comparable, quantifiable experiments. The evals package is private: true; it isn't shipped to users but is purely development-time quality infrastructure. Its existence is what lets the whole project keep making minimalism tradeoffs with confidence.

Practical Takeaways

pi-evals offers four transferable patterns for evaluating a non-deterministic agent.

Evaluate with a real model, not a mock. An eval really runs an AgentSession, really calls the model, really executes tools. The problem it solves: mocking the model can only test what you think it will do, not what it actually does. When evaluation is model-backed, you're measuring real emergent behavior rather than your assumptions. The cost is that evals are slow, expensive, and non-deterministic, but for the question "is the behavior correct", there is no cheaper shortcut.

Isolation + replayable artifacts. Every eval runs in a temporary directory with in-memory settings, and the directory is deleted afterward, but the session JSONL is snapshotted as an artifact. The problem it solves: evals interfering with each other, polluting the real environment, and leaving nothing to investigate after a failure. When every run is isolated yet leaves a complete record, evals are both repeatable and debuggable.

Comparison + repetition: turn a "feeling" into a "number". A baseline × candidate matrix, paired on identical inputs, repeated many times, computing correctness lift and token/cost paired differences. The problem it solves: a single run's result may be luck, and "it got better" is a vague feeling. When comparisons are paired, repeated, and lift is quantified, improvement becomes a statistically verifiable fact.

Drive architecture tradeoffs with evaluation. Use evals to verify whether removing or simplifying something hurts behavior, making minimalism a testable hypothesis rather than a matter of faith. The problem it solves: architecture tradeoffs made by intuition, where you can't tell if removing something was a mistake. When every tradeoff is judged by an eval, "staying minimal" has an objective basis: a way of combining engineering taste with engineering discipline.

Summary

pi-evals is Pi Agent's behavioral evaluation framework: createPiCodingAgentHarness adapts a real AgentSession into a vitest-evals harness that runs in a fully isolated temporary environment (in-memory settings, thinking off, session snapshotted as an artifact); evalHarnessTable builds a baseline × candidate comparison matrix with multiple repetitions; judging uses a deterministic judge or a model judge, and score >= 1 counts as passing; summary computes correctness lift (in percentage points) and token/latency/cost paired differences, rendered into a comparison report.

It isn't shipped to users (private: true), yet it is what lets the whole project keep making minimalism tradeoffs with confidence: every "should the core add/remove this" decision can be judged objectively by it. It is the infrastructure that turns minimalism from a matter of faith into a testable hypothesis.
