Chapter 10: System Prompts and Resource Assembly

The system prompt isn't a hardcoded string — it's assembled from tools' self-descriptions, project context files, and two-phase skill loading

The Agent's "Job Description"

The model itself doesn't know who it is, what tools it can use, or what conventions to follow. All of that lives in the system prompt — the Agent's "job description." Chapter 9's prompt() funnel cleans up user input, but before that ever runs, AgentSession has already assembled a system prompt as the backdrop for every model call.

This prompt is not a hardcoded string. It is assembled: dynamically pieced together from the active tools, the loaded skills, the project's context files, and the user's customizations. This chapter dissects that assembly process and the resource system behind it — skills, prompt templates, project context files, and slash commands.

Here lies a signature Pi Agent pattern: two-phase skill loading. The system prompt carries only each skill's name and description; the model reads the full content on demand. This seemingly simple decision resolves the fundamental tension between "more capabilities" and "bloated prompts."

buildSystemPrompt: The Assembly Pipeline

The system prompt is assembled by buildSystemPrompt (packages/coding-agent/src/core/system-prompt.ts). Its input is an options object:

export interface BuildSystemPromptOptions {
	customPrompt?: string;        // --system-prompt，替换默认提示词
	selectedTools?: string[];     // 默认 [read, bash, edit, write]
	toolSnippets?: Record<string, string>; // 每个工具的一行简介
	promptGuidelines?: string[];  // 追加的指南
	appendSystemPrompt?: string;  // --append-system-prompt，追加到末尾
	cwd: string;
	contextFiles?: Array<{ path: string; content: string }>; // AGENTS.md 等
	skills?: Skill[];
}

The default prompt (when there is no customPrompt) has this skeleton:

let prompt = `You are an expert coding assistant operating inside pi, a coding agent harness. You help users by reading files, executing commands, editing code, and writing new files.

Available tools:
${toolsList}

In addition to the tools above, you may have access to other custom tools depending on the project.

Guidelines:
${guidelines}

Pi documentation (read only when the user asks about pi itself, ...):
- Main documentation: ${readmePath}
- Additional docs: ${docsPath}
- Examples: ${examplesPath}
...`;

if (appendSection) prompt += appendSection;          // --append-system-prompt
// 项目上下文文件
if (contextFiles.length > 0) {
	prompt += "\n\n<project_context>\n\n";
	prompt += "Project-specific instructions and guidelines:\n\n";
	for (const { path: filePath, content } of contextFiles) {
		prompt += `<project_instructions path="${filePath}">\n${content}\n</project_instructions>\n\n`;
	}
	prompt += "</project_context>\n";
}
// skills
if (hasRead && skills.length > 0) prompt += formatSkillsForPrompt(skills);
// 工作目录
prompt += `\nCurrent working directory: ${promptCwd}`;

Let's walk through this assembly piece by piece.

"Available tools": From the Tools' Self-Descriptions

The tool list in the prompt isn't handwritten; it's stitched together from the active tools' promptSnippets:

const tools = selectedTools || ["read", "bash", "edit", "write"];
const visibleTools = tools.filter((name) => !!toolSnippets?.[name]);
const toolsList = visibleTools.length > 0
	? visibleTools.map((name) => `- ${name}: ${toolSnippets![name]}`).join("\n")
	: "(none)";

Recall from Chapter 4: every ToolDefinition carries its own promptSnippet (for the read tool, it's "Read file contents"). buildSystemPrompt collects the snippets of active tools and assembles the "Available tools" section. When a tool is active, its blurb automatically appears in the prompt; when it's disabled, the blurb disappears. This is the direct payoff of the self-describing tool design — adding a new tool requires no manual update to the system prompt.

Note the line "In addition to the tools above, you may have access to other custom tools depending on the project" — it tells the model that extensions may register custom tools (Chapter 14), keeping the model open to tools it hasn't seen.

"Guidelines": Generated Conditionally from the Toolset

The guidelines section isn't fixed; it's generated dynamically based on which tools are active:

const hasBash = tools.includes("bash");
const hasGrep = tools.includes("grep");
const hasFind = tools.includes("find");
const hasLs = tools.includes("ls");

// 文件探索指南
if (hasBash && !hasGrep && !hasFind && !hasLs) {
	addGuideline("Use bash for file operations like ls, rg, find");
}

for (const guideline of promptGuidelines ?? []) {
	addGuideline(guideline.trim()); // 工具自带的 promptGuidelines
}

// 总是包含
addGuideline("Be concise in your responses");
addGuideline("Show file paths clearly when working with files");

Look at the first condition: if bash is active but grep/find/ls are not (the default), the model is told to "Use bash for file operations like ls, rg, find." Because these three read-only tools are off in the default toolset (Chapter 4), the model needs to know it should use bash commands to search files. If the user enables grep/find/ls via --tools, this guideline disappears — the model now has dedicated tools.

addGuideline deduplicates with a Set — the tools' promptGuidelines (Chapter 4) merge with the default guidelines without repetition. So each tool's own guidelines (like read's "Use read to examine files instead of cat or sed") also flow into this section automatically.

Another win for self-description: tools not only declare what they "are" (snippet), but also what to "watch out for when using them" (guidelines), and the system prompt collects all of it automatically.

Project Context Files: <project_context>

If the project directory contains context files like AGENTS.md (or CLAUDE.md), their contents are wrapped in a <project_context> block:

<project_context>

Project-specific instructions and guidelines:

<project_instructions path="AGENTS.md">
...文件内容...
</project_instructions>

</project_context>

These files are discovered and loaded by ResourceLoader (its loadProjectContextFiles in packages/coding-agent/src/core/resource-loader.ts). Wrapping them in XML-style tags has two benefits: first, it gives the model a clear structural boundary ("these are project-specific instructions"); second, the path attribute lets the model know which file each instruction comes from.

Recall Chapter 1's security model: project context files come from potentially untrusted third-party repositories, so their loading is gated by project trust. --no-approve or --no-context-files skips them. This is the "project trust" decision showing up at the prompt-assembly stage — if you don't trust the project, its files never get injected into the prompt.

Two-Phase Skill Loading

Now for the highlight of this chapter. Skills are "specialized instructions for specific tasks" — like "how to review code" or "how to write migration scripts." A project may have dozens of skills, and each skill's full content can run hundreds of lines. Stuffing every skill's complete content into the system prompt would make it explode.

Pi Agent's solution is two-phase loading: the system prompt carries only each skill's name, description, and location, and the model reads the full content on demand. formatSkillsForPrompt (packages/coding-agent/src/core/skills.ts):

export function formatSkillsForPrompt(skills: Skill[]): string {
	const visibleSkills = skills.filter((s) => !s.disableModelInvocation);
	if (visibleSkills.length === 0) return "";

	const lines = [
		"\n\nThe following skills provide specialized instructions for specific tasks.",
		"Use the read tool to load a skill's file when the task matches its description.",
		"When a skill file references a relative path, resolve it against the skill directory ...",
		"",
		"<available_skills>",
	];
	for (const skill of visibleSkills) {
		lines.push("  <skill>");
		lines.push(`    <name>${escapeXml(skill.name)}</name>`);
		lines.push(`    <description>${escapeXml(skill.description)}</description>`);
		lines.push(`    <location>${escapeXml(skill.filePath)}</location>`);
		lines.push("  </skill>");
	}
	lines.push("</available_skills>");
	return lines.join("\n");
}

Here's the key instruction in that prompt text:

Use the read tool to load a skill's file when the task matches its description.

The system prompt gives the model only a "skill catalog" (name + description + file location) and tells it: "when a task matches a skill's description, use the read tool to load its file." Hence:

  • At startup: only the skill's frontmatter (name, description) is loaded — very cheap.
  • At call time: the model judges that the current task matches a skill, uses the read tool to load the full SKILL.md, and brings the detailed instructions into context.

That's the two phases: frontmatter goes into the prompt; the body is read on demand. A catalog of 30 skills might cost only a few hundred tokens, while their full contents could total tens of thousands — but the latter enters context only when actually needed.

The Skill interface (packages/coding-agent/src/core/skills.ts):

export interface SkillFrontmatter {
	name?: string;
	description?: string;
	"disable-model-invocation"?: boolean;
	[key: string]: unknown;
}

export interface Skill {
	name: string;
	description: string;
	filePath: string;
	baseDir: string;
	sourceInfo: SourceInfo;
	disableModelInvocation: boolean;
}

A skill is a SKILL.md file with YAML frontmatter. Skills with disableModelInvocation: true don't appear in the prompt (visibleSkills filters them out) — they can only be invoked explicitly by the user via /skill:name; the model can't trigger them on its own. This gives certain skills "for humans only, not the model" control.

Two-phase loading is another instance of Pi Agent's "push complexity to the edge" philosophy: the system prompt stays lean (the core), and full capabilities load on demand (the edge). It parallels the "two-phase skill loading" pattern of Claude Code in the reference book — a pattern proven repeatedly.

Prompt Templates: Reusable Prompt Fragments

Prompt templates (packages/coding-agent/src/core/prompt-templates.ts) are another "reusable prompt" mechanism, but unlike skills: templates are expanded when the user types, while skills are read on demand by the model.

export interface PromptTemplate {
	name: string;
	description: string;
	argumentHint?: string;
	content: string;
	sourceInfo: SourceInfo;
	filePath: string;
}

A template is a file whose content is a prompt with placeholders. When the user types /template-name arg1 arg2, expandPromptTemplate (:269) expands it into full text, and substituteArgs (:70) fills the arguments into the placeholders:

export function substituteArgs(content: string, args: string[]): string {
	// 把 $1, $2, ... 和 $@ 等占位符替换为实际参数
}

parseCommandArgs parses arguments with bash-style quoting rules (supporting "quoted arg"). So a user can define a /review template whose content is "Review the code for the following aspects: $1", and typing /review security expands to "Review the code for the following aspects: security".

The division of labor between templates and skills:

Prompt templatesSkills
Triggered byUser (types /name)Model (judges task match) or user
Expansion timingAt input time (in the prompt() funnel)At runtime (model reads via read)
Into system promptNo (expanded only when used)Yes (catalog goes into the prompt)
PurposePrompt shortcuts for the user's frequent useProfessional task instructions for the model

Both mechanisms "bake frequently used prompts into files," but they serve different audiences at different times.

Slash Commands: 22 Built-in Entry Points

Input starting with / is treated as a command. BUILTIN_SLASH_COMMANDS (packages/coding-agent/src/core/slash-commands.ts) defines 22 built-in commands:

/settings  /model  /scoped-models  /export  /import  /share  /copy
/name  /session  /changelog  /hotkeys  /fork  /clone  /tree
/trust  /login  /logout  /new  /compact  /resume  /reload  /quit

These commands fall into a few categories:

  • Session management: /new (new session), /session (switch), /fork//clone (branch), /tree (view the session tree), /resume (resume), /name (name)
  • Model and settings: /model (pick a model), /scoped-models, /settings, /hotkeys
  • Compaction: /compact (manual compaction, Chapter 7)
  • Import/export: /export//import (HTML/JSONL), /share (GitHub gist), /copy
  • Authentication: /login//logout
  • Trust: /trust (project trust, Chapter 1)
  • Extensions: /reload (reload extensions/resources)

Recall Chapter 9: the first step of the prompt() funnel is _tryExecuteExtensionCommand — input starting with / first tries to match an extension command. Extensions, skills, and templates can all register their own slash commands (SlashCommandSource = "extension" | "prompt" | "skill"), sharing the same / entry point as the built-ins. So / becomes the unified command surface of the product, extensions, skills, and templates.

ResourceLoader: The Resource Discoverer

Skills, templates, context files, extensions, themes — where do these resources come from? They're all discovered uniformly by ResourceLoader (packages/coding-agent/src/core/resource-loader.ts):

export interface ResourceLoader {
	reload(): Promise<...>; // 重新发现并加载所有资源
	// ...
}
export class DefaultResourceLoader implements ResourceLoader { ... }

DefaultResourceLoader.reload scans multiple locations (the project's .pi/, the user-global ~/.pi/, and paths given via CLI flags) and discovers extensions, skills, prompt templates, themes, and context files. It honors flags like --extension/--no-extensions, --skill/--no-skills, --prompt-template, --theme, and --no-context-files.

The /reload command re-invokes reload() — when you edit an extension or skill, /reload picks it up without restarting pi. AgentSessionRuntime's (Chapter 8) factory closure plays a role here: a reload can trigger session reconstruction.

Resource discovery is also gated by project trust — for an untrusted project, extensions and skills in its .pi/ are never loaded. Once again, Chapter 1's security model is put into practice.

Practical Takeaways

Pi Agent's resource assembly offers four transferable patterns for "how to give an agent capabilities and instructions."

The system prompt is assembled, not hardcoded. The tool list comes from tools' snippets, guidelines are generated conditionally from the active tools, and project files and skills are injected dynamically. The problem it solves: the prompt drifts out of sync with the toolset/capabilities, forcing you to hand-edit the prompt whenever you add a tool. When the prompt is assembled from components' self-descriptions, capabilities and prompt stay in sync forever.

Two-phase loading: catalog in the prompt, content read on demand. A skill puts only its name + description + location in the prompt, and the model loads the full body via the read tool when needed. The problem it solves: more capabilities mean a fatter prompt, until it blows up the context or dilutes attention. When only the "catalog" stays resident and "content" loads on demand, the number of capabilities is no longer bounded by prompt size. This pattern applies to any situation with "many optional capabilities, but only a few used at a time."

Distinguish "shortcuts for humans" from "professional instructions for the model." Prompt templates expand when the user types; skills are read on demand by the model — both pin down prompts as files, but their triggers and timing differ. The problem it solves: conflating the two needs, so either the user can't remember the commands or the model doesn't know when to use them. Once you separate the audiences, each mechanism can do its own job.

A unified command entry with an open registration surface. Built-in commands, extension commands, skills, and templates share the / entry point, and the first step of the prompt() funnel dispatches to extensions. The problem it solves: a closed command system leaves extensions unable to own their own commands. With a unified entry open to extensions, the product's command surface can grow linearly with its extensions.

Summary

Pi Agent's system prompt is assembled: buildSystemPrompt stitches the tool list and guidelines from the active tools' promptSnippet/promptGuidelines (a win for tool self-description), wraps project context files in <project_context> (gated by project trust), injects skills via two-phase loading (catalog in the prompt, body read on demand), and finally appends the working directory. Prompt templates and skills are two kinds of "reusable prompts" serving the user and the model respectively; the 22 built-in slash commands share the / entry point with extension/skill/template commands; ResourceLoader discovers all resources uniformly and supports hot reload via /reload.

The most profound piece is two-phase skill loading. With "catalog resident, content on demand," it resolves the fundamental tension of "more capabilities, fatter prompts" — yet another expression of Pi Agent's core philosophy: push complexity to the edge, and keep the core (here, the system prompt) lean.
