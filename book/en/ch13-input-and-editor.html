Chapter 13: Input, Keybindings, and the Editor

The complete journey of a keystroke from process.stdin to the focused component: raw mode, protocol negotiation, sequence reassembly, key parsing and keybinding, and that 2,352-line Emacs-style editor

The Underestimated Problem

If rendering is "writing strings to the terminal," then input is "reading strings from the terminal." Both sound easy, but anyone who has written a terminal application knows that input is a swamp.

Terminal keyboard input carries a heavy burden of legacy. When a keystroke reaches your program, it may be a single byte (a), a legacy escape sequence (the arrow key \x1b[A), a modifyOtherKeys sequence (Ctrl+Shift+p), or a Kitty protocol sequence (with modifiers, press/release, and base layout keys). Is Ctrl+C \x03 or \x1b[99;5u? Is Shift+Tab \x1b[Z or something else? How do you tell pasted multi-line text apart from keyboard input arriving byte by byte? The Windows console is yet another set of rules.

pi-tui's input stack exists to tame this swamp. This chapter follows a keystroke on its complete journey from process.stdin to the focused component's handleInput, and shows how Pi Agent makes sound engineering decisions at each layer: protocol negotiation, sequence reassembly, key parsing, and keybinding. Finally we look at the 2,352-line Editor, an Emacs-style multi-line editor and the input stack's heaviest consumer.

Terminal Setup: Raw Mode and Protocol Negotiation

ProcessTerminal.start (packages/tui/src/terminal.ts) is where input begins. It does several things:

// 1. 进入 raw mode：按键逐字节到达，不等回车、不回显
process.stdin.setRawMode(true);
process.stdin.setEncoding("utf8");
process.stdin.resume();

// 2. 启用 bracketed paste：粘贴内容被特殊序列包裹
process.stdout.write("\x1b[?2004h");

// 3. Windows：加载原生 addon 启用 VT 输入
this.enableWindowsVTInput();

// 4. 协商键盘协议
this.queryAndEnableKittyProtocol();

Raw mode is the prerequisite: by default the terminal is in "line mode": input is buffered until Enter and echoed automatically. Raw mode turns both off, letting every keystroke arrive immediately and untouched. It is the foundation of any interactive TUI.

Bracketed paste (\x1b[?2004h) makes the terminal wrap pasted content in \x1b[200~ ... \x1b[201~. This lets the program distinguish "the user pasted a block of code" from "the user typed a burst of keys"; the former is handled as a whole (even collapsed into a paste marker), the latter key by key. Without it, pasted multi-line text would be mistaken for a series of commands.

Negotiating the Kitty Keyboard Protocol

The most ingenious part is keyboard protocol negotiation. The legacy terminal keyboard protocol is riddled with ambiguities: Ctrl+Shift+p and Ctrl+p may emit the same sequence; key releases have no events; many combinations cannot be expressed at all. The Kitty keyboard protocol is a modern solution: it reports every key, modifier, and press/release unambiguously. But not every terminal supports it.

pi-tui's negotiation strategy (packages/tui/src/terminal.ts:220) is clever:

const KITTY_KEYBOARD_PROTOCOL_QUERY = `\x1b[>${DESIRED_KITTY_KEYBOARD_PROTOCOL_FLAGS}u\x1b[?u\x1b[c`;

This single line writes three sequences:

  1. \x1b[>Nu: requests enabling the Kitty protocol, with flags N = 1|2|4 (disambiguation + event types + alternate keys)
  2. \x1b[?u: queries the current Kitty protocol state
  3. \x1b[c: requests Device Attributes (DA), a sentinel

Then it watches how the terminal responds:

  • If the terminal supports Kitty, it reports back non-zero Kitty flags → activate the Kitty protocol
  • If the terminal doesn't support Kitty but does support DA, it replies with a DA response (not Kitty flags) → the sentinel fires, falling back to xterm's modifyOtherKeys (\x1b[>4;2m)

The "DA sentinel" design solves a classic problem: how do you know a terminal doesn't support Kitty? Unsupported terminals don't respond to the Kitty query; if you wait naively, you hang. But if you immediately follow with a DA query, terminals that support Kitty reply with DA and so do terminals that don't, so receiving a DA tells you "Kitty is out; use modifyOtherKeys." No timeout needed: the sentinel sequence turns "no response" into "a different kind of response." It is a neat trick that converts asynchronous probing into a deterministic branch.

Special Handling for Windows

The Windows console does not emit standard VT sequences by default. enableWindowsVTInput (:338) loads a precompiled native addon (native/win32/.../win32-console-mode.node), sets the ENABLE_VIRTUAL_TERMINAL_INPUT flag, and makes Shift+Tab arrive correctly as \x1b[Z. This is a microcosm of pi-tui's extensive terminal-specific engineering: there is also a native addon for macOS under native/darwin/.

StdinBuffer: Reassembling Fragmented Sequences

Bytes arrive fragmented. A \x1b[A (arrow key) may arrive in three pieces: \x1b, [, A. Processing byte by byte would mistake one escape sequence for three independent inputs. StdinBuffer (packages/tui/src/stdin-buffer.ts) handles the reassembly:

}

process accumulates incoming bytes into a buffer, and extractCompleteSequences uses isCompleteSequence to decide whether each sequence is complete. isCompleteSequence understands the framing of every kind of escape sequence: CSI (\x1b[...), OSC (\x1b]...), DCS, APC, SS3, and SGR mouse sequences (\x1b[<B;X;YM). Complete sequences are cut out, while the incomplete tail stays in the buffer waiting for the next batch of bytes.

What about the incomplete tail? StdinBuffer sets a 10ms timeout: if no further bytes arrive within 10ms, it flushes the tail as ordinary characters. This handles the case where "the user really pressed ESC" (ESC itself is \x1b, which is also the start of an escape sequence; if nothing follows within 10ms, it was a lone ESC).

StdinBuffer also handles bracketed paste specially: it recognizes the \x1b[200~ ... \x1b[201~ boundaries and emits the pasted content as a single paste event instead of splitting it into a stream of data events. It even handles terminal quirks, such as WezTerm splitting ESC from Kitty release sequences, and de-duplicating repeated Kitty printable characters.

StdinBuffer emits two kinds of events: data (a single complete sequence) and paste (a pasted body). This layer turns the "raw byte stream" into "structured input events."

Key Parsing: keys.ts

Complete sequences reach keys.ts (packages/tui/src/keys.ts), where they are mapped to a semantic key. One design choice here deserves praise: key ids are type-safe.

type ModifiedKeyId<Key extends string, RemainingModifiers extends ModifierName = ModifierName> = {
	[M in RemainingModifiers]: `${M}+${Key}` | `${M}+${ModifiedKeyId<Key, Exclude<RemainingModifiers, M>>}`;
}[RemainingModifiers];

export type KeyId = BaseKey | ModifiedKeyId<BaseKey>;

KeyId is a template literal type: strings like "ctrl+c", "ctrl+shift+p", and "escape" are themselves types. A Key helper object (:163) builds them with factory methods: Key.ctrl("c"), Key.ctrlShift("p"), Key.escape. So when binding keybindings, a misspelled key name fails at compile time instead of silently breaking at runtime.

The core API is two functions:

export function matchesKey(data: string, keyId: KeyId): boolean; // :820
export function parseKey(data: string): string | undefined;      // :1251

matchesKey decides whether a raw sequence matches a semantic key. Internally it must dispatch across several protocols:

  • Kitty CSI-u: the \x1b[99;5u form, with modifiers, shift/base layout keys, arrow keys, function keys, and event types
  • modifyOtherKeys: the \x1b[27;mod;keycode~ form
  • Legacy sequence tables: LEGACY_KEY_SEQUENCES, LEGACY_SHIFT_SEQUENCES, LEGACY_CTRL_SEQUENCES
  • Raw control characters: code & 0x1f (Ctrl+a = the codepoint of a & 0x1f = \x01)

The complexity of this dispatch is a direct map of the terminal keyboard's historical baggage: the same Ctrl+C can be four different byte sequences depending on the terminal and protocol. matchesKey has to recognize them all.

There is also careful handling of non-Latin layouts: the Kitty protocol reports both the "base layout key" and the "shifted key," and pi-tui only falls back to the base layout key when the codepoint is not a recognizable Latin letter or symbol, avoiding misreads on French and German keyboards. And there is handling of the Windows Terminal backspace ambiguity. These are scars left by real-world terminal fragmentation.

The event-type helpers isKeyRelease(data)/isKeyRepeat(data) scan for the :3u/:2u markers in a sequence: the Kitty protocol can distinguish press, repeat, and release. By default, release events are filtered out (unless a component sets wantsKeyRelease), because most components only care about presses.

Keybindings: Semantic Actions, Configurable

Parsed semantic keys are bound to actions through keybindings.ts (packages/tui/src/keybindings.ts). The design here is "action id + default key + user override":

// 语义动作 id（可通过声明合并扩展）
export interface Keybindings {
	"tui.editor.cursorWordLeft": ...;
	"tui.input.submit": ...;
	"tui.altScreen.pageUp": ...;
	// ...
}

// 默认绑定
export const TUI_KEYBINDINGS = {
	"tui.editor.deleteToLineEnd": { defaultKeys: "ctrl+k" },
	// ...
};

export class KeybindingsManager {
	// 解析用户覆盖、检测冲突、matches(data, keybinding)
}

Each action has a semantic id (tui.editor.deleteToLineEnd) and a default key (ctrl+k). KeybindingsManager parses user overrides, detects conflicts, and provides matches(data, keybinding). A global singleton is accessed via getKeybindings()/setKeybindings().

This design echoes a rule of the Pi Agent project. AGENTS.md states it explicitly:

Never hardcode key checks (e.g. matchesKey(keyData, "ctrl+x")). Add defaults to DEFAULT_EDITOR_KEYBINDINGS or DEFAULT_APP_KEYBINDINGS so they stay configurable.

In other words, the code must never hardcode "if Ctrl+X, do something"; it must register a semantic action through the keybinding system instead. This guarantees that all keybindings are configurable: users can rebind any action to any key. Separating "which key" from "which action" is the foundation of accessibility and personalization.

Focus and Overlays

When input reaches TuiBase.handleTerminalInput, it first passes through the registered input listeners (each can consume the input or rewrite data), handles the global debug key (shift+ctrl+d), filters key-release events, then routes to the focused component's handleInput, and finally calls requestRender().

setFocus(component) switches focus: it sets the focused flag on a Focusable component (which is why the component emits CURSOR_MARKER in render, Chapter 12).

There is also an overlay focus stack (overlayStack) that manages modal focus: when a picker pops up (say, model selection or trust confirmation), focus is captured by the overlay; when it closes, focus returns to the previous component. This state machine handles preFocus restoration, nonCapturing overlays, and the "blocked/eligible" focus restoration strategy. The pickers popped up by /model and /trust in interactive mode (Chapter 11) all rely on this overlay system for focus management.

Editor: A 2,352-Line Emacs-Style Editor

The input stack's heaviest consumer is the Editor (packages/tui/src/components/editor.ts, roughly 2,352 lines), the multi-line editor where users type prompts in interactive mode. It implements Component and Focusable and provides:

  • Multi-line editing with word wrap (wordWrapLine) and vertical scrolling
  • Autocomplete (autocomplete.ts): slash-command completion and file-path completion (CombinedAutocompleteProvider)
  • Kill ring (kill-ring.ts): an Emacs-style cut/paste ring: Ctrl+K kills to end of line into the ring, Ctrl+Y yanks it back, and repeated yanks cycle through history
  • Undo stack (undo-stack.ts): edit snapshots
  • Word navigation (word-navigation.ts): Ctrl+Left/Right jumps by word
  • Paste markers: large pastes are collapsed into a single marker instead of flooding the editor
  • History: the up/down arrow keys browse past inputs

Editor is not standalone; it is supported by several dedicated modules: kill-ring.ts, undo-stack.ts, word-navigation.ts, autocomplete.ts, and fuzzy.ts (fuzzy matching). This "heavy component + dedicated submodules" organization keeps a 2,352-line component maintainable: every editing feature has its own module.

Editor is also an implementation of the EditorComponent interface (packages/tui/src/editor-component.ts), the contract for "custom editors," which lets the product layer replace or extend editor behavior.

Why does a coding agent need such a heavy editor? Because users write multi-line prompts, paste code snippets, and edit with keybindings inside it; the input experience directly determines how usable the product is. Editor's Emacs-style keybindings (kill ring, word navigation, undo) let terminal-savvy users edit efficiently without a mouse. This is the investment a "product for humans" makes at the input layer.

Practical Takeaways

pi-tui's input stack offers four transferable patterns for "how to handle terminal input," each one born from real fights with terminal fragmentation.

Use a sentinel sequence to turn "no response" into "a different response." The Kitty protocol query is immediately followed by a DA query as the sentinel: receiving a DA tells you Kitty is unsupported, with no timeout wait. The problem it solves: when probing an optional capability, "not supported" manifests as "no response," which either hangs you or forces a fragile timeout. When a sentinel sequence converts silence into a definite signal, asynchronous probing becomes a deterministic branch.

Reassemble first, parse second. StdinBuffer reassembles the fragmented byte stream into complete sequences and separates pastes before handing them to key parsing. The problem it solves: escape sequences arrive in multiple batches, and byte-by-byte processing misjudges them. Once input is cut at the right granularity, "complete sequences," the layers above can parse correctly. Framing and parsing are two layers; don't mix them together.

Make key ids type-safe, and keybindings semantic and configurable. Key ids are template literal types (a typo fails to compile), actions have a semantic id + default key + user override, and hardcoded key checks are banned. The problems it solves: misspelled key names only surface at runtime, and keybindings cannot be reconfigured. When keys are types, actions are semantic, and bindings are overridable, both correctness and accessibility are guaranteed.

Split heavy components into dedicated submodules. The 2,352-line Editor is supported by independent modules: the kill ring, undo stack, word navigation, and autocomplete. The problem it solves: a single large component that kneads every feature together becomes impossible to test and maintain. When each editing feature is its own module, even a heavy component stays maintainable.

Summary

pi-tui's input stack is four layers from the bottom up: ProcessTerminal enters raw mode, enables bracketed paste, negotiates the Kitty keyboard protocol with a "DA sentinel" (falling back to modifyOtherKeys), and loads a native addon on Windows; StdinBuffer reassembles the fragmented byte stream into complete sequences and separates pastes; keys.ts maps sequences to semantic keys with the type-safe KeyId and matchesKey, dispatching across four protocols: Kitty, modifyOtherKeys, legacy, and raw control characters; keybindings.ts wires keys to actions through semantic action ids and configurable bindings. The focus system routes input to the focused component, and the overlay stack manages modal focus. The heaviest consumer is the 2,352-line Emacs-style Editor, supported by dedicated modules for the kill ring, undo stack, word navigation, and autocomplete.

Like the rendering layer, it embodies a "close to the metal" engineering taste: rather than depending on a high-level framework, it faces terminal protocol fragmentation head-on and handles each layer correctly. Each of the seemingly excessive details (the DA sentinel, the 10ms timeout, the non-Latin layout fallback, the Windows VT addon) is the fix for a real bug in some real terminal.
