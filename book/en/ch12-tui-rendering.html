Chapter 12: pi-tui — A Homegrown Renderer

Bringing rendering back to "lines + ANSI": components output string arrays, the renderer compares line by line and writes only what changed — a homegrown, flicker-free, scrollable terminal renderer

An Unusual Decision

Chapter 11's interactive mode renders AgentSessionEvent onto the terminal screen. Underneath those screens is pi-tui (packages/tui) — Pi Agent's terminal UI library.

One unusual decision deserves to be stated up front: pi-tui is not based on React/Ink. No virtual DOM, no JSX, no reconciler. In an era where "terminal UI" is nearly synonymous with Ink, Pi Agent wrote a renderer from scratch.

Why? Because Pi Agent's needs are in fundamental tension with Ink's model. Ink models the terminal as a fixed-height viewport and diffs a virtual DOM. But a coding agent's output is a streaming, ever-growing document — assistant replies pour out line by line, tool results get appended chunk by chunk, and the user needs to scroll up to review. Ink's "fixed viewport + full recompute" model flickers in this scenario and loses scroll history. What Pi Agent wants is "to write the ever-growing document efficiently into the terminal's scrollback buffer, rewriting only the lines that changed."

So pi-tui's core model is almost naively simple: components render into arrays of strings, and the renderer compares line by line, writing only what changed. This chapter dissects that model and shows how, with very little abstraction, it achieves flicker-free, scrollable terminal rendering with image and IME support.

The Component Contract: render(width) => string[]

pi-tui components are not React functions but an interface (packages/tui/src/tui.ts):

export interface Component {
	/** 把组件渲染成给定视口宽度下的若干行 */
	render(width: number): string[];
	/** 获得焦点时的键盘输入处理（可选） */
	handleInput?(data: string): void;
	/** 是否接收按键释放事件（Kitty 协议），默认 false */
	wantsKeyRelease?: boolean;
	/** 使缓存的渲染状态失效（主题变更等） */
	invalidate(): void;
}

The core is render(width): string[] — given a width, return an array of strings, one per line (possibly containing ANSI escape sequences). This is pull-based rendering: the renderer actively calls the component's render, and the component decides how many lines to emit based on its own content. There is no retained scene graph for the renderer to walk and lay out — components produce their own lines.

The benefit of this contract is a mental model that hugs the terminal: the terminal is "lines + ANSI," and a component's output is also "lines + ANSI." There is no virtual-DOM layer of translation in between. The cost is that each component must handle its own wrapping, truncation, and caching — but that logic is inherently component-specific anyway.

Focusable components implement Focusable:

export interface Focusable {
	focused: boolean; // TUI 在焦点变化时设置
}

A focused component emits a zero-width CURSOR_MARKER at its logical cursor position within its render output:

export const CURSOR_MARKER = "\x1b_pi:c\x07"; // 零宽 APC 序列

The renderer later finds this marker, computes the visual column, strips it, and moves the hardware cursor there — so the IME candidate window can position itself correctly. This zero-width marker is a neat design: the component doesn't need to know the hardware cursor exists; it just says "here is where my cursor is," and the renderer aligns the hardware cursor to it.

Composition: Container and the Component Catalog

Components compose through Container (packages/tui/src/tui.ts):

export class Container implements Component {
	children: Component[] = [];
	addChild(component: Component): void;
	removeChild(component: Component): void;
	clear(): void;
	invalidate(): void;
	render(width: number): string[]; // 垂直拼接所有子组件的行
}

Container.render simply calls each child's render(width) in turn and concatenates the results vertically. It's the most primitive layout — stacking top to bottom.

On top of that, pi-tui provides a component catalog (packages/tui/src/components/):

Renderers: One Interface, Two Implementations

TUI is the interface consumers see (packages/tui/src/tui.ts): addChild, setFocus, showOverlay/hideOverlay, start/stop, requestRender, addInputListener. It has an abstract base class TuiBase that leaves one abstract method:

export abstract class TuiBase extends Container implements TUI {
	protected abstract doRender(): void;
	// 焦点、overlay、输入监听、帧调度、终端查询
}

doRender() is the concrete "write the current frame to the terminal" implementation, provided by each of two subclasses:

  • TuiMainScreen (packages/tui/src/TuiMainScreen.ts): writes to the terminal's scrollback buffer; output can grow endlessly and scroll upward. This is what interactive mode uses by default — the agent's streaming output is an ever-growing document. It uses relative cursor movement to rewrite only the changed line range.
  • TuiAltScreen (packages/tui/src/TuiAltScreen.ts): enters the terminal's alternate screen, owning a fixed-height viewport with mouse support, selection, and true 2D layout. It rewrites line by line using absolute cursor addressing.

The two renderers share TuiBase's focus management, overlay system, frame scheduling, and input handling; they diverge only in "how the frame is written to the terminal." This is the strategy pattern: consumers face a single TUI interface while the underlying rendering strategy is swappable. The ViewportTUI interface plus the isViewportTUI guard identify "is this an alt-screen renderer," gating alt-screen-only features (such as setLayoutRoot).

Diff Rendering: A Line-by-Line Equality Scan

Now for the core. How does TuiMainScreen.doRender() (packages/tui/src/TuiMainScreen.ts:146) write only the changed lines? The answer is astonishingly plain — a line-by-line string equality scan:

let firstChanged = -1;
let lastChanged = -1;
const maxLines = Math.max(newLines.length, this.previousLines.length);
for (let i = 0; i < maxLines; i++) {
	const oldLine = i < this.previousLines.length ? this.previousLines[i] : "";
	const newLine = i < newLines.length ? newLines[i] : "";
	if (oldLine !== newLine) {
		if (firstChanged === -1) firstChanged = i;
		lastChanged = i;
	}
}

It compares the new frame (newLines, the result of render(width) across the whole component tree) with the previous frame (previousLines) line by line, finding the first and last changed lines. No LCS, no edit distance — just oldLine !== newLine.

Once the changed range is found, it rewrites only that range: it moves the hardware cursor to firstChanged (via relative moves \x1b[...A/\x1b[...B), then emits \x1b[2K (erase the whole line) plus the new content for each changed line. Stale old lines at the end are erased separately.

That's all "double buffering" means here: the previousLines array is retained between frames as the diff baseline. No offscreen canvas, no pixel buffer — the "buffer" is just an array of strings.

When a Full Redraw Happens

Not every situation can be incremental. doRender falls back to fullRender (clear screen + full resend) in several cases:

// 首次渲染
if (this.previousLines.length === 0 && !widthChanged && !heightChanged) {
	fullRender(false); // 全量，但不清屏
	return;
}
// 宽度变化、或变化发生在可视视口之上、或需要清屏收缩
if (widthChanged || firstChanged < prevViewportTop || ...) {
	fullRender(true); // 清屏 + 清滚动缓冲 + 全量
	return;
}

The firstChanged < prevViewportTop condition is worth noting: if a change happens above the region the user has scrolled up to (and can't see), incremental rewriting would miscount the cursor position, so it just does a full redraw. This is a pragmatic compromise — incremental rendering is efficient in the common cases (appends at the bottom, localized updates) and falls back to full rendering in the rare ones (changes above, size changes).

Synchronized Output: The Key to No Flicker

Whether incremental or full, the whole frame is wrapped in a synchronized output sequence:

let buffer = "\x1b[?2026h"; // Begin synchronized output
// ... 拼接所有变化行的擦除 + 重写 ...
buffer += "\x1b[?2026l"; // End synchronized output
this.terminal.write(buffer); // 一次性写出

\x1b[?2026h/\x1b[?2026l tell the terminal: "a batch of updates is coming — buffer them and display them all at once when the end sequence arrives." Terminals that support it (most modern ones) render the whole frame as one atomic operation — the user never sees the intermediate "erase first, then rewrite line by line" state, hence no flicker. The whole frame is assembled into a single string and written in one write call; combined with synchronized output, that guarantees atomicity.

Enforcing the Contract Defensively

doRender also has a guard: if any component returns a line whose visibleWidth exceeds the terminal width, it throws and writes a pi-crash.log:

// 若某行宽度超过终端宽度 → 抛错 + 诊断日志，指向 truncateToWidth

This turns a silent rendering corruption (lines so long that the terminal wraps them and the layout breaks) into an actionable error that directly points out "which component should use truncateToWidth." It's a good example of "turning a contract violation into a loud error" — rather than letting the user stare at a broken UI with no way to investigate, crashing and leaving a diagnostic log is friendlier.

Frame Scheduling: A 16ms Throttle

Components don't trigger a redraw on every state change. TuiBase.requestRender (packages/tui/src/tui.ts:745) coalesces and throttles:

requestRender(force = false): void {
	if (force) {
		this.resetRenderState();
		// ... 立即在 nextTick 渲染 ...
		return;
	}
	if (this.renderRequested) return; // 合并：已有请求就不重复
	this.renderRequested = true;
	process.nextTick(() => this.scheduleRender());
}

private scheduleRender(): void {
	if (this.stopped || this.renderTimer || !this.renderRequested) return;
	const elapsed = performance.now() - this.lastRenderAt;
	const delay = Math.max(0, TuiBase.MIN_RENDER_INTERVAL_MS - elapsed); // 16ms
	this.renderTimer = setTimeout(() => {
		this.renderTimer = undefined;
		if (this.stopped || !this.renderRequested) return;
		this.renderRequested = false;
		this.lastRenderAt = performance.now();
		this.doRender();
		if (this.renderRequested) this.scheduleRender(); // 期间又有请求就再排一次
	}, delay);
}

Two mechanisms:

  • Coalescing: the renderRequested flag ensures that multiple requestRender calls trigger only one render per frame. During streaming output every token delta calls requestRender, but the actual renders are coalesced.
  • Throttling: MIN_RENDER_INTERVAL_MS = 16 (about 60fps) ensures at least 16ms between frames. Spinners and streaming output never flush the terminal hundreds of times per second.

start() wires up the terminal: this.terminal.start((data) => this.handleTerminalInput(data), () => this.requestRender()) — input triggers a render, and window resizes do too. Components can also call tui.requestRender() themselves (e.g. Loader on its timer, Editor after edits).

The Dual Layout Model

VStack/HStack/ScrollView — these layout containers have an interesting split personality.

On TuiMainScreen (and in non-layout contexts), they use plain render(width) — VStack.render just concatenates the children's lines vertically, producing an unbounded document. That's exactly what streaming agent output needs: the document can grow without limit.

But on TuiAltScreen, they participate in a real 2D flexbox layout through a symbol protocol, LAYOUT_NODE (packages/tui/src/layout-node.ts):

export const LAYOUT_NODE = Symbol.for("@earendil-works/pi-tui/layout-node");
export type LayoutNode = StackLayoutNode | ScrollLayoutNode;
export function getLayoutNode(component: Component): LayoutNode | undefined

The alt screen's layout engine (renderLayoutFrame in packages/tui/src/layout.ts) recursively builds the layout tree, measures intrinsic sizes, distributes space by grow/shrink, computes clipping, and composites every box into the fixed-height screen. This lets the alt screen have "confined regions that scroll independently" — for example, a fixed-height list plus an independently scrolling details panel.

So the same set of components behaves as an unbounded document on the main screen and as a flexbox viewport on the alt screen. Using a symbol rather than instanceof as the capability protocol lets this duck-typed extension work across packages. It's a clean separation of two UI paradigms — "streaming document" versus "application viewport" — while reusing the components.

Practical Takeaways

pi-tui offers four transferable patterns for "how to build a terminal UI." Some run counter to the mainstream virtual-DOM approach, yet they fit streaming agents perfectly.

Rendering is strings; diffing is an equality scan. Components output string[], the renderer compares line by line with !== and rewrites only the changed range. The problem it solves: a virtual-DOM reconciler is overkill for an ever-growing streaming document, and the fixed-viewport model loses scroll history. When the output is already the terminal's native representation (lines + ANSI), the renderer can be paper-thin, and scrolling and incremental updates both fall out naturally. The cost is that each component manages its own wrapping/truncation/caching — but for a library this close to the terminal, that cost buys simplicity and control.

Synchronized output + a single write = no flicker. Assemble the whole frame into one string, wrap it in \x1b[?2026h/l, and write it once. The problem it solves: line-by-line writes expose the intermediate states of a redraw. When the terminal displays the whole frame as an atomic operation, the user sees one clean update no matter how many lines were erased internally.

Coalescing + throttling govern render frequency. renderRequested coalesces multiple requests, and a 16ms throttle caps the frame rate. The problem it solves: every streaming delta and every animation tick triggers a redraw, flooding the terminal and wasting CPU. When render requests are coalesced and throttled, the actual frame rate stays within a sane range no matter how often state changes.

Replace silent corruption with contract enforcement. A component returning an over-wide line throws and leaves a diagnostic log instead of quietly breaking the UI. The problem it solves: rendering bugs manifest as UI corruption that's hard to track down. When a contract violation becomes a loud error that points toward the fix, debugging costs drop sharply.

Summary

pi-tui is a fully homegrown terminal renderer whose core model is plain but powerful: components implement render(width): string[], Container concatenates vertically, TuiBase provides focus/overlays/frame scheduling, and two concrete renderers (the main screen TuiMainScreen writing the scrollback buffer and the alt screen TuiAltScreen writing a fixed viewport) share one TUI interface. Diff rendering is a line-by-line string equality scan that rewrites only the changed range; synchronized output plus a single write guarantees no flicker; a 16ms throttle plus request coalescing governs the frame rate. Focusable components mark the cursor with a zero-width CURSOR_MARKER for IME support, and the layout containers have their "unbounded document" / "flexbox viewport" split personality.

It isn't based on React/Ink — not for novelty's sake, but because a streaming agent's output is an ever-growing document that needs the "lines + diff + scrollback buffer" model rather than the "fixed viewport + virtual DOM" model. Understand that, and you understand why a decision that looks like "reinventing the wheel" is in fact a precise response to the requirement.
