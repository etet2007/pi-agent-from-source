Part III · Persistent Orchestration

Chapter 6: AgentHarness — A Persistable Orchestrator

A persistable, hook-driven orchestrator: IO dependency inversion, 22 typed hooks, safe-point persistence — and why the product layer ultimately bypassed it

The Gap the Core Deliberately Left

The core loop of Chapter 3 is pure: it only knows an emit callback and a set of "never-throwing" configuration slots. It touches no file system, performs no persistence, and manages no compaction. This is deliberate — but it is also incomplete. A real, usable agent needs to: persist the transcript to disk, compact the context when it grows too long, insert logic before and after tool calls, manage skills and prompt templates, and provide built-in file/Shell tools.

pi-agent-core puts these "batteries" in a separate layer: the Harness (packages/agent/src/harness/**). Its centerpiece is the AgentHarness class (packages/agent/src/harness/agent-harness.ts, about 1,186 lines), a persistable, hook-driven orchestrator built directly on top of runAgentLoop.

This chapter dissects this layer. But more importantly, we want to answer an architectural question: why does the same package contain both a minimal core and this fully-loaded Harness? And a sharper one: why did the product layer pi-coding-agent ultimately not use it, instead building its own orchestrator? The answers to these two questions are precisely the finest expression of the "minimal core" philosophy.

What the Harness Adds on Top of the Core

The core Agent class (Chapter 5) is an in-memory loop wrapper. AgentHarness adds on top of it an entire suite of persistence and orchestration capabilities:

Item by item:

  • Persistent session tree: the Harness holds a Session (the tree from Chapter 5) and persists each turn's messages into it.
  • Hook system: 22 typed hook events let external code insert logic at key nodes of the loop.
  • Compaction and branch summaries: automatically generates summaries when the context grows too long, and branch summaries when switching branches.
  • Built-in tools: bash, read, edit, write, built on the ExecutionEnv abstraction.
  • Skills and prompt templates: loads SKILL.md, formats prompt templates.
  • Phase state machine: tracks what the harness is currently doing (idle/turn/compaction/...).

The key point: these capabilities are not in the core loop. The core loop stays pure — the Harness achieves all of this by stuffing callbacks into the core's configuration slots and subscribing to the core's event stream. The Harness is a consumer of the core, not a modifier of it.

ExecutionEnv: Inverting IO Outward

The Harness's built-in tools need to read and write files and execute commands. But it doesn't use node:fs and node:child_process directly — that would bind it to the Node environment. It defines an IO abstraction, ExecutionEnv (packages/agent/src/harness/types.ts):

export interface ExecutionEnv extends FileSystem, Shell {}

FileSystem is a set of file operations, each returning a Result rather than throwing:

export interface FileSystem {
	cwd: string;
	absolutePath(path, abortSignal?): Promise<Result<string, FileError>>;
	readTextFile(path, abortSignal?): Promise<Result<string, FileError>>;
	readTextLines(path, options?): Promise<Result<string[], FileError>>;
	readBinaryFile(path, abortSignal?): Promise<Result<Uint8Array, FileError>>;
	writeFile(path, content, abortSignal?): Promise<Result<void, FileError>>;
	appendFile(path, content, abortSignal?): Promise<Result<void, FileError>>;
	listDir(path, abortSignal?): Promise<Result<FileInfo[], FileError>>;
	canonicalPath(path, abortSignal?): Promise<Result<string, FileError>>;
	exists(path, abortSignal?): Promise<Result<boolean, FileError>>;
	createDir(path, options?): Promise<Result<void, FileError>>;
	remove(path, options?): Promise<Result<void, FileError>>;
	createTempDir(prefix?, abortSignal?): Promise<Result<string, FileError>>;
	cleanup(): Promise<void>; // 必须尽力而为，且不得抛出
}

export interface Shell {
	exec(command, options?): Promise<Result<{ stdout: string; stderr: string; exitCode: number }, ExecutionError>>;
	cleanup(): Promise<void>;
}

Two design decisions here are worth noting.

First, the Result type replaces exceptions. Result<TValue, TError> is a simple discriminated union:

export type Result<TValue, TError> = { ok: true; value: TValue } | { ok: false; error: TError };

The documentation of FileSystem and Shell makes the requirement explicit: all failures are encoded into the returned Result, and implementations must uphold this invariant — never throw. This is the Chapter 3 "failure is data" contract continued at the IO layer. Tool execution logic can therefore be written as straightforward if (result.ok) ... else ..., without wrapping every file operation in try/catch. cleanup() even requires "best effort, and must not throw" — resource release can never blow up.

Second, dependency inversion makes tools portable across environments. Because tools depend on the ExecutionEnv interface rather than a concrete implementation, the same createBashTool can run on different environments. The Node environment uses NodeExecutionEnv (packages/agent/src/harness/env/nodejs.ts, based on node:fs/node:child_process); but in principle you could provide an implementation that forwards operations to a remote SSH host, a container, or a browser. The pluggable operations of tools mentioned in Chapter 4 (delegating file IO to a remote system) are built exactly on this abstraction.

withFileMutationQueue (the file mutex from Chapter 4) is also keyed by ExecutionEnv — a WeakMap<ExecutionEnv, ...> — so different execution environments get their own independent mutex queues. The IO abstraction and concurrency safety interlock naturally here.

The Phase State Machine: What the Harness Is Doing Now

AgentHarness tracks its macro-state with a phase field:

export type AgentHarnessPhase = "idle" | "turn" | "compaction" | "branch_summary" | "retry";
  • idle: idle, ready to accept new operations
  • turn: running a conversation turn
  • compaction: compacting the context
  • branch_summary: generating a branch summary
  • retry: retrying

One practical use of this state machine is mutex protection. For example, navigateTree (branch navigation) checks at the start:

async navigateTree(...): Promise<NavigateTreeResult> {
	if (this.phase !== "idle") throw new AgentHarnessError("busy", "navigateTree() requires idle harness");
	// ...
}

compact() likewise requires idleness. This avoids the dangerous concurrency of "modifying the session tree while a conversation is running". The phase is not UI state (that is driven by the event stream); it is the harness's own internal ledger of "what am I busy with".

The Harness also uses an activeTasks: Map<Promise, "operation" | "mutation"> to track all in-flight async work, distinguishing "operations" from "mutations", so it can wait for them to finish on shutdown.

createTurnState: A Snapshot per Turn

At the start of each turn, the Harness takes a snapshot, createTurnState() (packages/agent/src/harness/agent-harness.ts):

private async createTurnState() {
	// 从会话树构建上下文，快照：
	// messages, resources, toolContext, streamOptions, sessionId,
	// systemPrompt, model, thinkingLevel, tools, activeTools
}

It rebuilds the context from the Session (buildSessionContext), freezing the current model, thinking level, active tools, system prompt, resources, and more into an immutable per-turn state. That turn runs on this snapshot.

Why re-snapshot every turn? Because state can be modified while running — the user might switch models or change active tools while the agent is working. If the loop kept using the stale state from startup, those changes would never take effect. The snapshot mechanism gives "changes between turns" a well-defined moment to take effect.

This interlocks with the prepareNextTurn hook from Chapter 3. The Harness's createLoopConfig implements it like this:

prepareNextTurn: async () => {
	await this.flushPendingSessionWrites();      // 先把待写的落盘
	const nextTurnState = await this.createTurnState(); // 重新从会话树快照
	setTurnState(nextTurnState);
	return {
		context: this.createContext(nextTurnState),
		model: nextTurnState.model,
		thinkingLevel: nextTurnState.thinkingLevel,
	};
},

At the end of each turn and before the next one begins: first flush the buffered writes to disk, then rebuild the snapshot from the session tree, and return the fresh context/model/thinkingLevel to the loop. So mid-run modifications like setModel() take effect at the next turn boundary. This is a clean "changes take effect at safe points" model.

createLoopConfig: From Core Slots to Harness Hooks

This is the Harness's most central adaptation work. The core loop has only a handful of configuration slots (transformContext, beforeToolCall, afterToolCall, prepareNextTurn, getSteeringMessages, getFollowUpMessages), while the Harness has a much richer hook system. createLoopConfig is the adapter that maps the former onto the latter:

private createLoopConfig(getTurnState, setTurnState): AgentLoopConfig {
	const turnState = getTurnState();
	return {
		model: turnState.model,
		reasoning: turnState.thinkingLevel === "off" ? undefined : turnState.thinkingLevel,
		convertToLlm,
		// 核心的 transformContext 槽位 → harness 的 "context" hook
		transformContext: async (messages) => {
			const result = await this.emitHook({ type: "context", messages: [...messages] });
			return result?.messages ?? messages;
		},
		// 核心的 beforeToolCall 槽位 → harness 的 "tool_call" hook
		beforeToolCall: async ({ toolCall, args }) => {
			const result = await this.emitHook({
				type: "tool_call",
				toolCallId: toolCall.id,
				toolName: toolCall.name,
				input: args,
			});
			return result ? { block: result.block, reason: result.reason } : undefined;
		},
		// 核心的 afterToolCall 槽位 → harness 的 "tool_result" hook
		afterToolCall: async ({ toolCall, args, result, isError }) => {
			const patch = await this.emitHook({
				type: "tool_result",
				toolCallId: toolCall.id,
				toolName: toolCall.name,
				input: args,
				content: result.content,
				details: result.details,
				isError,
				usage: result.usage,
			});
			return patch ? { content: patch.content, details: patch.details, isError: patch.isError, usage: patch.usage, terminate: patch.terminate } : undefined;
		},
		prepareNextTurn: async () => { /* 如上 */ },
		getSteeringMessages: async () => this.drainQueuedMessages(this.steerQueue, this.steeringQueueMode),
		getFollowUpMessages: async () => this.drainQueuedMessages(this.followUpQueue, this.followUpQueueMode),
	};
}

Look at this mapping: the core's transformContext slot is wired to the harness's context hook, the core's beforeToolCall to the tool_call hook, and the core's afterToolCall to the tool_result hook. The core provides the mechanism ("here is a slot you can intercept"), and the Harness provides the policy ("which hooks fire when intercepted, and how results are aggregated").

This adaptation direction matters: the Harness adapts to the core, not the core to the Harness. The core loop knows nothing about the hook system — it just calls transformContext; whether that callback internally triggers a 22-event hook system is none of its concern. That is what layering is for: the lower layer stays stable, the upper layer evolves freely.

The Hook System: 22 Typed Events

The Harness's hook system is defined by AgentHarnessEventResultMap (packages/agent/src/harness/types.ts), listing all hook events and their return types:

export type AgentHarnessEventResultMap = {
	before_agent_start: BeforeAgentStartResult | undefined;
	context: ContextResult | undefined;
	before_provider_request: BeforeProviderRequestResult | undefined;
	before_provider_payload: BeforeProviderPayloadResult | undefined;
	after_provider_response: undefined;
	tool_call: ToolCallResult | undefined;
	tool_result: ToolResultPatch | undefined;
	session_before_compact: SessionBeforeCompactResult | undefined;
	session_compact: undefined;
	session_before_tree: SessionBeforeTreeResult | undefined;
	session_tree: undefined;
	retry_scheduled: undefined;
	retry_attempt_start: undefined;
	retry_finished: undefined;
	model_update: undefined;
	thinking_level_update: undefined;
	resources_update: undefined;
	tools_update: undefined;
	queue_update: undefined;
	save_point: undefined;
	abort: undefined;
	settled: undefined;
};

22 events, in two categories:

  • Behavior-affecting (return values other than undefined): before_agent_start, context, before_provider_request, before_provider_payload, tool_call, tool_result, session_before_compact, session_before_tree. Handlers of these hooks can return a result to change behavior — for example, tool_call returning { block: true } blocks a tool, and context returns a modified message list.
  • Notification-only (return undefined): after_provider_response, session_compact, retry_scheduled, model_update, tools_update, abort, settled, and others. These merely announce "something happened", for external code to record or sync state.

emitHook is the trigger:

private async emitHook<TType extends keyof AgentHarnessEventResultMap>(
	event: { type: TType } & ...,
): Promise<AgentHarnessEventResultMap[TType]> {
	// 依次调用注册的处理器，返回最后一个非 undefined 的结果
}

It calls handlers in registration order and returns the last non-undefined result. This "last-wins" semantics lets multiple handlers stack, with later ones overriding earlier ones.

Note that this hook system is strongly typed: the payload and return type of every event are precisely constrained by AgentHarnessEventResultMap. When you register a tool_call handler, you get full type checking at compile time. This stands in sharp contrast to "runtime hook strings" (hooks.on("PreToolUse", ...)) — where you only find out at runtime whether the event name is spelled correctly or what the payload looks like. In Chapter 14 we'll see that the product layer's extension system inherits this "typed extensions" taste.

Persistence: Writing at Safe Points

The Harness persists messages into the session tree, but not every message is written to disk immediately — it uses a write buffer, pendingSessionWrites, flushed in one go at safe points.

handleAgentEvent is the harness's event handler (the counterpart of the core Agent's processEvents). On message_end it records the message into the buffer, and on turn_end/agent_end it flushes:

private async handleAgentEvent(event: AgentEvent, signal?: AbortSignal): Promise<void> {
	// message_end → 记入 pendingSessionWrites
	// turn_end / agent_end → flushPendingSessionWrites()
}

private async flushPendingSessionWrites(): Promise<void> {
	while (this.pendingSessionWrites.length > 0) {
		const write = this.pendingSessionWrites[0]!;
		if (write.type === "message") {
			await this.session.appendMessage(write.message);
		} else if (write.type === "model_change") {
			// ...
		}
		// 出队，继续
	}
}

Why buffer instead of writing immediately? Because changes can occur mid-run (setModel(), setThinkingLevel()); if written into the session tree immediately, they could interleave with the in-flight message stream and produce inconsistent intermediate states. Buffering them and flushing at safe points like turn_end/agent_end/prepareNextTurn guarantees that session tree writes are ordered and atomic.

handleAgentEvent also handles failure fallback — just like the core Agent, unexpected errors are converted into a normal failure event sequence (message_start → message_end → turn_end → agent_end) before being handed to handleRunFailure for persistence. The contract "failure is also a normal event sequence" carries through from the core all the way to the Harness.

Compaction and Branch Navigation

The Harness exposes the two session-tree operations mentioned in Chapter 5 as methods: compact() and navigateTree().

compact(customInstructions?) (detailed in Chapter 7) triggers context compaction: it generates a summary, appends a CompactionEntry, and subsequent context builds use "summary + tail". It fires the session_before_compact and session_compact hooks around it and switches the phase to compaction.

navigateTree(...) navigates the session tree (branching, backtracking): it may generate a branch summary (BranchSummaryEntry) and then moveTo the target node. It fires the session_before_tree and session_tree hooks around it, with the phase switching to branch_summary. Both require the harness to be idle — you can't modify the tree mid-conversation.

These two methods are the capability outlets of the "session tree" design. Because the transcript is a tree rather than an array, compaction is reversible and branching is free — the Harness merely wraps these low-level capabilities into two high-level operations with hooks and phase protection.

Why the Product Layer Did Not Use It

Now let's answer the sharp question: since AgentHarness provides such complete persistent orchestration, why doesn't pi-coding-agent use it, instead building its own 3,333-line AgentSession?

The answer lies in a mismatch of concerns. AgentHarness is a generic persistent orchestrator — it cares about session trees, compaction, hooks, built-in tools, skills. But the product layer needs far more than that:

  • Three operating modes (interactive TUI / print / RPC)
  • An extension system (~40 events; registering tools/commands/keybindings/flags)
  • Project trust decisions
  • Slash commands, model-switching UI, theming
  • Settings management, authentication, OAuth
  • HTML export, session sharing

These product-level concerns don't overlap with AgentHarness's generic orchestration concerns. If the product layer forced itself onto AgentHarness, it would either stuff product logic into harness hooks (polluting the generic layer) or wrap the harness in yet another layer (making the harness a redundant middleman).

So the product layer made a sober choice: sit directly on the core Agent and build its own orchestration. Recall sdk.ts:294 from Chapter 1: agent = new Agent({...}) — the product layer instantiates the core Agent, not AgentHarness. It reuses the core's loop and event stream, but handles product orchestration with its own AgentSession and persistence with its own SessionManager (JSONL).

This reveals the real intent behind the two-layer design inside pi-agent-core:

The core provides the mechanism (loop, event stream, tool execution, message bridging). AgentHarness is an official strategy — "if you want a persistent agent out of the box". AgentSession is the product layer's other strategy — "if you want to build a full CLI product". SDK users can entirely write their own strategy.

The core doesn't force anyone to choose between AgentHarness and AgentSession, because it doesn't even know the two exist — it only exposes mechanisms. This is the full meaning of "minimal core": the core is small enough to be reused by any orchestration strategy, including ones the maintainers never imagined.

Practical Takeaways

AgentHarness's relationship with the core offers four transferable patterns for designing extensible frameworks.

Separate mechanism from policy, and keep the mechanism ignorant of the policy. The core loop provides slots (mechanism); the Harness and the product each stuff their own logic into the slots (policy); the core knows nothing about the policies. The problem it solves: a framework welds one particular usage into the core, forcing every other usage to contort around it. When the core exposes only mechanism, policies can flourish — a generic Harness, a product Session, and custom SDK usages each get what they need.

Isolate the environment with dependency inversion. The tools' IO depends on the ExecutionEnv interface rather than node:fs, and every operation returns a Result instead of throwing. The problem it solves: business logic bound to one runtime, with try/catch scattered everywhere. When IO is an interface and failure is a Result, the same tools run in Node, remotely, or in containers, and execution logic stays straightforward.

Connect different abstraction layers with an adapter. createLoopConfig maps the core's few slots onto the Harness's rich hook system, in the direction "upper layer adapts to lower layer". The problem it solves: changing lower-layer interfaces to satisfy upper-layer needs, breaking the lower layer's stability. When the adaptation direction is right, the lower layer (core loop) stays stable for a long time while the upper layer (hook system) evolves freely.

Make changes take effect at safe points. Mid-run state modifications are buffered and flushed/take effect atomically at turn boundaries (prepareNextTurn) or at run end (turn_end). The problem it solves: mid-run modifications interleaving with in-flight work and producing inconsistent intermediate states. When changes have a well-defined effective moment, state consistency is guaranteed.

Summary

AgentHarness is the "fully-loaded" layer pi-agent-core provides on top of the minimal core: it inverts IO with ExecutionEnv, protects concurrency with the phase state machine, absorbs mid-run changes with per-turn snapshots, adapts core slots to 22 typed hooks via createLoopConfig, persists at safe points with a write buffer, and exposes the session tree's capabilities through compact()/navigateTree().

But its deepest lesson isn't in itself — it's in the fact that it was not used by the product. The core provides mechanism, AgentHarness is one strategy, and the product's AgentSession is another — the core, small enough to favor no strategy, can be reused by all of them. This is the full circle of the "minimal core" philosophy.
