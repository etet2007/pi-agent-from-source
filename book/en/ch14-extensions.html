Chapter 14: The Extension System — Extending the Minimal Core

A factory function, about 40 typed events, and four groups of registration surfaces — the core pushes every "do one more thing" need out to extensions

The Cost of Minimalism — and the Answer

By now you will have noticed that Pi Agent "lacks" quite a lot: no built-in per-tool permission approval, no MCP, no Claude Code's 27 runtime hooks. Chapter 1 called this "conservation of complexity" — those capabilities didn't disappear; they were pushed out of the core.

This chapter reveals where they were pushed: the extension system. This is the payoff of the minimalism philosophy. The core can stay minimal because almost every "I want the agent to do one more thing" need can be met by an extension, without touching the core. Tools, commands, shortcuts, CLI flags, message rendering, lifecycle interception — extensions can register all of it.

More importantly, Pi Agent's extensions are not runtime hook strings (hooks.on("PreToolUse", ...)), but a strongly typed TypeScript API. Behind this choice is careful thought about how extensibility and maintainability can coexist. This chapter dissects the system and answers the question that runs through the book: why would Pi Agent rather go without MCP, and still shape its extensibility the way it has?

What an Extension Looks Like

An extension is simply a factory function (packages/coding-agent/src/core/extensions/types.ts):

export type ExtensionFactory = (pi: ExtensionAPI) => void | Promise<void>;

It receives a pi object (the ExtensionAPI) and registers things on it. A minimal extension might look like:

export default function myExtension(pi: ExtensionAPI) {
	pi.registerTool({
		name: "hello",
		label: "hello",
		description: "Greet someone",
		parameters: Type.Object({ name: Type.String() }),
		async execute(_id, { name }) {
			return { content: [{ type: "text", text: `Hello, ${name}!` }], details: {} };
		},
	});
}

That's all there is to it. Drop it into the project's .pi/extensions/ directory, and pi will discover and load it at startup — the model now has one more tool, hello. No config file, no manifest, no registry: a TypeScript file exporting a factory function is an extension.

ExtensionAPI: ~40 Events and Registration Surfaces

ExtensionAPI (packages/coding-agent/src/core/extensions/types.ts:1193) is everything an extension can do. It falls into a few broad categories.

Event Subscription: on(...)

An extension can subscribe to about 40 events, each with a precisely typed payload and return value. on is a set of overloads:

export interface ExtensionAPI {
	// 会话生命周期
	on(event: "project_trust", handler: ProjectTrustHandler): void;
	on(event: "session_start", handler: ExtensionHandler<SessionStartEvent>): void;
	on(event: "session_before_switch", handler: ExtensionHandler<SessionBeforeSwitchEvent, SessionBeforeSwitchResult>): void;
	on(event: "session_before_fork", handler: ExtensionHandler<SessionBeforeForkEvent, SessionBeforeForkResult>): void;
	on(event: "session_before_compact", handler: ExtensionHandler<SessionBeforeCompactEvent, SessionBeforeCompactResult>): void;
	on(event: "session_shutdown", handler: ExtensionHandler<SessionShutdownEvent>): void;
	// 提供商层
	on(event: "context", handler: ExtensionHandler<ContextEvent, ContextEventResult>): void;
	on(event: "before_provider_request", handler: ExtensionHandler<BeforeProviderRequestEvent, BeforeProviderRequestEventResult>): void;
	on(event: "before_provider_headers", handler: ExtensionHandler<BeforeProviderHeadersEvent>): void;
	on(event: "after_provider_response", handler: ExtensionHandler<AfterProviderResponseEvent>): void;
	// Agent / 轮次 / 消息
	on(event: "before_agent_start", handler: ExtensionHandler<BeforeAgentStartEvent, BeforeAgentStartEventResult>): void;
	on(event: "agent_start", handler: ExtensionHandler<AgentStartEvent>): void;
	on(event: "turn_start", handler: ExtensionHandler<TurnStartEvent>): void;
	on(event: "message_end", handler: ExtensionHandler<MessageEndEvent, MessageEndEventResult>): void;
	// 工具
	on(event: "tool_call", handler: ExtensionHandler<ToolCallEvent, ToolCallEventResult>): void;
	on(event: "tool_result", handler: ExtensionHandler<ToolResultEvent, ToolResultEventResult>): void;
	// 输入
	on(event: "input", handler: ExtensionHandler<InputEvent, InputEventResult>): void;
	on(event: "user_bash", handler: ExtensionHandler<UserBashEvent, UserBashEventResult>): void;
	// ... 共约 40 种
}

Note the ExtensionHandler<Event, Result> generic: every event's payload type and return type are precisely constrained. When you subscribe to tool_call, your handler receives an event of type ToolCallEvent and returns a ToolCallEventResult (you can block the tool with { block: true, reason }). A wrong event name, payload field, or return type is a compile-time error.

This stands in stark contrast to runtime hook strings. Recall the AgentHarnessEventResultMap from the Harness in Chapter 6 — the product-layer extension system inherits that "typed extension" taste and takes it further. The ~40 events cover the whole lifecycle: sessions, providers, agents, turns, messages, tools, and input.

Many of these events are the productized exposure of seams we saw in earlier chapters:

  • context → the transformContext slot from Chapter 3
  • tool_call/tool_result → Chapter 4's beforeToolCall/afterToolCall
  • input → extension interception of the prompt() funnel in Chapter 9
  • before_provider_headers → the transformHeaders inside Chapter 8's streamFn
  • session_before_compact/session_before_tree → the compaction/fork hooks from Chapter 7

The core and the Harness provide the mechanisms (the slots); the product-layer extension system exposes those mechanisms to extensions as about 40 typed events. It is yet another instance of layering.

Tool Registration: registerTool

registerTool<TParams extends TSchema, TDetails, TState>(tool: ToolDefinition<TParams, TDetails, TState>): void;

Tools registered by extensions use the ToolDefinition from Chapter 4 — the rich interface with promptSnippet, promptGuidelines, renderCall, and renderResult. Custom tools thus get, for free: a place in the system prompt (snippet/guidelines, Chapter 10), rendering in the terminal (renderCall/renderResult, Chapter 12), and execution by the loop (Chapter 4). Internally, registerTool wraps the ToolDefinition into an AgentTool (wrapToolDefinition) and hands it to the core.

Custom tools and built-in tools are completely equal in the system — the model neither knows nor cares whether a tool is built in or registered by an extension. This is the ultimate payoff of the self-describing tool design: extension tools need no special handling.

Command, Shortcut, and Flag Registration

registerCommand(name: string, options: Omit<RegisteredCommand, "name" | "sourceInfo">): void;
registerShortcut(shortcut: KeyId, options: { description?; handler: (ctx) => void | Promise<void> }): void;
registerFlag(name: string, options: { description?; type: "boolean" | "string"; default? }): void;
getFlag(name: string): boolean | string | undefined;

Extensions can register:

  • Slash commands (registerCommand): join the / command surface from Chapter 10, alongside the 22 built-in commands.
  • Shortcuts (registerShortcut): the shortcut is the type-safe KeyId from Chapter 13, bound to a handler.
  • CLI flags (registerFlag): recall Chapter 8 — the core CLI collects unknown --flags into unknownFlags; an extension declares its own flags via registerFlag and reads them with getFlag. Extensions can thus own their command-line arguments.

These three registration surfaces let extensions hook into every interaction entry point of the product: commands, the keyboard, and the command line.

Rendering Registration

registerMessageRenderer<T>(customType: string, renderer: MessageRenderer<T>): void;
registerEntryRenderer<T>(customType: string, renderer: EntryRenderer<T>): void;
registerMarkdownTransformer(transformer: MarkdownTransformer): void;

Recall Chapter 5: AgentMessage can be extended with custom types via declaration merging. An extension can register custom message types and provide their renderers in the terminal via registerMessageRenderer/registerEntryRenderer (returning pi-tui components). registerMarkdownTransformer can transform the user's or assistant's Markdown before pi renders it.

Extensions can thus influence not just the agent's behavior but also its presentation — custom message types plus custom rendering let an extension add anything it wants to show into the transcript.

Actions: Cross-Process UI

ExtensionAPI also offers a set of "action" methods (excerpt): select, confirm, input, notify, widgets, and more. An extension can pop a selection box, ask for confirmation, request input, or send a notification.

In interactive mode these UI actions are rendered directly by the TUI. But in RPC mode (Chapter 11) they cross process boundaries through the extension_ui_request/extension_ui_response mechanism — the UI request is serialized and sent to the peer (the IDE), which renders it and sends the user's selection back. So the same extension can pop UI in both interactive and RPC modes; only the rendering location differs. This is the "event stream as contract" idea extended to extension UI.

Loading Extensions and Trust

Where do extensions come from? They are discovered by the ResourceLoader (Chapter 10), loaded by discoverAndLoadExtensions (packages/coding-agent/src/core/extensions/loader.ts), and run by the ExtensionRunner (runner.ts). Discovery locations include:

  • the project's .pi/extensions/
  • the user-global ~/.pi/extensions/
  • paths specified by the --extension/-e flag
  • built-in extensions (builtInExtensions)

Loading is gated by project trust (Chapter 1). This is a key point of the security model: extensions in a project directory come from potentially untrusted third-party repositories, and they can register tools, intercept events, and influence agent behavior — a huge attack surface. So before loading a project's extensions, pi asks: "Do you trust this project?" If not (--no-approve), it doesn't load its extensions.

Recall Chapter 1: Pi Agent has no per-tool approval and leaves isolation to containers. But the project-trust decision at extension loading is a concrete instance of its "check once at the boundary" model — no gate before every tool call, but one question before loading potentially malicious extensions. The project_trust event even lets extensions participate in that decision (ProjectTrustHandler).

--no-extensions disables extensions entirely, and --extension explicitly loads a specific one. Unknown flags are handed to extensions via unknownFlags (Chapter 8).

Built-in Extension: llama.cpp

The most interesting example is the built-in extension. packages/coding-agent/src/extensions/index.ts:

export const builtInExtensions: InlineExtension[] = [
	{ name: "llama.cpp", factory: llamaExtension, hidden: true },
];

Pi Agent made llama.cpp local model support an extension (src/extensions/llama/)! It includes provider.ts (registers a local model provider), client.ts (talks to the llama.cpp server), huggingface.ts (downloads models), and ui.ts (a model management UI).

This example perfectly illustrates the expressiveness of the extension system: even "adding a new LLM provider" can be an extension, without entering the core. Recall Chapter 2: providers are a core capability of pi-ai. But a provider like llama.cpp — niche, optional, requiring extra dependencies — lives in an extension, loaded on demand. The core's provider list stays lean; long-tail needs are carried by extensions.

hidden: true means it doesn't appear in the extension list (it's built in, so users don't manage it). Chapter 8's main() injects it via MainOptions.extensionFactories.

Skills, Templates, Themes: Lighter Extension Points

The extension system (TypeScript code) is the most powerful extension point, but not the only one. Several mechanisms introduced in Chapter 10 are lighter ways to extend:

Extension pointFormCapabilityBarrier
ExtensionTypeScript codeTools, events, commands, UI, providers... everythingHigh (requires code)
SkillsSKILL.md fileTask instructions for the modelLow (write Markdown)
Prompt templatesTemplate filesShortcuts for user promptsLow
ThemesJSON filesTerminal color schemeLow
Custom providersExtension + pi-ai APIConnect a new LLMMedium

This is a layered extension system: simple needs (adding a task instruction) use plain-text mechanisms like skills; complex needs (registering tools, intercepting events) use TypeScript extensions. Barrier scales with capability. A user doesn't need to write an extension to "add a rule for the model" — that's a skill's job.

This layering is itself an expression of the minimalism philosophy: the core doesn't build in a pile of complex "rule config" or "template config" mechanisms; instead it offers a graduated range of extension points, from plain text to code, so users can pick the lightest one that fits.

Why There Is No MCP

Now for that question: why doesn't Pi Agent support MCP (Model Context Protocol)?

MCP is a standardized "external tool protocol" — it defines how agents connect to external tool servers (8 transports, OAuth, tool wrapping). The everything-included route (Claude Code, for instance) builds MCP in, letting agents plug into the vast MCP tool ecosystem.

Pi Agent's choice: not built in, but implementable as an extension. Its reasoning:

  1. MCP is an optional, ecosystem-related capability; it doesn't belong in the "minimal core".
  2. The extension system is powerful enough that one could write an extension that "connects to an MCP server and registers MCP tools as pi tools" (using registerTool plus an MCP client).
  3. Building MCP in would suck the complexity of 8 transports, OAuth, and protocol version management into the core — against the minimalism principle.

So Pi Agent turned "whether to support MCP" into an extension decision rather than a core decision. Users who want MCP install an MCP extension; users who don't have no such code in the core at all.

This is the same logic as "llama.cpp as an extension" in Chapter 2: long-tail, optional, ecosystem-related capabilities go to extensions; the core keeps only what is universal and necessary. That is the fundamental way a minimal core stays minimal — not by refusing to do these things, but by making them pluggable edges.

Of course, this choice has a cost: out of the box, Pi Agent doesn't reach the MCP ecosystem as conveniently as a built-in-MCP approach would; it relies on the community to provide extensions. This is the trade-off between "minimalism" and "works out of the box", and Pi Agent has explicitly chosen the former.

Practical Takeaways

Pi Agent's extension system offers four transferable patterns for designing extensible systems.

Extensibility via a typed API, not hook strings. Extensions face a strongly typed ExtensionAPI; the payloads and return values of the ~40 events have precise types, so mistakes fail at compile time. The problem it solves: runtime hook strings (event names, payload shapes) only surface errors at runtime, with no autocompletion. When the extension surface is typed, extension development gains compile-time safety and IDE support, and maintainability improves dramatically.

Extensions and built-ins are equal in the system. Tools registered by extensions use the same ToolDefinition and are treated identically to built-in tools; even adding a provider can be an extension. The problem it solves: extensions as "second-class citizens", with limited capabilities or special paths. When extensions and built-ins run through the same mechanism, extension expressiveness has no artificial ceiling, and the core needs no special cases.

Layered extension points, where barrier scales with capability. Plain-text skills/templates/themes serve simple needs; TypeScript extensions serve complex ones. The problem it solves: a single heavyweight extension mechanism, so even "adding a rule" requires code. When extension points are layered from light to heavy, users can always pick the lightest one, and the core doesn't need to build in configuration machinery.

Push optional ecosystem capabilities out into extensions. Optional, ecosystem-related capabilities like MCP and llama.cpp stay out of the core and are carried by extensions. The problem it solves: a core held hostage by long-tail needs, growing ever more bloated. When the core keeps only universal necessities and hands the long tail to pluggable extensions, it can stay minimal for the long run — this is "conservation of complexity" realized along the extension dimension.

Summary

Pi Agent's extension system is the payoff of the minimalism philosophy: the core stays minimal because almost every "do one more thing" need can be satisfied by an extension. An extension is a factory function (pi: ExtensionAPI) => void; ExtensionAPI provides about 40 typed event subscriptions, tool/command/shortcut/flag registration, custom message rendering, and cross-process UI actions. Extension loading is gated by project trust — the point where the "check once at the boundary" security model lands. The built-in llama.cpp extension proves that even "adding a provider" can be an extension; skills/templates/themes are lighter extension points.

It has no MCP and no runtime hook strings — not a deficiency but a choice: optional ecosystem capabilities like MCP are left to extensions, and extensibility itself is expressed through a strongly typed API rather than string hooks. Understand this, and you understand how Pi Agent, without building everything in, still commands nearly unbounded extensibility.
