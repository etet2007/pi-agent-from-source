Chapter 2: Talking to Models — The pi-ai Unified LLM Layer

How to make roughly 38 LLM providers look like one: few protocols, many endpoints

An Underappreciated Problem

On the surface, "calling a large model" is simple: send an HTTP request, read a streaming response. But when you need to support OpenAI, Anthropic, Google, AWS Bedrock, Google Vertex, OpenRouter, Groq, xAI, DeepSeek… roughly 38 providers at once, the simple thing becomes tricky. Each provider has its own:

  • request format (how messages are represented, how tools are declared, how thinking is toggled)
  • streaming protocol (SSE event names, chunk structure, termination signals)
  • authentication (API key, OAuth, AWS credentials, ADC files, environment variables)
  • usage and billing semantics (cache reads/writes, reasoning tokens, tiered pricing)
  • error semantics (which errors warrant a retry, which are permanent failures)

If you wrote an end-to-end adapter for every provider, you'd end up with 38 subtly different implementations, and every new vendor would be a copy-paste disaster. pi-ai (packages/ai) exists to eliminate that duplication. Its package.json self-description reads:

Unified LLM API with automatic model discovery and provider configuration.

This chapter dissects how it pulls that off. At the core is a duality: protocols are few, endpoints are many.

The Core Duality: Api and Provider

pi-ai splits "talking to models" into two orthogonal concepts. This is the organizing principle for understanding the entire package.

Api (wire protocol) answers "how to talk to a family of servers." It lives in packages/ai/src/api/*.ts, about 10 of them: openai-completions, openai-responses, openai-codex-responses, azure-openai-responses, anthropic-messages, bedrock-converse-stream, google-generative-ai, google-vertex, mistral-conversations, pi-messages.

Provider (a configured endpoint) answers "which concrete service to connect to." It lives in packages/ai/src/providers/*.ts, roughly 38 of them. A Provider carries an id, a baseUrl, auth configuration, a model catalog, and bindings to one or more Apis.

The key reuse: many Providers speak the same dialect. OpenRouter, Groq, and Together all speak openai-completions/openai-responses. So about 10 protocol adapters unify roughly 38 vendors. To add a provider that "speaks the OpenAI dialect," you barely touch any protocol code — you just write a factory function and a model catalog.

A unified request input: Context

No matter the provider, the loop feeds pi-ai the same Context (packages/ai/src/types.ts):

export interface Context {
	systemPrompt?: string;
	messages: Message[];
	tools?: Tool[];
}

Message is a union type (UserMessage | AssistantMessage | ToolResultMessage) whose content blocks are normalized into TextContent, ThinkingContent, ImageContent, and ToolCall. Each provider's Api adapter is responsible for translating this unified representation into its own wire format — you'll see the translation details in the second half of this chapter.

A unified output: AssistantMessage and Usage

Every provider's response is folded into the same AssistantMessage, which carries normalized usage and cost (packages/ai/src/types.ts):

export interface Usage {
	input: number;
	output: number;
	cacheRead: number;
	cacheWrite: number;
	cacheWrite1h?: number; // 仅 Anthropic 报告 1h 缓存写入的细分
	reasoning?: number; // reasoning/thinking token，是 output 的子集
	totalTokens: number;
	cost: {
		input: number;
		output: number;
		cacheRead: number;
		cacheWrite: number;
		total: number;
	};
}

export type StopReason = "pending" | "stop" | "length" | "toolUse" | "error" | "aborted";

Note how Usage folds "cache reads/writes," "reasoning tokens," and "cost" into one unified accounting. This means the usage numbers upper layers (the Agent loop, product UI, evals) receive are comparable across providers — you don't need to know whether a call went to Anthropic or Groq to display token counts and spend correctly. calculateCost(model, usage) (packages/ai/src/models.ts) computes cost from a model's rates ($/M tokens) and tiered pricing, with a special case billing Anthropic's 1h cache writes at 2×.

Normalizing StopReason is equally critical. Anthropic's end_turn, OpenAI's stop, and the various "reached a limit" and "tool triggered" signals are all mapped onto one of these six values. Recall from Chapter 1: the core loop only checks stopReason === "error" | "aborted" to handle failures and checks toolUse to decide whether to continue — it can be this concise precisely because pi-ai has already translated every vendor's dialect into this unified vocabulary.

Provider and Models: Two Factories

The Provider interface

A Provider's shape (packages/ai/src/models.ts):

export interface Provider<TApi extends Api = Api> {
	readonly id: string;
	readonly name: string;
	readonly baseUrl?: string;
	readonly headers?: ProviderHeaders;
	readonly auth: ProviderAuth;
	getModels(): readonly Model<TApi>[];
	refreshModels?(context: RefreshModelsContext): Promise<void>;
	filterModels?(models, credential): readonly Model<TApi>[];
	stream<T extends TApi>(model, context, options?): AssistantMessageEventStream;
	streamSimple(model, context, options?): AssistantMessageEventStream;
}

Providers are built by the factory function createProvider(input). The factory's core responsibility is API dispatch: the api parameter can be a single ProviderStreams, or a map keyed by model.api (when a provider speaks multiple dialects); apiFor(model) selects the right implementation, and if a model's api has no matching entry, dispatch(...) produces a streaming error.

ProviderStreams: the uniform shape of every protocol module

Every src/api/*.ts module satisfies the same interface (packages/ai/src/types.ts):

export interface ProviderStreams {
	stream(model: Model<Api>, context: Context, options?: StreamOptions): AssistantMessageEventStream;
	streamSimple(model: Model<Api>, context: Context, options?: SimpleStreamOptions): AssistantMessageEventStream;
}

stream is the full-featured version (exposing provider-specific options), while streamSimple is the minimal one (it's what the Agent loop uses). The module itself is the implementation of this interface — anthropic-messages.ts exports stream and streamSimple, which directly satisfy ProviderStreams. This "module-as-interface" convention lets protocol adapters be passed around as values and lazily wrapped.

Models: the collection of providers

Models (built by createModels(), packages/ai/src/models.ts) holds a Map of providers and is responsible for auth resolution and dispatch. Models.stream() looks up the provider that owns a model, applies auth/headers/environment variables, then calls provider.stream(...). complete() is just a convenience wrapper around stream(...).result(). builtinModels() (packages/ai/src/providers/all.ts) registers all built-in providers.

EventStream: the streaming primitive running through the stack

pi-ai's streaming responses aren't callbacks, nor RxJS-style Observables, but a minimal async-iterable primitive called EventStream (packages/ai/src/utils/event-stream.ts). It is the cornerstone of streaming throughout the whole system, and worth seeing in full:

export class EventStream<T, R = T> implements AsyncIterable<T> {
	private queue: T[] = [];
	private waiting: ((value: IteratorResult<T>) => void)[] = [];
	private done = false;
	private finalResultPromise: Promise<R>;
	private resolveFinalResult!: (result: R) => void;
	private isComplete: (event: T) => boolean;
	private extractResult: (event: T) => R;

	constructor(isComplete: (event: T) => boolean, extractResult: (event: T) => R) {
		this.isComplete = isComplete;
		this.extractResult = extractResult;
		this.finalResultPromise = new Promise((resolve) => {
			this.resolveFinalResult = resolve;
		});
	}

	push(event: T): void {
		if (this.done) return;
		if (this.isComplete(event)) {
			this.done = true;
			this.resolveFinalResult(this.extractResult(event));
		}
		const waiter = this.waiting.shift();
		if (waiter) waiter({ value: event, done: false });
		else this.queue.push(event);
	}

	async *[Symbol.asyncIterator](): AsyncIterator<T> {
		while (true) {
			if (this.queue.length > 0) yield this.queue.shift()!;
			else if (this.done) return;
			else {
				const result = await new Promise<IteratorResult<T>>((resolve) => this.waiting.push(resolve));
				if (result.done) return;
				yield result.value;
			}
		}
	}

	result(): Promise<R> {
		return this.finalResultPromise;
	}
}

This class does exactly one thing: decouple "producer pushes events" from "consumer pulls events." Internally it's a queue plus a list of waiters — if a consumer is waiting, push delivers directly; otherwise it enqueues. It offers two ways to consume:

  • for await (const event of stream) — process incremental events one by one (this is what the TUI's incremental rendering uses)
  • await stream.result() — grab the final result directly (complete() and the loop's final message use this)

AssistantMessageEventStream is its specialization: completion is an event of type done or error, and the result extractor pulls the AssistantMessage out of done, or the error-carrying AssistantMessage out of error:

export class AssistantMessageEventStream extends EventStream<AssistantMessageEvent, AssistantMessage> {
	constructor() {
		super(
			(event) => event.type === "done" || event.type === "error",
			(event) => {
				if (event.type === "done") return event.message;
				else if (event.type === "error") return event.error;
				throw new Error("Unexpected event type for final result");
			},
		);
	}
}

This is where the "failures are encoded into the stream" convention from Chapter 1 lives: an error event is not an exception but a legitimate terminal event of the stream, whose payload is an AssistantMessage with stopReason: "error". result() still resolves normally on error (resolving to that error message) instead of rejecting. That's why upper layers never need to try/catch model calls.

The event protocol itself is a discriminated union, AssistantMessageEvent: start, text_start/delta/end, thinking_start/delta/end, toolcall_start/delta/end, done, error. Each provider's adapter translates its native streaming events into this unified event vocabulary.

Streaming Parsing: Handwritten SSE and SDK Iterators

With the unified event protocol established, each Api adapter's job is to translate the provider's native stream into it. Two styles exist here, and the contrast is instructive.

Handwritten SSE: Anthropic

The Anthropic adapter (packages/ai/src/api/anthropic-messages.ts) is a model of hand-rolled SSE. Instead of relying on the SDK's streaming wrapper, it grabs the raw ReadableStream of the Response and parses server-sent events itself:

async function* iterateSseMessages(
	body: ReadableStream<Uint8Array>,
	signal?: AbortSignal,
): AsyncGenerator<ServerSentEvent>

function decodeSseLine(line: string, state: SseDecoderState): ServerSentEvent | null

async function* iterateAnthropicEvents(
	response: Response,
	signal?: AbortSignal,
): AsyncGenerator<RawMessageStreamEvent>

iterateSseMessages reads chunks with body.getReader(), decodes them with TextDecoder({ stream: true }) (correctly handling multi-byte characters that span chunks), splits into lines (consumeLine/nextLineBreakIndex handle all three of \r, \n, and \r\n), and reassembles SSE's event:/data: frames. iterateAnthropicEvents filters for Anthropic's event types, parses each data with parseJsonWithRepair, throws on event: error, and verifies that every message_start has a matching message_stop.

Then the main stream function folds these raw events into the unified AssistantMessage: message_start seeds usage; content_block_start/delta/stop build up the text/thinking/toolCall blocks (tool arguments accumulate as partialJson, incrementally parsed with parseStreamingJson); message_delta updates stopReason (via mapStopReason) and the final usage.

Notably, the request itself still goes through the official SDK, but is forced to return the raw Response:

client.messages.create({ ...params, stream: true }, { maxRetries: 0 }).asResponse()

maxRetries: 0 is deliberate — retries are taken over uniformly by pi-ai's own retryProviderRequest(...) (see below), because the official SDK's retries don't respect AbortSignal.

SDK iterators: the OpenAI family

The OpenAI family's adapter (packages/ai/src/api/openai-completions.ts) takes the other route — it uses the official SDK's async iterator directly:

const response = await retryProviderRequest(
	() => client.chat.completions.create(params, requestOptions).withResponse(),
	...,
);
// ...
for await (const chunk of openaiStream) {
	// 把每个 chunk 翻译成统一的 AssistantMessageEvent
}

Google, Mistral, Bedrock, and OpenAI Responses all follow the same module pattern (stream + streamSimple), each mapping native events onto the shared AssistantMessageEvent protocol.

The two styles each have tradeoffs: handwritten SSE gives you full control (incremental JSON repair, precise termination validation) but you handle the protocol details yourself; SDK iterators save effort, but you're constrained by the SDK's behavior. pi-ai lets each protocol choose for itself — pragmatic minimalism in its own right: implementation means aren't forced to be uniform, only the outward contract is.

Lazy loading: keeping heavy SDKs out of startup

Every src/api/*.ts has a companion *.lazy.ts. lazyApi(load) (packages/ai/src/api/lazy.ts) wraps a dynamically import()ed protocol module as a ProviderStreams, so heavy SDKs (like @anthropic-ai/sdk) are only loaded the first time they're actually used:

export function lazyApi(load: () => Promise<ProviderStreams>): ProviderStreams

lazyStream(model, setup) synchronously returns an AssistantMessageEventStream while running setup asynchronously behind it (auth, dynamic import), forwarding internal events via forwardStream and converting a setup failure into an error event. This is "failures are encoded into the stream" once again — even "failed to load the protocol module" isn't an exception, but a stream event.

Lazy loading is critical to startup speed. Starting the pi command doesn't require loading the SDKs of all 10 protocols — only the one you actually use. Chapter 8 will show how the bootstrap pipeline benefits from this design.

Adding a Provider: Three Files

The quality of an abstraction shows in how much code adding a new provider requires. The answer here: one factory file + one model catalog file + one line in the registry.

The factory (packages/ai/src/providers/anthropic.ts is the minimal template):

export function anthropicProvider(): Provider<"anthropic-messages"> {
	return createProvider({
		id: "anthropic",
		name: "Anthropic",
		baseUrl: "https://api.anthropic.com",
		auth: {
			apiKey: anthropicApiKeyAuth(),
			oauth: lazyOAuth({ name: "Anthropic (Claude Pro/Max)", load: loadAnthropicOAuth }),
		},
		models: Object.values(ANTHROPIC_MODELS),
		api: anthropicMessagesApi(), // 来自 ../api/anthropic-messages.lazy.ts
	});
}

The auth.apiKey.resolve() callback is where environment variables/credentials get translated into { apiKey } or { headers }. A provider speaking multiple dialects instead passes an api map keyed by model.api.

The model catalog (packages/ai/src/providers/anthropic.models.ts):

import values from "./data/anthropic.json" with { type: "json" };
import { flattenModelCatalog, type ModelCatalog } from "../model-catalog.ts";

export const ANTHROPIC_MODELS: ModelCatalog<typeof values, "anthropic"> =
	flattenModelCatalog("anthropic", values);

flattenModelCatalog (packages/ai/src/model-catalog.ts) merges the per-API-grouped JSON into a flat { [modelId]: Model } map while preserving strong typing.

Registration (packages/ai/src/providers/all.ts): builtinProviders() instantiates the factories, and builtinModels() registers them into Models.

That's all there is. If the provider you're adding speaks an existing dialect (say, yet another OpenAI-compatible service), you don't even need to write any protocol code.

Model Metadata: Generated from models.dev

Each model's metadata (context window, max tokens, pricing, reasoning capability, input modalities) isn't handwritten — it's generated. The header of packages/ai/src/models.generated.ts reads:

Do not edit manually - run 'npm run generate-models'.

The generator packages/ai/scripts/generate-models.ts takes its primary data source from the models.dev API:

await fetch("https://models.dev/api.json")

It also queries live provider endpoints (the models APIs of NVIDIA, OpenRouter, AI-Gateway), maps ModelsDevModel (cost, limits, modalities, reasoning_options) into the internal Model shape, applies extensive per-provider manual corrections (long comments in the source document where models.dev data disagrees with reality), and finally writes out each provider's data/<id>.json plus the aggregated models.generated.ts.

The Model record (packages/ai/src/types.ts) is the unified model metadata: id, name, api, provider, baseUrl, reasoning, thinkingLevelMap?, input: ("text"|"image")[], cost: ModelCost, contextWindow, maxTokens, headers?, compat?. The compat field is a conditional type that selects OpenAICompletionsCompat / AnthropicMessagesCompat / BedrockCompat etc. by api — these flag sets are where an individual Api adapter absorbs vendor quirks (like thinkingFormat, supportsStrictMode, cacheControlFormat).

The value of this mechanism: the model catalog is data, not code. When a provider releases a new model or adjusts pricing, the update comes from a data refresh — not from changing code, passing review, and shipping a release. AGENTS.md even has a dedicated rule: never hand-edit models.generated.ts; edit generate-models.ts and regenerate instead.

Cross-Provider Normalization of Tool Calls

Tools are the heart of an Agent, and every provider declares tools and returns tool calls in a different format. pi-ai normalizes in both directions.

The unified tool input is Tool { name; description; parameters: TSchema; constrainedSampling? } (a TypeBox schema), the unified tool call is ToolCall, and the result is ToolResultMessage. Every Api adapter converts in both directions:

  • Anthropic: convertTools(...) builds input_schema ({ type: "object", properties, required }), adding strict/eager_input_streaming/cache_control per compat flags; convertMessages(...) handles thinking blocks and tool_use, and merges consecutive toolResults into one user turn carrying a tool_result block; normalizeToolCallId(id) scrubs ids to the character set Anthropic allows (id.replace(/[^a-zA-Z0-9_-]/g, "_").slice(0, 64)).
  • OpenAI: convertTools(...) emits { type: "function", function: {...} }; convertMessages(...) handles OpenAI's message/tool-call/tool-result shapes.

The shared normalization lives in packages/ai/src/api/transform-messages.ts: transformMessages(messages, model, normalizeToolCallId) runs before provider-specific conversion, and includes downgradeUnsupportedImages (replacing images with placeholder text when a model's input doesn't include "image") plus tool-call id normalization. constrained-sampling.ts maps the unified constrainedSampling config onto a provider's strict/grammar behavior.

One interesting detail: the Anthropic adapter has toClaudeCodeName/fromClaudeCodeName, which remap tool names to Claude Code's canonical casing when using OAuth tokens. This exists to match what Anthropic's server expects for certain tool names — a real, production-sourced quirk.

Error Handling: Two Layers of Retry

pi-ai's retries are split into two layers, each owning its own slice.

Layer one: transport/SDK retries (packages/ai/src/utils/provider-retry.ts):

export async function retryProviderRequest<T>(
	request: () => Promise<T>,
	options: ProviderRetryOptions = {},
): Promise<T>

It replicates the OpenAI/Anthropic SDKs' backoff logic, but makes the sleep interruptible by AbortSignal (the official SDKs ignore the signal, so the adapters call the SDK with maxRetries: 0 and wrap this layer around it). isRetryableProviderError honors the x-should-retry header and retries 408/409/429/5xx; getRetryDelayMs reads retry-after-ms/retry-after first, then falls back to exponential backoff with jitter; delays beyond maxRetryDelayMs (default 60s) fail fast.

Layer two: assistant-level retries (packages/ai/src/utils/retry.ts):

export async function retryAssistantCall(
	produce: () => Promise<AssistantMessage>,
	policy: RetryPolicy | undefined,
	signal: AbortSignal | undefined,
	callbacks?: RetryCallbacks,
): Promise<AssistantMessage>

export function isRetryableAssistantError(message: AssistantMessage): boolean

This layer works at the AssistantMessage level. isRetryableAssistantError classifies with two regex sets: RETRYABLE_PROVIDER_ERROR_PATTERN (overloaded, rate-limited, 429/5xx, network/socket/timeout, stream ending early, gRPC ResourceExhausted, etc.) minus NON_RETRYABLE_PROVIDER_LIMIT_ERROR_PATTERN (quota/billing/budget exhausted, like insufficient_quota). The subtraction is key: an exhausted quota shouldn't be retried (retrying would just waste time), while a transient overload should be.

The division of labor between the two layers: the transport layer handles "the HTTP request itself failed," while the assistant layer handles "the request succeeded but the model returned a response indicating a transient problem." And every failure that never recovers is, by contract, encoded into the stream's error event — upper layers always see just a message with stopReason: "error".

Token estimation

packages/ai/src/utils/estimate.ts provides heuristic token estimation (CHARS_PER_TOKEN = 4, ESTIMATED_IMAGE_CHARS = 4800):

export function estimateContextTokens(context: Context | readonly Message[]): ContextUsageEstimate

The clever part: it anchors on the authoritative usage the API reported in the most recent assistant response, and only estimates the messages added after that anchor (getLastAssistantUsageInfo). Estimation error is thus bounded to "what was added in the most recent round" instead of accumulating over the whole conversation. Real token counts come from the provider's usage; estimation only kicks in as a fallback when no authoritative number exists. Chapter 7's context compaction will lean on this function heavily.

Restraint at the Public Entry Point

pi-ai's main entry, packages/ai/src/index.ts, is deliberately minimal and side-effect free — it only re-exports types and core helper functions, and does not export provider factories or the generated model catalog. Those live behind subpath exports: @earendil-works/pi-ai/providers/*, /api/*, /compat.

This means merely import { ... } from "@earendil-works/pi-ai" won't trigger loading any provider SDK. Combined with lazy loading, pi-ai carries "pay only for what you use" all the way down to the module-system level: you load only what you use.

Practical Takeaways

pi-ai offers four transferable patterns for "how to unify multiple external services," applicable to any system that must adapt many third-party APIs.

Separate "protocols" from "endpoints." Identify the few "dialects" (protocols) your vendors share and write one adapter per dialect; model each concrete vendor as "endpoint = config + protocol binding." The problem it solves: N vendors × M capabilities = N×M adapter implementations. When protocols are few and endpoints are many, the amount of adapter code drops from multiplicative to additive.

Unify the usage and termination vocabulary. Normalize each vendor's token accounting, cache semantics, and stop reasons into a single Usage and StopReason. The problem it solves: upper-layer logic being forced to know every provider's quirks. When StopReason has only six values, the loop's stop decision collapses into a single field comparison.

Failure is data, not an exception. Use EventStream to encode errors as a terminal event of the stream, letting result() resolve normally even on error. The problem it solves: try/catch scattered through async streaming pipelines and consumers not knowing when to disconnect. When failure is a payload, error handling collapses into "check the type of the terminal event."

Catalogs are data, not code. Make frequently changing, externally sourced information (model lists, pricing) a generated artifact refreshed from an authoritative data source, rather than handwritten code. The problem it solves: changes in the outside world being forced through the code-release pipeline. When the model catalog is an output of generate-models.ts, updating pricing is a data refresh, not a code review.

Summary

pi-ai is the foundation of the whole system, answering one question: how do you make roughly 38 LLM providers look like one? The answer is a two-level Api/Provider abstraction — about 10 protocol adapters unify roughly 38 endpoints speaking a handful of dialects. A unified Context goes in; a unified AssistantMessage (with normalized Usage and StopReason) comes out; and in between, EventStream — an async-iterable primitive — carries both streaming and failure.

It also models a restrained engineering taste: lazy loading keeps heavy SDKs out of startup, the model catalog is a generated artifact rather than handwritten code, retries are split into two layers each owning a slice, and the public entry point introduces no side effects. Together these choices serve one goal — giving the upper layers (the Agent loop) a simple, unified, never-throwing model interface.
