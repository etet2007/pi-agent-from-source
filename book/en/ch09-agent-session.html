Chapter 9: AgentSession – The Central Orchestrator

The heart of the product layer: how a line of input passes through extension interception, skill expansion, queueing, and validation before it reaches the core loop

The Heart of the Product Layer

In Chapter 8 we saw that the three operating modes share a single runtime. At the core of this runtime is one object: AgentSession (packages/coding-agent/src/core/agent-session.ts, 3,333 lines). It is the heart of the product layer – every mode drives the conversation through it, and every product-level concern converges here.

Recall the key conclusion of Chapter 6: the product layer does not use pi-agent-core's AgentHarness; it builds its own orchestration. AgentSession is that self-built orchestrator. Sitting on top of the core Agent, it translates the pristine AgentEvent stream of Chapter 3 into a much richer product-level event stream, and expands the act of "the user typed a line" into a chain of product logic – extension interception, skill expansion, template substitution, model validation, auth checks, compaction decisions.

This chapter dissects this orchestrator. By the end you will understand why a "minimal core" does not mean a "simple product": the core can be small, but a complete CLI product still has just as much to handle – it is simply that all of it lives outside the core.

What It Wraps

AgentSession is built from an AgentSessionConfig (packages/coding-agent/src/core/agent-session.ts):

export interface AgentSessionConfig {
	agent: Agent;                  // 核心 Agent（第 5 章）
	sessionManager: SessionManager; // JSONL 会话持久化（第 5 章）
	settingsManager: SettingsManager; // 设置
	cwd: string;
	scopedModels?: Array<{ model: Model<any>; thinkingLevel?: ThinkingLevel }>; // Ctrl+P 循环的模型
	resourceLoader: ResourceLoader; // 扩展/skills/模板/主题/上下文文件
	customTools?: ToolDefinition[]; // SDK 注册的自定义工具
	modelRuntime: ModelRuntime;     // pi-ai 的模型运行时
	// ...
}

This configuration list reveals AgentSession's "convergence" role: it holds the core Agent, session management, settings, the model runtime, the resource loader, and custom tools. Components from different packages and subsystems are assembled here into a usable product.

At construction time, AgentSession subscribes to the core Agent's event stream:

this._unsubscribeAgent = this.agent.subscribe(this._handleAgentEvent);

This is the junction of the two event systems. The core Agent emits AgentEvent (the ten kinds from Chapter 3); AgentSession._handleAgentEvent receives them, performs product-level processing (persistence, state updates), and translates them into AgentSessionEvent distributed to the modes' subscribers.

AgentSessionEvent: A Richer Vocabulary

The core AgentEvent has only ten event kinds, enough to describe "what the loop is doing". But the product needs more – compaction started, retry scheduled, session renamed, thinking level changed. AgentSessionEvent (packages/coding-agent/src/core/agent-session.ts) extends AgentEvent with these product-level events:

export type AgentSessionEvent =
	// 继承核心的大部分事件
	| Exclude<AgentEvent, { type: "agent_end" }>
	// agent_end 被增强：多了 willRetry
	| { type: "agent_end"; messages: AgentMessage[]; willRetry: boolean }
	// 产品级事件：
	| { type: "agent_settled" }
	| { type: "queue_update"; steering: readonly string[]; followUp: readonly string[] }
	| { type: "compaction_start"; reason: "manual" | "threshold" | "overflow" }
	| { type: "compaction_end"; reason: ...; result: CompactionResult | undefined; aborted: boolean; willRetry: boolean; errorMessage?: string }
	| { type: "entry_appended"; entry: SessionEntry }
	| { type: "session_info_changed"; name: string | undefined }
	| { type: "thinking_level_changed"; level: ThinkingLevel }
	| { type: "auto_retry_start"; attempt: number; maxAttempts: number; delayMs: number; errorMessage: string }
	| { type: "auto_retry_end"; success: boolean; attempt: number; finalError?: string }
	| { type: "summarization_retry_scheduled"; ... }
	| { type: "bash_execution_update"; id?: string; delta: string };

Notice a few design choices.

agent_end is enhanced. The core's agent_end carries only messages. The product version adds willRetry – telling the UI "this turn is over, but an automatic retry is coming". The UI can then show "Error, retrying in 3 seconds" instead of "Done".

Compaction has a complete event pair. compaction_start/compaction_end carry a reason (manual/threshold/overflow – manual, threshold reached, overflow recovery), letting the UI distinguish "user-initiated compaction" from "automatic system compaction" and show progress.

Retries are visible. auto_retry_start/auto_retry_end expose Chapter 2's pi-ai two-layer retry to the UI. Users can see "request failed, retrying 2/3".

queue_update exposes queue state. Emitted when the contents of the steering/followUp queues change, letting the UI show "2 messages queued".

This is a clear "event translation" pattern: the core provides fine-grained loop events, and the product aggregates them into high-level events meaningful to users. The modes (TUI/print/RPC) subscribe to AgentSessionEvent and never need to care about the details of the core AgentEvent.

prompt(): The Lifecycle of One Turn

AgentSession.prompt() (packages/coding-agent/src/core/agent-session.ts:1114) is the most central method of the product layer. When the user types a line and presses Enter, it ultimately lands here. It expands "a line of text" into a chain of product logic:

Step by step (key code excerpts):

1. Extension commands first. If the text starts with /, try executing it as an extension command first:

if (expandPromptTemplates && text.startsWith("/")) {
	const handled = await this._tryExecuteExtensionCommand(text);
	if (handled) {
		preflightResult?.(true);
		return; // 扩展命令已执行，没有提示词要发
	}
}

Extension commands (Chapter 14) manage their own LLM interaction and do not go through the normal prompt path. Note that they execute immediately even during streaming – extension commands are control instructions and should not be queued.

2. Extensions intercept input. An input event is emitted to extensions, which can "handle" (handled) or "transform" (transform) the input:

if (this._extensionRunner.hasHandlers("input")) {
	const inputResult = await this._extensionRunner.emitInput(currentText, currentImages, options?.source ?? "interactive", ...);
	if (inputResult.action === "handled") { preflightResult?.(true); return; }
	if (inputResult.action === "transform") {
		currentText = inputResult.text;
		currentImages = inputResult.images ?? currentImages;
	}
}

This is the main hook for extensions to intervene in user input – for example, an extension could intercept something like !ls and handle it itself, or apply some preprocessing to the input text.

3. Expand skills and templates. Expand /skill:name args and /template args into actual text:

let expandedText = currentText;
if (expandPromptTemplates) {
	expandedText = this._expandSkillCommand(expandedText);
	expandedText = expandPromptTemplate(expandedText, [...this.promptTemplates]);
}

Skills and prompt templates (Chapter 10) are "reusable prompt fragments". A user typing /review may have it expanded into a full code-review prompt.

4. Queue during streaming. If the agent is working (isStreaming), a new message cannot be sent directly – it must be queued:

if (this.isStreaming) {
	if (!options?.streamingBehavior) {
		throw new Error("Agent is already processing. Specify streamingBehavior ('steer' or 'followUp') to queue the message.");
	}
	if (options.streamingBehavior === "followUp") await this._queueFollowUp(expandedText, currentImages);
	else await this._queueSteer(expandedText, currentImages);
	preflightResult?.(true);
	return;
}

Recall from Chapters 3 and 5: steering is "interjecting while working", followUp is "say it when you're done". streamingBehavior makes the caller choose explicitly. If it is not specified, an error is thrown – a "force explicit intent" design that keeps user messages from being silently dropped or misqueued. _queueSteer/_queueFollowUp ultimately call the core Agent's steer()/followUp() (the two queues of Chapter 5).

5–7. Flush, validate, compact. Flush pending bash messages, verify a model is selected and auth is valid (an expired OAuth token prompts /login), then _checkCompaction checks whether the previous turn's response triggered a compaction condition:

const lastAssistant = this._findLastAssistantMessage();
if (lastAssistant) {
	await this._checkCompaction(lastAssistant, false);
}

_checkCompaction (:1953) uses Chapter 7's shouldCompact to decide, triggering compaction when needed. It checks before the prompt in order to catch "an aborted response from the previous turn" – if the previous response was aborted mid-way, the token count may be inaccurate, so this is a re-evaluation.

8. Build the message and drive the core. Finally, build the messages array (user message + optional images) and call this.agent.prompt(messages) – handing control back to the core Agent and entering Chapter 3's loop.

The whole prompt() is a "product-logic funnel": the user's raw input passes through extension interception, skill expansion, template substitution, queue decisions, model validation, auth checks, and compaction decisions, finally becoming a clean user message fed to the core loop. The core loop knows nothing about this product logic – it only receives a message.

Model and Thinking Management

AgentSession also manages "which model, and how deep the thinking". This is a product-level concern – the core Agent has just one model field, but the product must support runtime switching, cycling, and a UI selector.

get model();
get thinkingLevel();
async setModel(model: Model<any>): Promise<void>;       // :1578
async cycleModel(direction): Promise<void>;
setThinkingLevel(level): void;
cycleThinkingLevel(): void;

scopedModels (from the --models flag) defines the set of models that can be cycled through. In interactive mode, pressing Ctrl+P calls cycleModel, rotating among these models – each switch takes effect at a turn boundary via prepareNextTurn (Chapter 3) and fires a thinking_level_changed/model-change event, persisted as a ModelChangeEntry in the session tree (Chapter 5). So "I switched to a stronger model at turn 5" becomes part of the session history.

setModel is not merely changing a field – it must update the core Agent's state, persist the model change, notify subscribers, and possibly re-resolve auth. All this orchestration lives in AgentSession; the core Agent still only knows "my model changed".

Compaction and Session Tree Operations

AgentSession exposes Chapter 7's compaction and Chapter 5's session-tree operations as product methods:

async compact(customInstructions?: string): Promise<CompactionResult>; // :1783 手动压缩
get isCompacting(): boolean;
setAutoCompactionEnabled(enabled: boolean): void;
async navigateTree(...): Promise<...>;   // 分支导航
getUserMessagesForForking(): ...;
createReplacedSessionContext(): ...;

compact() is manual compaction (the /compact command); _checkCompaction is automatic compaction (threshold reached or overflow recovery). Both fire compaction_start/compaction_end events so the UI can show progress.

navigateTree navigates the session tree – the machinery behind the /tree, /fork, and /clone commands. It may generate a branch summary (Chapter 7), then move the leaf. When forking a session, getUserMessagesForForking extracts the user messages and createReplacedSessionContext builds the new session's context.

These operations all build on Chapter 5's tree structure. AgentSession simply wraps them into product methods with events and UI feedback.

Bash Execution and Export

AgentSession also handles some product-specific features:

async executeBash(...): Promise<...>;   // 直接执行 bash（! 命令）
recordBashResult(...): void;
abortBash(): void;
getSessionStats(): SessionStats;
getContextUsage(): ...;
async exportToHtml(): Promise<...>;     // HTML 导出
exportToJsonl(): ...;
getLastAssistantText(): string;

executeBash supports the !command syntax – users can run shell commands right in the input box without going through the model. The bash_execution_update event streams the command's stdout.

exportToHtml/exportToJsonl export the session – the /export command. getSessionStats/getContextUsage give the UI token usage and cost statistics (from Chapter 2's Usage). getLastAssistantText extracts the last assistant text – print mode uses it to output the final result.

Walkthrough: A /model Switch + a Question

Let's tie AgentSession together. In interactive mode you press Ctrl+P to switch models, then ask a question.

  1. Ctrl+P: InteractiveMode captures the keybinding and calls session.cycleModel("next"). AgentSession takes the next model from scopedModels and calls setModel. setModel updates the core Agent's state, persists a ModelChangeEntry via sessionManager.appendModelChange(provider, modelId), and fires a model-change event. The TUI receives the event and updates the model display in the footer.
  2. Type "keep fixing": prompt("keep fixing"). It does not start with /, so extension commands are skipped. emitInput – no extension interception. Skill/template expansion – no change. Not streaming. Flush bash. Validate the model (the one just switched) and auth. _checkCompaction – threshold not reached. Build the user message and call agent.prompt(messages).
  3. Core loop: enter Chapter 3's loop. prepareNextTurn rebuilds context from the session tree between turns, picking up the model change just made – the next turn uses the new model.
  4. Event backflow: the core emits AgentEvent; _handleAgentEvent translates it into AgentSessionEvent; the TUI renders incrementally.

Throughout, AgentSession is the hub: it receives user actions, orchestrates product logic, drives the core loop, translates the event backflow, and persists state. The core Agent always sees only clean messages and configuration.

Practical Takeaways

AgentSession offers four transferable patterns for "how to build a product on top of a minimal core".

Isolate core from product with event translation. The core emits fine-grained events; the product aggregates them into high-level events meaningful to users; the modes subscribe to product events and never touch core events. The problem it solves: the UI being forced to understand the core's internal events, or the core being forced to accommodate the UI's needs. When AgentSession does the translation, the core stays pristine and the UI gets "compaction started" instead of a combination of low-level events.

Turn user input into a processing funnel. Extension interception → skill expansion → template substitution → queue decisions → validation → compaction → drive the core; every step can short-circuit or transform. The problem it solves: product logic scattered everywhere, or crammed into the core loop. When prompt() is a clear funnel, every product concern has a definite place, and the core loop only receives clean input at the end of the funnel.

Force explicit intent instead of silent guessing. Sending a message during streaming requires specifying streamingBehavior, otherwise an error is thrown. The problem it solves: user messages silently dropped or misqueued, causing the confusion of "I said something but the agent didn't react". Demanding explicitness at ambiguity is safer than guessing user intent.

Configuration changes take effect at turn boundaries and are persisted. setModel updates state, persists a change entry, and takes effect between turns via prepareNextTurn. The problem it solves: configuration changes mid-run either don't take effect or conflict with in-flight work. When changes have a definite effective moment and are persisted, both consistency and traceability are guaranteed.

Summary

AgentSession is the heart of the product layer: a 3,333-line central orchestrator. It wraps the core Agent, subscribes to its AgentEvent and translates it into the richer AgentSessionEvent (agent_end with willRetry, a compaction event pair, retry events, queue updates); its prompt() is a product-logic funnel (extension interception, skill/template expansion, streaming queueing, model/auth validation, compaction checks) that hands a clean message to the core loop only at the end; it also manages model switching, thinking levels, compaction, session-tree navigation, bash execution, and export.

It embodies Chapter 6's conclusion perfectly: the core provides the mechanism (loop + event stream), and the product builds its own policy (AgentSession). Because the core is small, it can be cleanly wrapped by such a large product orchestrator – all product complexity lives in AgentSession, and the core loop remains pristine.
