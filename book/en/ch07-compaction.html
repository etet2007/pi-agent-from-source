Chapter 7: Context Compaction and Branch Summaries

Compaction doesn't delete history: it inserts a summary node into the session tree, letting a finite window hold an unbounded task

A finite window, an unbounded task

Every model has a context window: the token limit it can "see" at once. But real coding tasks tend to be long: reading dozens of files, running dozens of commands, going back and forth for dozens of turns. The transcript grows, and sooner or later it hits that wall. What happens then?

The monolithic approach answers with "four-layer compaction": snip, microcompact, collapse, autocompact, triggered progressively from light to heavy, plus a circuit breaker to prevent infinite retries. That is a submarine-grade complex system.

Pi Agent's answer is far simpler, yet it carries a distinctive twist: compaction does not delete history. Recall Chapter 5: the transcript is an immutable tree. Compaction does not remove nodes from the tree; it inserts a summary node (CompactionEntry) into it. The original history stays on the tree intact; compaction only changes the "context view sent to the model". That makes compaction a reversible view transformation: the user can move back before the compaction point and re-expand that stretch of history.

This chapter dissects the mechanism: when to compact, where to cut, how the summary is written, and how it all meshes with the tree.

When to compact: threshold and estimation

The compaction trigger is a simple inequality. shouldCompact (packages/agent/src/harness/compaction/compaction.ts):

export function shouldCompact(contextTokens: number, contextWindow: number, settings: CompactionSettings): boolean {
	if (!settings.enabled) return false;
	return contextTokens > contextWindow - settings.reserveTokens;
}

When the estimated context token count exceeds "window size minus reserved space", it's time to compact. The defaults (DEFAULT_COMPACTION_SETTINGS):

export const DEFAULT_COMPACTION_SETTINGS: CompactionSettings = {
	enabled: true,
	reserveTokens: 16384,   // 为摘要提示词和输出预留
	keepRecentTokens: 20000, // 压缩后大约保留多少近期 token
};
  • reserveTokens (16,384): space reserved at the top of the window for the summary-generation model call, also serving as a safety margin.
  • keepRecentTokens (20,000): the amount of recent context to keep after compaction, with cut-point selection revolving around this budget.

Token estimation: anchored on authoritative usage

Deciding "how many tokens are there right now" is itself a hard problem: you can't send the entire transcript to the model every time for an exact count. estimateContextTokens uses a clever hybrid strategy:

export function estimateContextTokens(messages: AgentMessage[]): ContextUsageEstimate {
	const usageInfo = getLastAssistantUsageInfo(messages);
	if (!usageInfo) {
		// 没有任何权威用量：全部用启发式估算
		let estimated = 0;
		for (const message of messages) estimated += estimateTokens(message);
		return { tokens: estimated, usageTokens: 0, trailingTokens: estimated, lastUsageIndex: null };
	}
	// 有权威用量：用它做锚，只估算锚点之后的新增消息
	const usageTokens = calculateContextTokens(usageInfo.usage);
	let trailingTokens = 0;
	for (let i = usageInfo.index + 1; i < messages.length; i++) {
		trailingTokens += estimateTokens(messages[i]);
	}
	return { tokens: usageTokens + trailingTokens, usageTokens, trailingTokens, lastUsageIndex: usageInfo.index };
}

The key insight: the usage field of the most recent assistant response is authoritative — it is the token count the provider actually reported for the entire context up to and including that message. The estimate therefore becomes "authoritative anchor + heuristic increment after the anchor". The error is confined to "what's new since the last turn" rather than accumulating across the whole conversation. That is far more accurate than estimating the entire transcript from scratch.

When no anchor exists (for example, at the very start of a session), it falls back to the pure heuristic estimateTokens: a conservative "characters / 4" estimate, with images counted as ESTIMATED_IMAGE_CHARS = 4800 characters:

export function estimateTokens(message: AgentMessage): number {
	let chars = 0;
	switch (message.role) {
		case "user":
			chars = estimateTextAndImageContentChars(message.content);
			return Math.ceil(chars / 4);
		case "assistant":
			// 累加 text、thinking、toolCall（名字 + 参数 JSON）的字符
			return Math.ceil(chars / 4);
		// ... toolResult, bashExecution, branchSummary, compactionSummary
	}
	return 0;
}

calculateContextTokens(usage) takes the total from the authoritative usage: usage.totalTokens || usage.input + usage.output + usage.cacheRead + usage.cacheWrite.

Where to cut: choosing the cut point

Once we've decided to compact, the next question is: where to cut? Everything before the cut goes into the summary; everything after it stays verbatim. findCutPoint makes this decision, aiming to keep roughly keepRecentTokens of recent context.

Valid cut points

Not just any position can serve as a cut. findValidCutPoints filters out the valid ones:

function findValidCutPoints(entries: SessionTreeEntry[], startIndex: number, endIndex: number): number[] {
	const cutPoints: number[] = [];
	for (let i = startIndex; i < endIndex; i++) {
		const entry = entries[i];
		switch (entry.type) {
			case "message": {
				const role = entry.message.role;
				switch (role) {
					case "bashExecution":
					case "custom":
					case "branchSummary":
					case "compactionSummary":
					case "user":
					case "assistant":
						cutPoints.push(i); // 这些消息边界可以切
						break;
					case "toolResult":
						break; // 工具结果不能作为切点
				}
				break;
			}
			// 配置变更条目（model_change 等）不是切点
		}
		if (entry.type === "branch_summary" || entry.type === "custom_message") cutPoints.push(i);
	}
	return cutPoints;
}

Note that toolResult cannot be a cut point. Why? Because the protocol requires every tool_use to be followed by its matching tool_result (the "orphaned tool result" problem from Chapter 3). If you cut between a tool call and its result, the retained second half would begin with an orphaned toolResult, and the provider would reject it. Restricting cut points to message boundaries such as user/assistant guarantees that both halves of the cut are each a valid conversation fragment.

Working the budget backward from the tail

findCutPoint accumulates tokens from the tail backward until it reaches the keepRecentTokens budget, then picks the nearest valid cut point after that position:

export function findCutPoint(entries, startIndex, endIndex, keepRecentTokens): CutPointResult {
	const cutPoints = findValidCutPoints(entries, startIndex, endIndex);
	if (cutPoints.length === 0) {
		return { firstKeptEntryIndex: startIndex, turnStartIndex: -1, isSplitTurn: false };
	}
	let accumulatedTokens = 0;
	let cutIndex = cutPoints[0];

	// 从尾部往前累积，直到达到 keepRecentTokens
	for (let i = endIndex - 1; i >= startIndex; i--) {
		const entry = entries[i];
		if (entry.type !== "message") continue;
		accumulatedTokens += estimateTokens(entry.message);
		if (accumulatedTokens >= keepRecentTokens) {
			// 找到这个位置之后最近的合法切点
			for (let c = 0; c < cutPoints.length; c++) {
				if (cutPoints[c] >= i) { cutIndex = cutPoints[c]; break; }
			}
			break;
		}
	}
	// 往前微调，避免切在 compaction 或 message 之前的"空档"
	while (cutIndex > startIndex) {
		const prevEntry = entries[cutIndex - 1];
		if (prevEntry.type === "compaction" || prevEntry.type === "message") break;
		cutIndex--;
	}
	const cutEntry = entries[cutIndex];
	const isUserMessage = cutEntry.type === "message" && cutEntry.message.role === "user";
	const turnStartIndex = isUserMessage ? -1 : findTurnStartIndex(entries, cutIndex, startIndex);
	return {
		firstKeptEntryIndex: cutIndex,
		turnStartIndex,
		isSplitTurn: !isUserMessage && turnStartIndex !== -1,
	};
}

The logic: count backward from the newest message until about 20,000 tokens have accumulated, then align to the nearest valid cut point. The retained tail is thus roughly keepRecentTokens in size, and everything before the cut goes into the summary.

Split turn: cutting mid-turn

There's a subtle case: the cut point can land in the middle of a turn; say a single user request triggers ten tool calls, and the cut happens to fall right after the fifth. The "retained tail" after the cut would then begin with a tool result that has no context, leaving the model confused.

findCutPoint detects this via the isSplitTurn flag: if the cut point isn't a user message, it uses findTurnStartIndex to walk back to the start of that turn (the user message that began it). isSplitTurn: true means "the cut has split a turn in two".

This case needs special handling: the retained tail (the second half of a turn) needs an extra note about "what happened in the first half". We'll see shortly how compact resolves it with a dedicated "turn prefix" summary.

Preparation: prepareCompaction

prepareCompaction turns the cut-point decision into a CompactionPreparation holding everything compaction needs as input:

export function prepareCompaction(pathEntries, settings): Result<CompactionPreparation | undefined, CompactionError> {
	// 如果路径为空，或最后一个条目已经是 compaction，无需压缩
	if (pathEntries.length === 0 || pathEntries[pathEntries.length - 1].type === "compaction") {
		return ok(undefined);
	}

	// 找到上一个 compaction（用于迭代更新摘要）
	let prevCompactionIndex = -1;
	for (let i = pathEntries.length - 1; i >= 0; i--) {
		if (pathEntries[i].type === "compaction") { prevCompactionIndex = i; break; }
	}
	let previousSummary: string | undefined;
	let boundaryStart = 0;
	if (prevCompactionIndex >= 0) {
		previousSummary = (pathEntries[prevCompactionIndex] as CompactionEntry).summary;
		// 边界从上次压缩的 firstKeptEntry 开始
		// ...
	}

	const tokensBefore = estimateContextTokens(buildSessionContext(pathEntries).messages).tokens;
	const cutPoint = findCutPoint(pathEntries, boundaryStart, pathEntries.length, settings.keepRecentTokens);
	const firstKeptEntryId = pathEntries[cutPoint.firstKeptEntryIndex].id;

	// 三段消息：
	const historyEnd = cutPoint.isSplitTurn ? cutPoint.turnStartIndex : cutPoint.firstKeptEntryIndex;
	const messagesToSummarize = []; // 边界 → historyEnd：进主摘要
	const turnPrefixMessages = [];  // turnStart → 切点：split-turn 的前半，单独摘要
	const retainedTail = [];        // 切点 → 末尾：保留原文

	const fileOps = extractFileOperations(messagesToSummarize, pathEntries, prevCompactionIndex);

	return ok({ firstKeptEntryId, messagesToSummarize, turnPrefixMessages, retainedTail, isSplitTurn, tokensBefore, previousSummary, fileOps, settings });
}

It slices the path into three segments:

  • messagesToSummarize: the messages from the boundary to the cut point (or the split turn's starting point), which will be compacted into the main summary.
  • turnPrefixMessages: only present on a split turn: the first half of the cut turn, which needs its own summary.
  • retainedTail: the recent messages after the cut point, kept verbatim and stored directly on the compaction entry.

Note previousSummary: if compaction has already happened, this run doesn't start from scratch; it incrementally updates on top of the previous summary. That's an important optimization, as we'll see below.

fileOps, meanwhile, extracts the files that were read or modified within this stretch of history (extractFileOperations) and stores them in the compaction entry's details. The post-compaction context thus still "remembers" which files were touched: CompactionDetails { readFiles, modifiedFiles }.

How the summary is written: a structured prompt

The quality of the summary decides whether the agent can keep working after compaction. Pi Agent constrains the summary format with a highly structured prompt. The system prompt (SUMMARIZATION_SYSTEM_PROMPT) first pins the model into a "summary-only" role:

You are a context summarization assistant. Your task is to read a conversation between a user and an AI assistant, then produce a structured summary following the exact format specified.

Do NOT continue the conversation. Do NOT respond to any questions in the conversation. ONLY output the structured summary.

Then the user prompt (SUMMARIZATION_PROMPT) dictates the exact output format:

## Goal
[What is the user trying to accomplish?]

## Constraints & Preferences
- [Any constraints, preferences, or requirements mentioned by user]

## Progress
### Done
- [x] [Completed tasks/changes]
### In Progress
- [ ] [Current work]
### Blocked
- [Issues preventing progress, if any]

## Key Decisions
- **[Decision]**: [Brief rationale]

## Next Steps
1. [Ordered list of what should happen next]

## Critical Context
- [Any data, examples, or references needed to continue]

Keep each section concise. Preserve exact file paths, function names, and error messages.

The format is carefully designed. It doesn't "compress the conversation into a paragraph"; it reconstructs the conversation as a handoff document: goal, constraints, progress (done / in progress / blocked), key decisions, next steps, critical context. The closing line, "Preserve exact file paths, function names, and error messages", matters most: a summary may lose wording, but it must not lose exact identifiers, because the work ahead depends on them.

Iterative updates: UPDATE_SUMMARIZATION_PROMPT

If a previousSummary already exists (compaction has happened before), UPDATE_SUMMARIZATION_PROMPT is used instead. It places the old summary inside a <previous-summary> tag and asks the model to update incrementally rather than rewrite:

Update the existing structured summary with new information. RULES:

- PRESERVE all existing information from the previous summary

- ADD new progress, decisions, and context from the new messages

- UPDATE the Progress section: move items from "In Progress" to "Done" when completed

- PRESERVE exact file paths, function names, and error messages

This avoids the waste of "re-summarizing the entire history on every compaction". On the second compaction, the model only needs to read "the previous summary plus the messages added since", not "the full original history". Compaction cost therefore doesn't grow linearly with session length.

Generation: generateSummaryWithUsage

The actual generation call (generateSummaryWithUsage) has a few details:

const maxTokens = Math.min(
	Math.floor(0.8 * reserveTokens),
	model.maxTokens > 0 ? model.maxTokens : Number.POSITIVE_INFINITY,
);
// ...
const response = await completeSimpleWithRetries(models, model, {
	systemPrompt: SUMMARIZATION_SYSTEM_PROMPT,
	messages: summarizationMessages,
}, completionOptions, retry, callbacks);
  • Output cap: maxTokens is the smaller of 0.8 * reserveTokens and the model's own limit; summary output stays within the reserved space and can't blow up the window on its own.
  • Isolated request: completeSimpleWithRetries gives the summary call a brand-new sessionId and cacheRetention: "none":
export async function completeSimpleWithRetries(models, model, context, options, retry?, callbacks?) {
	// 摘要是独立请求：隔离路由，避免写入无法复用的缓存
	const requestOptions = { ...options, cacheRetention: "none", sessionId: uuidv7() };
	return retryAssistantCall(() => models.completeSimple(model, context, requestOptions), retry, requestOptions.signal, callbacks);
}

Why isolate it? Because the summary request's content (serialized history + the summarization prompt) differs completely from a normal conversation's prompt prefix, so writing a prompt cache for it is wasteful: that cache would never be reused. A fresh sessionId with no cache avoids polluting the main conversation's cache statistics. It's also wrapped in retryAssistantCall (the assistant-level retry from Chapter 2), making summary generation resilient to transient failures.

Putting it together: compact and split turns

compact wires preparation and generation together and produces the final CompactionResult:

export async function compact(preparation, models, model, customInstructions?, signal?, thinkingLevel?, retry?, callbacks?): Promise<Result<CompactionResult, CompactionError>> {
	const { firstKeptEntryId, messagesToSummarize, turnPrefixMessages, retainedTail, isSplitTurn, tokensBefore, previousSummary, fileOps, settings } = preparation;

	let summary: string;
	let summaryUsage: Usage;

	if (isSplitTurn && turnPrefixMessages.length > 0) {
		// split-turn：先摘要历史，再单独摘要这一轮的前半
		let historyText = "No prior history.";
		if (messagesToSummarize.length > 0) {
			const historyResult = await generateSummaryWithUsage(messagesToSummarize, ...);
			if (!historyResult.ok) return err(historyResult.error);
			historyText = historyResult.value.text;
		}
		const turnPrefixResult = await generateTurnPrefixSummary(turnPrefixMessages, ...);
		if (!turnPrefixResult.ok) return err(turnPrefixResult.error);
		summary = `${historyText}\n\n---\n\n**Turn Context (split turn):**\n\n${turnPrefixResult.value.text}`;
		summaryUsage = combineUsage(...);
	} else {
		// 普通情况：一次摘要
		const summaryResult = await generateSummaryWithUsage(messagesToSummarize, ...);
		if (!summaryResult.ok) return err(summaryResult.error);
		summary = summaryResult.value.text;
		summaryUsage = summaryResult.value.usage;
	}
	// 返回 { summary, firstKeptEntryId, tokensBefore, usage, retainedTail, details: fileOps }
}

The split-turn handling is the highlight: when the cut splits a turn in two, compact runs two summaries: one regular history summary (SUMMARIZATION_PROMPT), and one dedicated "turn prefix summary" (TURN_PREFIX_SUMMARIZATION_PROMPT) that uses a different format:

This is the PREFIX of a turn that was too large to keep. The SUFFIX (recent work) is retained.

## Original Request / ## Early Progress / ## Context for Suffix

The two pieces are then joined. That way the retained tail (the second half of a turn) gets an account of "what happened in the first half", and the model never sees a headless tool result.

CompactionResult carries summary, firstKeptEntryId (where the retained history begins), tokensBefore, usage, retainedTail (the retained tail messages), and details (the file operations).

Meshing with the tree: how compaction takes effect

The result produced by compact is ultimately written by AgentHarness (or the product layer) as a CompactionEntry appended to the session tree. Recall defaultContextEntryTransform from Chapter 5: on every subsequent context build, if this compaction entry is on the path, the context becomes "[compaction] + retained tail".

The whole compaction pipeline thus closes the loop:

And the original history (the entries behind messagesToSummarize) is never deleted. It stays on the tree. When the user moveTos back before the compaction point, defaultContextEntryTransform no longer sees that compaction entry (it lies off the path), and the original history re-expands. Compaction is reversible.

This is the fundamental difference between Pi Agent and "deletive compaction". Deletive compaction (splicing old messages out of an array) is simple but irreversible, and it forfeits the ability to "look back at history". Pi Agent uses the tree to separate "storage" from "view"; the cost is one more layer of abstraction, and the payoff is that compaction, branching, and backtracking all become natural and reversible.

Branch summaries: the handoff when switching branches

Besides compaction, there's another kind of summary: branch summarization (packages/agent/src/harness/compaction/branch-summarization.ts).

Recall Chapter 5: the user can moveTo another branch on the session tree. When you switch from branch A to branch B, what happened on branch A may be useful context for the work ahead on branch B ("I just tried plan X on another branch; it didn't work"). generateBranchSummary generates a summary (BranchSummaryEntry) for a branch as you leave it, so that the essence of that exploration isn't lost when you switch away and back.

collectEntriesForBranchSummary gathers the branch entries to summarize, and generateBranchSummary produces the summary with a similar structured prompt. It shares compaction's philosophy of "reconstructing the conversation as a structured handoff document"; only the trigger differs: compaction fires on "context is too full", branch summarization on "I'm leaving this branch".

AgentHarness.navigateTree (Chapter 6) triggers it during branch navigation: the phase switches to branch_summary, and the session_before_tree/session_tree hooks fire.

Practical Takeaways

Pi Agent's compaction offers four transferable patterns for "managing an agent's finite context".

Anchor on authoritative usage; estimate only the increment. Use the real token count reported by the provider in the latest response as the anchor, and apply heuristic estimation only to the messages added after it. The problem it solves: heuristic estimation over the whole transcript accumulates error, while exact counting is too expensive. The anchor method confines the error to "the most recent turn", balancing cost against accuracy.

Align cut points to protocol-legal boundaries. A cut point must not fall between a tool call and its result, or the retained second half would start with an orphaned result. The problem it solves: a naive "cut by token count" can produce protocol-illegal fragments. Constraining cut points to legal boundaries (user/assistant) guarantees both halves are valid on their own.

Write the summary as a structured handoff document, not an abbreviation. Constrain the summary with a fixed format (goal / constraints / progress / decisions / next steps / critical context) and force exact identifiers to be preserved. The problem it solves: free-form summaries lose the precise details needed to continue working (file paths, function names, error messages). The structured format turns the summary into a usable handoff document rather than a vague recap.

Compaction is a view transformation, not data deletion. Separate "storing the full history" from "what gets sent to the model": compaction inserts a summary node, the original history is retained, and context builds substitute on demand. The problem it solves: deletive compaction is irreversible and loses the ability to look back and backtrack. When compaction is reversible, the user can freely toggle between "saving tokens" and "reviewing history". The cost is needing a tree-shaped storage model; once again, Chapter 5's tree structure pays off here.

Summary

Pi Agent's compaction is a mechanism designed around the "tree-shaped transcript": shouldCompact judges the timing with "authoritative anchor + incremental estimation", findCutPoint retains roughly keepRecentTokens of recent context at protocol-legal boundaries (and detects split turns), prepareCompaction slices the path into three segments, generateSummary reconstructs the history into a handoff document using a structured prompt (supporting iterative updates and the split-turn's two-part summary), and finally the CompactionEntry produced by compact is appended to the tree: the original history is never deleted; compaction is only a reversible replacement of the context view. Branch summarization, meanwhile, preserves the essence of exploration when switching branches.

It is an order of magnitude simpler than the monolithic approach's "four-layer compaction", yet it sacrifices none of the core capabilities, because the tree absorbs the complexity. Once you understand Chapter 5's tree, the compaction here almost writes itself. That is the value of a good low-level abstraction: it makes the features above it simple.
