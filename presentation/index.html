Pi Agent

源码解析：把复杂性挡在核心之外

从 LLM 边界、Agent Loop 到 AgentSession，读懂一个最小化编码 Agent 的架构选择。

20–25 MIN·CHINESE TECH TALK

今天不做 Pi Agent 的功能清单，也不逐章复述源码书。我们只追一个问题：一个生产级编码 Agent，核心究竟可以小到什么程度？

Pi 的答案不是“少做功能”，而是重新安排复杂性的位置。接下来会沿着模型边界、Agent Loop、产品编排三层往外看。

THE PLACEMENT OF COMPLEXITY
问题设定 · 复杂性守恒
book/index.html

普通 CLI 是确定的：参数进去，动作出来。Agent CLI 不同，模型在运行时生成下一步，工具调用又会改变真实世界。

所以“把代码写少”并不会让风险自动消失。我们要观察的是：Pi 把什么留在核心，把什么交给外围，以及这些选择的代价。

这六个数字先帮我们定位：Pi 不是一个“玩具循环”。当前工作区有九个包单元（不计 install-lock），内置工具目录有七个、默认启用四个；CLI 有 TUI、print（含 JSON）和 RPC 三条消费路径，SDK 则是另一种嵌入入口。

反差在于，核心循环只需要十种事件和两层 while；真正庞大的部分是三千多行的 AgentSession。最小化的是核心，不是整个产品。

Pi 的第一层克制体现在包边界。pi-ai 不认识 Agent，pi-tui 也不认识 LLM；核心只依赖更低层抽象。

这意味着每层都能单独复用。远程、存储、评估是旁支，不反向侵入产品核心。层级本身就是复杂性的防火墙。

Boundary · StreamFn
06 / 18
模型世界只有一条缝

StreamFn

核心循环不认识 OpenAI、Anthropic 或 Google；它只接收一个返回事件流的函数。

失败不抛异常。
失败被编码进最后一条消息。
stopReason: error | aborted
type StreamFn = (
  model,
  context,
  options?

// done  → AssistantMessage
// error → AssistantMessage
模型边界 · 以契约换循环简洁
packages/agent/src/types.ts

核心循环只通过 StreamFn 触碰模型层。具体提供商、认证、重试、流式协议，都被挡在这条边界外。

最关键的契约是“永不抛出”：失败也要收敛成 AssistantMessage。于是循环不必在每个模型调用周围堆 try/catch，只检查 stopReason。

agent-loop.ts · core/tools

循环只做三件事：按 schema 校验、执行、收集结果。工具是什么、如何渲染、能否并发，都由工具自己声明。

并发策略也很克制：配置要求串行，或者这一批里出现 sequential 工具，就顺序执行；否则可以并行。复杂性被内聚在边界，而不是扩散到循环。

pi-agent-core 里既有纯净核心，也有可选 Harness。最值得注意的是，官方 CLI 产品没有直接使用通用 AgentHarness，而是在核心 Agent 上自建了 AgentSession。

这说明 Harness 只是可选策略，不是框架强加的命运。机制与策略分离之后，产品才能拥有自己的扩展、信任和模式管理。

State · Session Tree
11 / 18
历史不是一个可变数组

会话是一棵树

每条记录有 id 与 parentId；leaf 表示当前所在位置。

压缩不是删历史，
而是追加一条 summary 节点。
APPEND-ONLY SESSION MODEL
root
 └─ user: task
    └─ assistant: tool call
       ├─ toolResult
       │  └─ assistant: answer  ← leaf
       └─ branch_summary
          └─ user: new direction

moveTo(entryId) → 改变当前位置
compact()       → 追加摘要入口
回溯、分支、压缩成为一等能力
agent/src/harness/session

如果历史只是数组，回退常常意味着复制或删除。Pi 用 parentId 把会话记录组织成树，leaf 指向当前分支。

moveTo 只改变当前位置；压缩追加摘要条目而不是销毁原记录。这让 fork、回溯、分支摘要都能建立在同一个数据模型上。

AgentSession · 3.3K LINES
按 → 逐步点亮
core/agent-session.ts

AgentSession 是产品层的中央编排器。用户输入并不会直接丢给模型，而是先经过扩展、skill 和模板展开、认证与模型校验、压缩判断。

只有当产品关注点都处理完，核心才收到干净消息。这不是复杂性变少，而是复杂性被集中到一个明确的产品边界。

Projection · Three Modes
13 / 18
同一条 AgentSessionEvent 流

三种消费方式

TUI
把事件翻译成可交互终端组件，复杂度主要来自“与人交互”。
Print
输出纯文本或 JSON Lines，给脚本和流水线消费。
RPC
stdin/stdout 上收命令、发事件，供 IDE 或守护进程驱动。

新增一种呈现方式，不需要改 Agent Loop。

事件流即产品层契约
coding-agent/src/modes

三种模式共享同一个 AgentSession，只是消费事件的方式不同。TUI 渲染组件，print 写 stdout，RPC 把操作和事件序列化成 JSON 行。

这条边界的价值在于：新增 IDE 集成或后台服务时，不需要复制 Agent 逻辑，只写新的消费者。

边界与赌注

最小化不是免费午餐，也不是普遍最优。

TRADE-OFFS

最后一幕讨论两个最容易被口号化的地方：扩展和安全。Pi 的路线有明确优势，也把更多责任交给了使用者和执行环境。

Extension · Typed Surface
15 / 18
没有 MCP，不等于没有扩展性

ExtensionAPI

扩展直接运行在同一 TypeScript 进程里，获得编译期类型与完整产品上下文。

core/extensions/types.ts

Pi 不内置 MCP，而是把扩展性集中到 ExtensionAPI。扩展可以注册工具、命令、快捷键和 flag，并订阅三十三个强类型 on 入口。

收益是类型安全和低协议成本；代价是扩展与产品运行在同一进程，跨语言和跨进程生态需要额外桥接。它是取舍，不是单方面胜利。

Security · Trust Boundary
16 / 18
最刺眼的差异

逐工具审批 vs 环境隔离

In-process Permission

每个动作前判断

细粒度审批、权限模式、工具级规则。适合直接运行在用户主机且必须限制动作的场景。

Pi's Bet

先把环境变安全

项目级信任只管资源加载；执行隔离依赖容器、VM 或沙箱。默认进程拥有启动用户的权限。

不能控制执行环境时，逐动作审批仍然可能是必要的。
APPLICABILITY BOUNDARY
最小化安全模型有明确前提
coding-agent/docs/security.md

Pi 没有内置逐工具权限系统。项目级信任只决定是否加载项目本地设置、资源与扩展，它不是沙箱；面对不受信任务，源码文档建议把整个进程放进容器、VM、微虚拟机或策略沙箱。

这把权限系统从核心拿掉；但如果 Agent 裸跑在用户主机上，它就拥有启动用户的权限。无法控制执行环境时，不应机械照搬这条路线。

Takeaway · Architecture
17 / 18
读完源码，留下三句话
边界比功能表重要。 事件流比 UI 形态稳定。 复杂性只会移动，不会消失。
MECHANISM·CONTRACT·TRADE-OFF
可迁移的架构判断
TAKEAWAY

第一，先看边界与依赖方向，再看功能数量。第二，稳定的事件契约能让 TUI、脚本和 RPC 共用一套 Agent 逻辑。

第三，任何“最小化”都必须回答复杂性去了哪里。外推是有效设计，但外围责任必须有人真正承担。
