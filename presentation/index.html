Mental Model · Chat vs Agent
03 / 24
先拆掉第一个误解

Agent 不是“更会聊天”

Chatbot

输入一句话，输出一段话

模型看到消息后生成回答。它可以告诉你“应该修改 README”，但它自己没有文件系统，也没有真的改任何东西。

Agent

边思考，边请求程序行动

程序把工具说明交给模型；模型提出结构化 Tool Call；程序执行后把 Tool Result 再交回模型，直到任务结束。

模型负责“决定下一步”，程序负责“真的去做”。
DECISION IS NOT EXECUTION
Agent = Model + Tools + Loop + State
packages/agent/src/types.ts

这条边界非常重要。模型不会直接访问你的电脑；它只能生成一个请求。真正的权限、校验和副作用都发生在程序侧。

StreamFn

  options?

StreamFn 是模型适配层和核心循环之间的契约。它让“调用哪个厂商”和“循环怎么跑”成为两个问题。

Tool Runtime · Validation and Execution
13 / 24
工具不是随便调用一个函数

一次 Tool Call 要过四道门

01 · Resolve
找到工具
按 name 在当前工具集合里定位定义；不存在就返回错误结果。
02 · Validate
校验参数
用 TypeBox schema 检查 path、command 等字段是否符合契约。
03 · Execute
执行副作用
工具可以顺序或并行运行，并用 update 回报中间进度。
04 · Finalize
形成结果
内容、错误状态和 details 被包装成 Tool Result，交回模型。
内置目录有 7 个工具；默认交给模型的是 read、write、edit、bash 这 4 个。
grep / find / ls ARE AVAILABLE BUT NOT DEFAULT
新增工具不需要修改 Agent Loop
executeToolCalls · core/tools/index.ts

这里能看到“模型提议，程序负责”的完整含义。工具层把 schema、执行和结果格式收在一个契约里。

Control Flow · Stop and New Input
15 / 24
什么时候停，什么时候继续

三种“没有结束”

还有 Tool Call
当前任务还没完成。执行结果写回 Context，内层循环再次调用模型。
Steering
Agent 工作时用户插话。消息在下一个安全点注入当前 Run，改变接下来的方向。
Follow-up
当前任务结束后，队列里还有下一条用户消息。外层循环继续，而不是立刻 agent_end。

真正停止：没有 Tool Call、没有待注入消息、也没有 Follow-up，循环才发出 agent_end。

两层循环对应两种用户插话时机
agent-loop.ts · queues

这一页把循环和真实交互体验连接起来。用户并不总是等 Agent 完全结束后才说下一句话。

State · Session Tree
18 / 24
一次 Run 结束后，历史还要活着

Session 是一棵追加树

每条记录都有 id 与 parentId；当前 leaf 指向正在使用的分支。用户消息、模型回复、工具结果和摘要都成为节点。

压缩不是删除旧消息，而是追加 summary，再让后续分支从摘要继续。
user: 修改 README
 └─ assistant: read
    └─ toolResult: README 内容
       └─ assistant: edit
          └─ toolResult: 已修改
             └─ assistant: bash
                └─ toolResult: tests pass ← leaf

fork(entryId)   → 新分支
compact()       → 追加摘要
moveTo(entryId) → 切换当前位置
回退、分支和压缩共享同一个数据模型
session-manager.ts · harness/session

贯穿任务的每一步都可以进入会话树。这样下一次用户提问时，产品能够恢复完整上下文，而核心循环仍然只处理内存中的消息。

Projection · One Session, Many Consumers
19 / 24
执行逻辑只有一份，呈现方式可以很多

同一事件流，四种入口

贯穿任务中的 message_update、tool_execution_start 和 agent_end，不关心最终是画在终端、写到 stdout，还是发给另一个进程。

Interactive
TUI 把流式文本、工具状态和输入框渲染成交互终端。
HUMAN
Print / JSON
单次执行后退出；文本模式只给最终答案，JSON 模式输出事件行。
SCRIPT
RPC
通过 stdin/stdout 接收命令、发送事件，方便 IDE 或守护进程驱动。
PROCESS
SDK

事件流是产品层的稳定契约。同一任务可以在人类界面、流水线或 IDE 中运行，而无需重写执行逻辑。

Extension · Typed Surface

ExtensionAPI

扩展是运行在同一 TypeScript 进程里的模块。它可以订阅 33 个强类型事件，也可以把新能力注册进产品。

收益：类型直接、协议成本低。
代价：扩展拥有与 Pi 进程相同的权限。

Security · Three Different Questions
22 / 24
不要把“信任”误解成“沙箱”

三层安全边界

Project Trust
决定是否加载项目本地设置、资源、包和扩展；它防止仓库在启动阶段悄悄注入代码。
LOAD
Tool Permission
Pi 不内置逐工具审批弹窗。开始工作后，工具拥有启动 Pi 的用户权限。
ACT
Sandbox
容器、VM、微虚拟机或策略沙箱限制整个进程；真正隔离必须由操作系统或虚拟化边界提供。
ISOLATE
如果不能控制执行环境，就不要把“没有逐动作审批”机械照搬到自己的产品。
PROJECT TRUST IS NOT A SANDBOX
安全模型的适用条件必须讲清楚
coding-agent/docs/security.md

项目级信任、逐工具权限和进程隔离回答的是三个不同问题。Pi 只内置第一层，并建议不受信工作使用外部隔离。

END · Q&A

最后不要只记住两层 while。真正值得带走的是角色之间的边界：模型不执行，工具不决策，循环不持久化，Session 不负责具体呈现。

这些边界让 Pi 的核心小而清楚，也让产品复杂性有明确归属。
